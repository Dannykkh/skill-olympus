# Acceptance Checklist Guide

설계와 구현이 같은 ID로 완료 기준을 주고받는 계약. 젭마인이 약속을 정의하고, 구현 하네스(포세이돈·다이달로스·크로노스)가 이행을 기록하고, 감리(아르고스·클리오)가 확인한다.
시스템 역할 표와 같은 방식이다 — 한 곳에서 정의하고, 나머지 문서는 ID로만 가리킨다. ID가 없으면 다른 문서가 그 항목을 가리킬 수도, 통과 수를 셀 수도, 감리에서 대조할 수도 없다.

이 문서가 형식·ID·상태·증거 규칙의 유일한 정본이다. 다른 스킬은 이 파일을 가리키기만 한다.

---

## 파일 셋

| 파일 | 역할 | 쓰는 쪽 |
|------|------|--------|
| `sections/section-NN-*.md`의 `## Acceptance Criteria` | **정본** — 완료 기준의 정의 | 젭마인 Step 20 (바꿀 때는 설계 변경 절차) |
| `checklist.md` | **집계본** — 섹션 AC를 한 표로 모으고 검증 연결을 붙인 것 | 젭마인 Step 22A가 섹션에서 기계적으로 생성 |
| `checklist-status.md` | **이행 장부** — 항목별 상태와 증거 | 구현 리더(메인)만 갱신. 작업자는 반환값으로 보고 |

세 파일 모두 `<planning_dir>/`에 둔다. 정본은 섹션 파일이므로 `checklist.md`와 다르면 섹션이 맞다. 구현자는 `checklist.md`를 직접 고치지 않는다.

planning_dir이 없는 포세이돈 자유 모드는 태스크별 기준을 같은 형식(`AC-<태스크 번호>-k`)으로 정해 실행 계획에 함께 출력하고, 장부는 activity log의 `## Acceptance` 표로 둔다. 상태·증거 규칙은 아래와 같다.

## ID 규칙

- 형식: `AC-<NN>-<k>` — `NN`은 섹션 번호 2자리, `k`는 그 섹션 안의 순번(1부터).
- 섹션이 없는 경로(젭마인 없이 시작한 다이달로스)는 승인된 제안서의 작업 단위 번호를 `NN`으로 쓴다.
- 한 번 붙인 ID는 바꾸거나 재사용하지 않는다. 항목을 없애면 행을 지우지 않고 `(삭제 — 사유)`로 남긴다.

## 항목 작성 규칙 (섹션 파일)

```markdown
## Acceptance Criteria

- [ ] AC-03-2 회원이 대여 가능한 도서를 신청하면 201과 반납 예정일을 받는다 — 근거: P1, POST /api/loans — 검증: test loans.create.success, QA-07
```

- **관찰 가능한 동작으로 쓴다.** "X 클래스가 있다"가 아니라 "X하면 Y가 된다". 코드가 있다는 사실은 완료가 아니다.
- **근거 1개 이상:** Problem Statement 문제 ID(`P1`…), 화면, 엔드포인트, 역할 ID 중 무엇을 위한 기준인지.
- **검증 1개 이상:** 섹션 Test Scenarios의 테스트 이름, QA 시나리오 ID(`QA-<n>`), 실행 명령, 화면 관찰 중 무엇으로 증명하는지. 아직 모르면 `검증 미정`으로 두되 Step 23이 경고한다.
- **그 섹션 안에서 검증할 수 있어야 한다.** 다른 섹션의 기능이 있어야 확인되는 기준이면 그 섹션을 Dependencies에 넣거나 기준을 그 섹션으로 옮긴다. 아니면 구현 첫 Wave에서 증명할 수 없어 `weak`로 남는다.
- 필드는 ` — 근거:`와 ` — 검증:` 표지로 나눈다. 기준 문장 안에 ` — `가 있어도 표지 앞까지가 문장이다.
- 빌드·회귀 같은 공통 조건은 AC가 아니다 — 섹션의 Quality Gate에 둔다.

## checklist.md 형식

```markdown
# Acceptance Checklist

> 정본: sections/section-*.md의 Acceptance Criteria. 이 파일은 집계본이며 구현 중 직접 고치지 않는다.
> 이행 상태: checklist-status.md

| ID | 섹션 | 완료 기준 | 근거 | 검증 |
|----|------|----------|------|------|
| AC-03-2 | section-03-loans | 회원이 대여 가능한 도서를 신청하면 201과 반납 예정일을 받는다 | P1, POST /api/loans | test loans.create.success, QA-07 |

## 추적 요약

| 문제 | AC |
|------|----|
| P1 | AC-02-1, AC-03-2 |
```

검증 열에는 섹션 파일의 검증 항목에 더해, `qa-scenarios.md`에서 이 AC를 `관련 AC`로 가리키는 QA ID를 덧붙인다.

## checklist-status.md 형식

```markdown
# Checklist Status

> 약속: checklist.md (수정 금지). 이행 상태는 이 파일에만 기록하고, 갱신은 구현 리더(메인)만 한다.
> 상태: proved / weak / missing / contradicted

| ID | 상태 | 증거 | 확인 | 비고 |
|----|------|------|------|------|
| AC-03-2 | proved | `tests/loans.test.ts:48` — `npm test -- loans` 통과 | 2026-10-02 14:10 | |
| AC-05-1 | missing | | | PARK: 결제 키 미발급 |
```

- 구현을 시작할 때 모든 행을 `missing`으로 만든다. 파일이 이미 있으면 새로 만들지 않고 이어서 쓴다(재개).
- 상태는 크로노스 완료 계약과 같은 4상태다:

| 상태 | 의미 |
|------|------|
| `proved` | 증거가 현재 코드에서 재현됨 — 실행한 테스트·명령·화면 관찰 |
| `weak` | 코드는 있으나 실행 증거가 없거나 약함, 또는 그 뒤 관련 코드가 바뀜 |
| `missing` | 증거 없음 |
| `contradicted` | 증거가 오히려 기준을 반증함 — 최우선 수정 대상 |

- **증거 규칙:** `proved`는 실행 결과로만 준다(테스트 이름과 통과, 명령과 출력 요지, 관찰한 화면). "파일·함수가 있다"는 `weak`다.
- 검증 열은 계획된 방법이다. `검증 미정`이거나 다른 방법으로 증명했으면 구현 쪽이 테스트를 만들어도 되고, 장부 증거 칸에 실제로 무엇으로 증명했는지 적는다. `checklist.md`는 고치지 않는다.
- **다시 확인했을 때:** 다시 실행해 실패하거나 기준과 반대로 동작하면 `contradicted`, 인용한 증거를 다시 실행할 수 없거나(테스트가 없어짐 등) 그 뒤 코드가 바뀌어 아직 다시 돌리지 않았으면 `weak`다.
- **계약 모순:** 두 AC를 같은 입력에서 함께 만족할 수 없으면 구현 실패가 아니라 설계 결함이다. 한쪽을 구현하고 다른 쪽을 `contradicted` + `PARK: 계약 모순 — AC-xx와 충돌, 계약 변경 필요`로 남긴다.
- 관련 코드가 다시 바뀌면 해당 `proved` 행은 `weak`로 내리고 재확인한다. 마지막 통합 게이트(빌드·전체 테스트) 뒤에 `proved` 행의 증거를 한 번 더 확인한다.
- 막힌 항목은 상태를 바꾸지 않고 비고에 `PARK: 사유`를 적는다(크로노스의 주차와 같음).
- **완료 판정:** 삭제 행을 뺀 모든 행이 `proved`일 때만 완료다. 하나라도 아니면 완료로 보고하지 않고 "M/N proved, 남은 ID 목록"을 보고한다. `proved`가 아닌 행을 **미이행 AC**라 부른다.

## 작업자 반환 계약

작업자는 맡은 AC ID마다 `ID | 증거 | 상태 제안`을 반환한다. 장부는 구현 리더만 갱신한다(병렬 작업자가 한 파일을 함께 쓰는 충돌을 막고, activity log와 같은 규칙을 따른다).

## 계약 변경

구현을 시작한 뒤(장부가 생긴 뒤) 기준을 바꿔야 하면 설계 변경이다. 범위가 바뀌므로 사용자 승인을 받은 뒤 아래를 따른다. 장부가 생기기 전 젭마인 Step 23에서 고치는 것은 아직 설계 중이므로 이 승인 절차가 필요 없다.
1. 해당 섹션 파일의 Acceptance Criteria를 고친다 (ID 규칙 유지).
2. `checklist.md`를 다시 만든다.
3. `integration-notes.md`에 무엇을 왜 바꿨는지 적는다.
4. 장부의 해당 행을 `missing`으로 되돌린다.

## checklist.md가 없는 경우 (구버전 산출물)

구현 리더가 섹션 파일에서 기계적으로 만든다. 섹션 순서·항목 순서대로 `AC-NN-k`를 붙이고, 근거·검증은 섹션 파일(Test Scenarios 등)에서 찾을 수 있으면 채우고 없으면 `미정`으로 둔다. 기준 문장은 고치지 않는다. activity log에 "checklist.md를 구버전 섹션에서 생성"이라고 남긴다.
