# MCP Specification Guide

계획 단계에서 에이전트(Claude 등 LLM)↔프로그램 간 계약서 `mcp-spec.md`를 작성하는 가이드.

웹·서버·로컬 프로그램은 사람이 화면으로 하는 일을 에이전트도 도구로 할 수 있게 MCP 서버를 함께 둡니다. 그래서 `mcp-spec.md`는 HTTP API가 있을 때만 생기는 `api-spec.md`와 달리 거의 항상 생성됩니다.

- **REST가 있는 프로그램**: 도구는 REST 엔드포인트를 감쌉니다. 도구 블록은 엔드포인트를 **이름과 파라미터 이름으로 참조만** 하고 스키마를 복사하지 않습니다. 스키마를 복사하면 두 문서가 따로 어긋납니다. 도구 블록의 `응답 필드`도 필드 이름(부분집합)만 적고 타입·형식은 `api-spec.md`가 정본입니다. 페이지네이션·에러 형식은 `api-spec.md`의 Conventions를 따릅니다.
- **REST가 없는 로컬 프로그램**(데스크톱·CLI): 도구는 UI가 부르는 것과 같은 **내부 명령**을 감쌉니다. 내부 명령 계약은 이 문서의 `## Internal Commands`가 정본입니다.

어느 쪽이든 검증·권한 검사는 도구가 감싸는 대상(엔드포인트 또는 내부 명령) 한 곳에 있습니다. 도구는 그 대상을 거쳐서만 동작합니다.

## 언제 생성하나?

| 프로젝트 유형 | MCP Spec 생성 |
|--------------|---------------|
| 웹앱 (프론트+백엔드) | ✅ |
| REST/GraphQL API 서버 | ✅ |
| 모바일 앱 + API | ✅ (서버 쪽에 MCP) |
| 데스크톱 앱 | ✅ (stdio) |
| CLI 도구 | ✅ (stdio) |
| 라이브러리/패키지 | ❌ `NOT APPLICABLE: no MCP — 실행되는 프로그램이 아님` |
| 정적 사이트 (API 없음) | ❌ `NOT APPLICABLE: no MCP — 조작할 기능 없음` |

위 표에서 ✅인데 계획에서 MCP를 넣지 않기로 했으면 `NOT APPLICABLE: no MCP — <사유>`를 씁니다. 건너뛸 때도 `mcp-spec.md`를 만들고 이 한 줄만 적어 사유를 남깁니다. 사유 없는 생략은 없습니다. (`api-spec.md`는 HTTP가 없으면 파일을 만들지 않지만, MCP는 기본으로 넣는 것이라 넣지 않은 이유를 남깁니다.)

**MCP 서버가 있다는 것이 모든 기능을 도구로 연다는 뜻은 아닙니다.** 도구 노출은 기본으로 꺼져 있고, 이 문서의 `## Tools`에 적은 것만 열립니다(Conventions 참조).

## 작성 순서

Step 17(`api-spec.md`)과 Step 16(`db-schema.md`) 다음에 씁니다. 화면에서 출발한 API 명세가 먼저 있고, 에이전트 작업에서 출발한 이 문서가 그 위에 얹힙니다.

1. **에이전트 작업 요구 표 작성** — 작업마다 역할, **입력으로 아는 것**, 필요한 결과를 적습니다. 에이전트는 화면과 달리 id를 모르고(이메일·이름·날짜·가게 이름으로 찾아야 함), 여러 화면에 걸친 결과를 한 번에 원하며, 호출 순서를 스스로 정합니다. 그래서 화면 표와 별도 입력입니다. 재료는 다음 순서로 씁니다.
   - `plan.md`·`spec.md`·`interview.md`에 적힌 에이전트 사용 사례 → 근거에 문서와 위치를 적습니다.
   - 위가 없으면 사람이 화면에서 하는 일을 에이전트에게 말로 시킬 일로 바꿔 후보를 만듭니다. 재료는 `api-spec.md` Screen Data Requirements의 액션, 없으면(로컬 프로그램) api-spec-guide 작성 순서 1과 같은 화면 재료(`spec.md`의 역할 표 `화면` 열·화면 설명, `personas-and-journeys.md` 여정, `design-system.md`, `research.md` 메뉴 구조)입니다. 근거는 `화면 액션 파생`이고, 에이전트 사용을 인터뷰하지 않았다는 사실을 `integration-notes.md`에 미결로 한 번 올립니다.
   - 후보 중 노출하지 않기로 한 것(되돌릴 수 없는 작업 등)도 표에 남기고 `도구` 열에 `-`와 사유를 적습니다. 무엇을 일부러 닫았는지가 계약에 남아야 나중에 다시 판단할 수 있습니다.
   - 재료에 없는 작업은 지어내지 않습니다. "AI가 알아서 도와줬으면" 같은 막연한 요구는 작업으로 만들지 않고 미결로 올립니다.
   - 사용 사례가 원하는 역할이 그 기능의 권한 규칙보다 넓으면(예: 인터뷰는 사서가 하길 원하는데 규칙은 관리자만) 권한을 넓히지 않습니다. `역할` 열에는 규칙의 역할을 쓰고 충돌을 괄호로 적은 뒤 미결로 올립니다.
2. **서버 구성 작성** — 전송 방식, 프로세스 구성, 인증, 호출 한도 기본값, 기록 방식을 `## Server`에 적습니다.
3. **감쌀 대상 확인**
   - REST가 있으면: 작업마다 기존 엔드포인트로 되는지 봅니다. 안 되면(자연키 검색, 화면에 없던 발송 등) 먼저 기존 엔드포인트의 필터 추가로 해결되는지 보고, 안 되면 `api-spec.md`에 엔드포인트를 추가합니다(Frontend Caller는 `mcp`). 화면도 부르는 엔드포인트는 Frontend Caller에 화면을 적고, MCP가 부른다는 사실은 Summary의 `MCP Tool` 열로만 표시합니다. 새 필터·검색 컬럼은 `db-schema.md` 인덱스 표와 DDL에도 넣습니다. 추가한 내용은 `integration-notes.md`에 기록합니다.
   - REST가 없으면: UI가 부르는 내부 명령을 모두 `## Internal Commands`에 적고, `호출자` 열에 UI와 도구를 적습니다(UI만 부르면 UI만). 이 표가 로컬 프로그램의 유일한 명령 계약이기 때문입니다. 명령의 검색·필터·정렬 컬럼은 api-spec-guide의 인덱스 역반영과 같이 `db-schema.md` 인덱스 표와 DDL에 넣고 기록합니다.
4. **도구 정의** — 작업마다 도구를 정하고 `## Tools`에 적습니다. 엔드포인트·명령을 1:1로 모두 노출하지 않습니다. 규약은 `## Conventions`를 따릅니다. REST가 있으면 `api-spec.md` Summary의 `MCP Tool` 열에 도구 이름을 채웁니다(영향 파악용).
5. **대응 검사** — 문서 끝의 체크리스트를 통과시킵니다.

````markdown
# MCP Specification

> 이 문서는 에이전트↔프로그램 간의 계약서입니다.
> 구현 중 도구를 추가·변경하면 반드시 이 문서를 먼저 고치세요.

## Server

| 항목 | 내용 |
|------|------|
| 전송 | Streamable HTTP `/mcp` (웹·서버) / stdio (로컬) |
| 프로세스 구성 | 웹 서버에 내장 / 별도 프로세스 — 별도면 실행 중인 앱과 상태를 어떻게 나누는지(같은 명령 모듈 사용, 잠금·트랜잭션, 변경 알림) |
| 감싸는 대상 | REST 엔드포인트 (`api-spec.md`) / 내부 명령 (`## Internal Commands`) |
| 인증 | HTTP: MCP 클라이언트가 사용자 토큰을 얻는 방식 (정해지지 않았으면 미결) / stdio: 실행한 OS 사용자 권한, 앱 안의 어떤 역할로 동작하는지 |
| 호출 한도 기본값 | 예: 사용자당 분당 60회 |
| 기록 | 에이전트 경유 표시 방법 + 쓰기 감사 로그 위치 |

## Conventions

(아래 `## Conventions` 규약을 프로젝트 값으로 채움. REST가 있으면 페이지네이션·에러 형식은 `api-spec.md` Conventions를 따른다고 한 줄로 적고, REST가 없으면 api-spec-guide `## Conventions`와 같은 형식(목록 `{ items, page, size, total }`·크기 상한, 에러 `{ error, message }`)을 여기에 정의)

## Agent Task Requirements

| ID | 작업 | 역할 | 입력으로 아는 것 | 필요한 결과 | 도구 | 근거 |
|----|------|------|------------------|-------------|------|------|
| A1 | 이메일·이름 일부로 회원을 찾아 역할·주문 수 확인 | admin, operator | 이메일 또는 이름 일부 | id, 이름, 이메일, 역할, 주문 수 | `find_users` | `interview.md` 운영 자동화 답변 |
| A2 | 회원 역할 변경 | admin | 이메일, 새 역할 (id는 모름) | 바뀐 역할 | `find_users` → `update_user_role` | `interview.md` 운영 자동화 답변 |

`입력으로 아는 것`이 id가 아니면 그 값으로 찾는 도구가 먼저 있어야 합니다(A2는 A1의 도구로 id를 얻음).

## Internal Commands

REST가 있으면 `NOT APPLICABLE: REST — 도구는 api-spec.md 엔드포인트를 감쌈`.

(로컬 프로그램 예시)

| 명령 | 입력 | 출력 | 에러 (`error` 코드) | 호출자 |
|------|------|------|---------------------|--------|

## Tools

#### `find_users` — 회원 검색

| 항목 | 내용 |
|------|------|
| 작업 | A1, A2 |
| 구성 대상 | `GET /api/users` (`q`, `role`, `page`, `size`) |
| 허용 역할 | admin, operator (엔드포인트와 같음) |
| annotations | `readOnlyHint: true`, `openWorldHint: false` |
| 호출 한도 | 기본값 |
| 응답 필드 | `id`, `name`, `email`, `role`, `orderCount`, `page`, `total` |
| 개인정보 | `email` 포함 — 작업 A1·A2가 이메일로 대상을 확인하므로 넣음 |

**에이전트 설명:**
> 이메일이나 이름 일부로 회원을 찾는다. 회원 id를 모를 때 먼저 호출한다. 한 번에 최대 20명을 돌려주며 `total`이 더 크면 `page`를 올려 다시 호출한다. 역할을 바꾸려면 찾은 `id`로 `update_user_role`을 호출한다.

**실행 에러 (`isError: true`):**
| error | 모델용 문구 |
|-------|-------------|
| `FORBIDDEN` | 회원 검색은 admin·operator만 할 수 있다. 사용자에게 권한이 필요하다고 알리고 다시 시도하지 않는다. |

---

#### `update_user_role` — 회원 역할 변경

| 항목 | 내용 |
|------|------|
| 작업 | A2 |
| 구성 대상 | `PUT /api/users/:id` (`role` 필드만 — 이름·이메일은 바꾸지 않음) |
| 허용 역할 | admin (엔드포인트의 admin, user(본인) 중 역할 변경 권한이 있는 admin만) |
| annotations | `destructiveHint: true`, `idempotentHint: true`, `openWorldHint: false` |
| 호출 한도 | 기본값 |
| 응답 필드 | `id`, `role` |
| 개인정보 | 없음 |

**에이전트 설명:**
> 회원 한 명의 역할을 admin, operator, user 중 하나로 바꾼다. 기존 역할을 덮어쓰므로 호출 전에 대상 회원(이름·이메일)과 새 역할을 사용자에게 보여 주고 확인을 받는다. 회원 id를 모르면 `find_users`를 먼저 호출한다. 이름·이메일 수정에는 쓰지 않는다.

**실행 에러 (`isError: true`):**
| error | 모델용 문구 |
|-------|-------------|
| `USER_NOT_FOUND` | id {id} 회원이 없다. `find_users`로 이메일을 검색해 id를 확인한 뒤 다시 호출한다. |
| `VALIDATION_ERROR` | role은 admin, operator, user 중 하나여야 한다. 사용자가 말한 역할이 셋 중 무엇인지 확인한다. |
| `FORBIDDEN` | 역할 변경은 admin만 할 수 있다. 사용자에게 권한이 없다고 알리고 다시 시도하지 않는다. |

`DELETE /api/users/:id`처럼 되돌릴 수 없는 작업은 노출하지 않는 것이 기본이라 도구 블록을 만들지 않습니다.

|------|-----------|------|-----------|------------------|-----------|
| `find_users` | `GET /api/users` | A1, A2 | admin, operator | 조회 | 기본값 |
| `update_user_role` | `PUT /api/users/:id` (`role`만) | A2 | admin | 덮어쓰기 · 확인 필요 | 기본값 |
````

## Conventions

- **노출은 기본으로 꺼짐.** `## Tools`에 블록이 있는 것만 도구가 됩니다. 되돌릴 수 없는 작업(삭제, 메일·알림 발송, 결제 등)은 기본으로 노출하지 않으며, 노출하면 도구 블록에 사유를 적고 에이전트 설명에 "호출 전 사용자 확인"을 넣습니다.
- **이름**: snake_case `동사_대상` (`find_users`, `update_user_role`). 서버 안에서 고유하고 영문·숫자·`_`·`-`·`.`만 씁니다.
- **감싸는 대상을 거침**: 도구는 구성 대상(엔드포인트 또는 내부 명령)을 거쳐서만 동작합니다. DB·파일을 직접 읽거나 쓰는 도구는 UI가 받는 검증·권한 검사를 건너뛰므로 만들지 않습니다. 계획 재료가 직접 접근을 적었더라도 내부 명령을 거치게 바꾸고 `integration-notes.md`에 기록합니다.
- **에이전트 설명**: 모델이 도구를 고르는 근거입니다. 사람용 설명을 복사하지 않고 세 가지를 씁니다 — 무엇을 하는가 / 언제 쓰는가(어떤 값을 알고 있을 때, 어떤 도구 다음에) / 쓰지 말아야 할 때와 대신 쓸 도구. 목록 도구는 한 번에 돌려주는 건수와 다음 페이지를 받는 법도 적습니다.
- **입력**: 에이전트가 아는 값으로 시작할 수 있어야 합니다. id를 받는 도구가 있으면 그 id를 돌려주는 도구(이메일·이름으로 찾는 도구 등)도 있어야 합니다.
- **권한**: 도구의 허용 역할은 구성 대상의 허용 역할을 넘지 않습니다. 에이전트는 호출한 사용자의 권한으로 구성 대상을 부르고, 권한 검사는 구성 대상이 합니다. 도구가 검사를 대신하거나 건너뛰지 않습니다.
- **위험 표시 (`annotations`)**: MCP 스펙의 기본값은 `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true`입니다. 아무것도 적지 않은 도구는 가장 위험한 쪽으로 취급되므로 도구마다 명시합니다. 표시는 클라이언트를 위한 힌트일 뿐이며 안전장치는 구성 대상의 권한 검사입니다.

  | 도구 성격 | 표시 |
  |-----------|------|
  | 조회만 | `readOnlyHint: true` |
  | 추가만 (기존 값을 바꾸지 않음) | `destructiveHint: false` |
  | 덮어쓰기·삭제 | `destructiveHint: true` + 에이전트 설명에 "호출 전 사용자 확인" |
  | 추가만이지만 되돌릴 수 없는 외부 작업 (메일·알림 발송, 결제) | `destructiveHint: false`, `openWorldHint: true` + 에이전트 설명에 "호출 전 사용자 확인" |
  | 같은 인자로 다시 불러도 상태가 더 바뀌지 않음 (두 번째 호출이 에러를 내도 상태가 그대로면 해당) | `idempotentHint: true` |
  | 이 프로그램 안에서만 동작 (외부 발송·결제 없음) | `openWorldHint: false` |

- **대량 처리**: 가져오기·일괄 변경처럼 한 번에 많은 행을 바꾸는 도구는 노출하면 한 번에 처리할 건수 상한을 도구 블록에 적고, 되돌리는 방법이 없으면 되돌릴 수 없는 작업으로 봅니다.
- **호출 한도**: 서버는 도구 호출 수를 제한합니다(MCP 스펙의 MUST). 에이전트는 반복문으로 같은 도구를 수십 번 부를 수 있기 때문입니다. `## Server`에 기본값을 적고, 외부 발송·결제·대량 처리 도구는 도구 블록에 도구별 한도와 **같은 대상 중복 방지**(예: 같은 회원에게 24시간 1회)를 적습니다. 중복 방지에 발송 이력 같은 저장소가 필요하면 `db-schema.md`에 추가하고 기록합니다.
- **에이전트 경유 기록**: 도구가 구성 대상을 부를 때 에이전트 경유 표시(예: 헤더 `X-Invoked-Via: mcp`, 명령 컨텍스트 `via: "mcp"`)를 붙이고, 쓰기 도구 호출은 감사 로그에 남깁니다(사용자, 도구, 인자 요약, 결과, 시각). 이 표시는 기록용입니다. 위조할 수 있으므로 권한을 넓히는 근거로 쓰지 않습니다(에이전트 경유일 때 더 막는 데는 쓸 수 있음).
- **응답 크기**: 목록 도구는 구성 대상과 같은 페이지네이션을 씁니다. 응답은 작업에 필요한 필드만 돌려주고 구성 대상 응답 전체를 그대로 넘기지 않습니다(모델 컨텍스트 비용). 필드가 많고 작업마다 필요한 필드가 다르면 `fields` 파라미터로 고르게 합니다.
- **개인정보**: 응답에 개인정보 필드(이메일·전화번호 등)가 있으면 도구 응답에 넣을지 가릴지를 도구마다 적습니다. 도구 응답은 MCP 클라이언트를 거쳐 모델 제공자에게 전달됩니다. 로컬 전용·오프라인을 약속한 프로그램이면 이 점을 미결로 올려 사용자 확인을 받습니다.
- **에러**: 없는 도구·형식이 틀린 요청은 프로토콜 에러(JSON-RPC `error`)이고, 구성 대상이 돌려준 에러는 실행 에러로 `isError: true` 결과에 담습니다. MCP 서버 자신이 내는 실행 에러(호출 한도 초과 `RATE_LIMITED` 등)도 같은 방식으로 `## Conventions`에 공통 행으로 적고, 문구에 언제 다시 시도할 수 있는지를 넣습니다. 실행 에러는 구성 대상의 `error` 코드를 그대로 쓰되, 사용자용 `message`와 별도로 **모델용 문구**를 둡니다 — 무엇이 틀렸고 다음에 무엇을 하면 되는지(고칠 값, 먼저 부를 도구, 다시 시도하지 말 것).
- **도구 수**: 도구가 수십 개를 넘어 모델이 고르기 어려워지면, 서버 목록 → 도구 목록 → 스키마 순으로 필요한 것만 찾게 하는 단계적 탐색을 검토하고 기록합니다.
- **구현**: 도구의 입력·응답 스키마는 가능하면 구현된 엔드포인트 스키마(OpenAPI 등)나 내부 명령의 타입에서 생성하고, 노출 여부·에이전트 설명·위험 표시·한도·모델용 문구만 손으로 씁니다.

## 구현 중 도구 추가/변경 규칙

**⚠️ 이 규칙은 섹션 파일과 실행 파일에 포함되어야 합니다:**

```
구현 중 MCP 도구를 추가하거나 바꾸면:
1. mcp-spec.md를 먼저 고친다 (도구 블록, Summary, REST면 api-spec.md Summary의 MCP Tool 열)
2. 에이전트 설명·annotations·노출 여부·호출 한도는 모델의 행동을 바꾸는 계약이다 — 바꾼 이유를 기록한다
3. 노출을 새로 켜거나, 위험 표시를 낮추거나(예: destructive → 아님), 한도를 푸는 변경은 사용자 확인을 받는다
4. 구성 대상(엔드포인트·내부 명령)이 바뀌면 그 대상을 감싸는 도구 블록도 함께 고친다

절대 하지 말 것:
- mcp-spec에 없는 도구를 암묵적으로 추가
- DB·파일을 직접 읽거나 쓰는 도구 (구성 대상을 건너뜀)
- 구성 대상의 권한 검사를 건너뛰거나 더 넓은 권한으로 동작하는 도구
- 에이전트 경유 표시를 근거로 권한을 넓히기
```

## 대응 검사

mcp-spec.md를 마치기 전과 Step 23 Final Status에서 확인:

- [ ] `## Server`의 전송·프로세스 구성·인증·호출 한도 기본값·기록이 채워졌다 (정해지지 않은 것은 미결로 올렸다)
- [ ] Agent Task Requirements의 모든 작업이 도구 1개 이상에 대응하거나, `도구` 열에 `-`와 노출하지 않는 사유가 있다 (막연한 요구·권한 충돌은 미결로 올렸다)
- [ ] 모든 도구에 구성 대상이 있다 — REST면 `api-spec.md`에 실재하는 엔드포인트, 아니면 `## Internal Commands`의 명령
- [ ] REST면 `api-spec.md` Summary의 `MCP Tool` 열과 `## Tools`가 1:1이고, Frontend Caller가 `mcp`인 엔드포인트마다 도구가 있다
- [ ] DB·파일을 직접 다루는 도구가 없다
- [ ] id를 입력으로 받는 도구마다 그 id를 돌려주는 도구가 있다
- [ ] 도구의 허용 역할이 구성 대상의 허용 역할을 넘지 않는다
- [ ] 에이전트 설명에 언제 쓰는지와 쓰지 말아야 할 때(대신 쓸 도구)가 있다
- [ ] 모든 도구가 `annotations`를 명시했다 — 조회 도구는 `readOnlyHint: true`, 덮어쓰기·삭제·외부 발송 도구는 설명에 호출 전 사용자 확인이 있고, 되돌릴 수 없는 작업을 노출했으면 사유가 있다
- [ ] 외부 발송·결제·대량 처리 도구마다 도구별 호출 한도와 중복 방지가 있다
- [ ] 쓰기 도구의 감사 기록 방법이 `## Server`에 있다
- [ ] 실행 에러마다 모델용 문구가 있고, 문구가 다음 행동(고칠 값, 먼저 부를 도구, 다시 시도하지 말 것)을 알려 준다
