# 상태 변경의 신뢰성 계약

멱등성, 분산 트랜잭션, 메시지 중복 소비, 데이터 일관성을 설계·구현·검증에 연결하는 공통 기준입니다.
용어를 모두 적용하는 대신 **요청된 기능에서 실패하거나 반복될 수 있는 경계**를 먼저 찾습니다.
기존 [서버 검증 계약](security-audit.md#api-직접-호출서버-검증-계약)의 인증·인가·거부 후 무변경을
유지하면서, 정상 요청의 응답 유실·부분 성공·재전달을 보완합니다. 전체 보안 감사 실행을 뜻하지 않습니다.

## 적용 범위와 정본

- 상태 변경·외부 부수 효과가 있는 기능의 설계/변경, 또는 중복·누락·상태 불일치 장애에 적용합니다.
  실제 영향 경로의 DB·외부 서비스·작업 큐·웹훅·캐시/읽기 모델과 기존 보장을 확인합니다.
- 단일 DB에서 끝나면 기존 트랜잭션·제약·원자적 갱신을 우선합니다. 서비스 분리, 큐, 분산 락,
  Saga, Outbox, 새 멱등성 테이블을 기본 요구로 추가하지 않습니다. 필요한 보장과 실패 틈을
  확인한 뒤 기존 구조로 해결되지 않을 때만 대안을 비교합니다.
- 조회·정적 페이지·국소 스타일 변경에는 관련 없는 검사를 붙이지 않습니다. 외부 결제 한 곳만
  연동한 단일 앱도 로컬 DB와 외부 처리 사이의 원자성 경계는 존재할 수 있습니다.
- 결정은 기존 spec·API/DB 명세·섹션 Module Contract와 AC/QA에 연결합니다. 전용 장부나 필수
  문서 양식을 만들지 않습니다. 미정인 업무 규칙은 제안과 확정 사항을 구분하고 `UNVERIFIED`,
  해당 없음은 근거와 함께 `N/A`로 둡니다. 단순 조회만 보고 변경 경로까지 제외하지 않습니다.

## 해당 기능에서 정할 계약

| 관점 | 설계·구현·리뷰에서 확인할 결정 |
|---|---|
| 업무 불변 조건 | 무엇이 한 번만 일어나야 하는지, 허용 수량/금액/상태와 데이터의 기준 원천. 항상 지킬 조건과 일시적으로 달라도 되는 읽기 결과를 구분 |
| 동일 작업 식별 | 같은 업무 요청과 새 요청의 구분, 키의 사용자/조직·업무 범위, 같은 키에 다른 입력의 처리, 보존 기간과 만료 후 늦은 재전송 정책 |
| 원자성 경계 | 한 트랜잭션에 포함되는 쓰기와 포함되지 않는 외부 효과. 중복 판별·업무 변경·결과 기록 사이의 장애/동시 실행을 막는 방법 |
| 실패와 복구 | 처리 중·성공·확정 실패·결과 미확정의 구분, 결과 조회/재시도/보상의 조건·상한·소유자. 복구 자체 실패와 수동 대사 경로 |
| 메시지와 수렴 | 발행·처리·완료 확인의 보장, 메시지/업무 식별자, 필요한 순서/버전 규칙, 일시 불일치의 허용 범위·목표 시간과 미수렴 탐지·복구 |

### 멱등성과 동시 실행

같은 작업의 반복으로 **업무 효과가 추가되지 않는지** 확인합니다. 응답 바이트·코드가 항상 같아야
한다는 뜻은 아니며, 처리 중·이미 완료된 결과를 조회/응답하는 방법은 API 계약으로 정합니다.
정상적인 새 주문까지 내용이 같다는 이유로 합치지 않고, 키가 달라도 같은 주문의 결제가 한 번이어야
한다면 업무 키의 유니크 제약·상태 전이도 확인합니다. 키는 인증·인가를 대신하지 않습니다.

중복 조회 후 쓰기, 메모리 플래그, 버튼 비활성화만으로 동시 요청과 프로세스 재시작을 막았다고
판정하지 않습니다. 같은 DB의 처리 완료 기록과 업무 변경은 필요한 원자성을 함께 보장해야 합니다.
먼저 완료로 기록하면 작업이 유실될 수 있고, 효과를 만든 뒤 기록하면 재실행 때 중복될 수 있습니다.
외부 효과에는 그 시스템의 멱등성·결과 조회 보장과 로컬 복구를 함께 연결합니다.
응답 타임아웃만으로 실패를 확정하거나 새 키로 같은 작업을 다시 시작하지 않습니다.

### 분산 트랜잭션과 부분 성공

DB 커밋과 외부 API/메시지 발행을 같은 로컬 트랜잭션으로 묶었다고 가정하지 않습니다.
각 경계에서 한쪽만 성공했을 때의 지속 가능한 복구 정보를 확인합니다. DB 변경과 발행 의도를
함께 저장하는 Outbox 등은 이 틈을 해결하는 선택지이며, 그 발행·소비의 중복 방지는 별도로 필요합니다.

여러 단계의 업무는 기존 보장에 따라 재개·재시도·보상 중 적절한 경로를 정합니다. Saga 등 보상
흐름은 전역 ACID 롤백과 같지 않습니다. 이미 보낸 메일·배송 같은 되돌릴 수 없는 효과, 다른
작업의 동시 변경, 보상 자체의 중복·실패를 고려합니다. 무한 재시도로 덮지 않고 상한 이후 상태와
복구 담당을 남깁니다. 외부 결과를 모르면 먼저 조회/대사하고 무조건 취소나 재청구하지 않습니다.

### 메시지 중복 소비와 데이터 일관성

실제 브로커·웹훅의 전달/재전달 보장을 확인합니다. 발행 확인과 소비 완료 확인은 다른 증거입니다.
처리 완료를 안전하게 기록하기 전 완료 확인(ack/offset commit)을 보내 유실시키지 않으며,
효과 저장 후 확인 전에 중단되어 다시 전달돼도 업무 효과가 늘지 않아야 합니다. 처리한 메시지
기록과 같은 DB의 변경은 함께 보호하고, 외부 효과는 앞 절의 별도 경계로 검증합니다.
브로커의 `exactly-once`라는 이름만으로 외부 DB·결제·메일까지 한 번 처리됨을 주장하지 않습니다.

순서가 중요한 흐름은 지연·순서 역전·재처리가 최신 상태를 되돌리지 않는지 확인합니다. 모든 큐에
전역 순서를 강제하지 않습니다. 재시도 소진·격리 메시지(DLQ 등)의 탐지, 재처리 조건과 담당을 정하고,
격리됐다는 사실을 업무 성공으로 기록하지 않습니다. 중복 판별 보존 기간은 실제 재전달/재처리
기간과 대조합니다. 같은 업무에서 새 메시지 ID가 생길 수 있으면 업무 단위 중복도 확인합니다.

캐시·복제본·읽기 모델의 지연을 허용하면 기준 원천, 허용되는 중간 상태, 수렴 확인 방법·목표 시간,
초과 시 알림/대사를 정합니다. '최종적 일관성'만 적고 영구 누락을 통과시키지 않습니다.
목표 시간이 미정이면 임의 수치를 만들지 말고 미확정으로 남깁니다.

## 실행으로 확인할 사례

허용된 격리 환경과 테스트 데이터로 정상 대조군부터 확인하고 **해당 경계의 사례만** 기존 QA에
연결합니다. 외부 부수 효과는 sandbox/테스트 대역을 사용하며 운영 장애를 유발하지 않습니다.

| 상황 | 확인할 결과 |
|---|---|
| 같은 작업 순차 반복·제한된 동시 요청 | 업무 효과 1회, 처리 중/완료 응답 계약, 서로 다른 정상 작업은 각각 처리 |
| 같은 키·다른 입력, 다른 사용자/조직 | 정의한 충돌 처리와 범위 격리, 다른 사용자의 결과 유출 없음 |
| 커밋 후 응답 유실 → 동일 작업 재시도 | 저장/외부 효과가 늘지 않고 원래 결과를 확인 가능 |
| 완료 기록·업무 쓰기·발행·ack 전후 중단 → 재시작/재전달 | 중복뿐 아니라 유실도 없음. 각 원자성 경계의 실제 전후 상태 확인 |
| 일부 단계 성공 후 나머지 실패, 복구 중 재실패 | 계약한 재개/보상/대사 상태, 중복 보상 없음, 무한 처리 중 상태 탐지 |
| 필요한 메시지 순서 역전·지연·보존 기간 경계 | 오래된 상태 덮어쓰기 방지, 재처리 규칙 준수, 합의한 수렴 조건 만족 |

기존 API·통합·worker 테스트로 검사하고 브라우저는 해당 UI 상태를 확인합니다. HTTP 200, 버튼
비활성화, 큐 수신 로그만으로 저장·외부 효과의 멱등성을 증명하지 않습니다. 고정 sleep만 기다리기보다
정해진 기한 안에서 실제 완료 조건을 관측합니다. 실패 주입·재시작을 못 했다면 정적 분석과 구분합니다.

기존 AC/QA 증거에 대상 버전·환경·테스트 ID/명령, 요청/업무/메시지 식별자(민감값 제외), 반복·동시성·
장애 지점, 전후 데이터·부수 효과, 복구/수렴 결과를 남깁니다. 한 번 처리돼야 할 업무 효과와 정상
감사 로그/시도 횟수 증가는 구분합니다. 위반 재현은 `FAIL`, 실행/관측 불가는 `NOT RUN`, 적용 근거가
없거나 계약 미정은 `UNVERIFIED`입니다. 테스트 대역의 결과를 실제 외부 서비스의 보장으로 확대하지 않습니다.

## 단계별 책임

젭마인은 계약과 AC/QA를 정하고, 포세이돈·다이달로스는 같은 계약으로 구현·통합합니다. 코드 리뷰는
변경 경계의 실패 틈을 찾고, 아르고스는 계약→코드→실행 증거를 대조합니다. 미노스·API 테스터는
각자 실행 가능한 범위의 실제 결과를 검증하며 클리오는 기존 필수 기준에 그 증거를 합산합니다.
아프로디테는 처리 중·결과 미확정·완료·실패/복구와 새로고침 후 상태 확인을 화면 계약에 반영합니다.
필요한 백엔드 계약을 연결하고, 프론트 조작 제어를 서버 멱등성 검증으로 대체하지 않습니다.
