# 아틀라스 — 부품 지도 전체 정리

`/atlas` 또는 “부품 지도 전체 정리해줘”로 요청한다. 범위를 줄이려면 `/atlas olympus.installer`처럼
부품 이름을, 또는 “설치기 쪽만”처럼 말로 준다. 하던 것을 이어서 할 때는 “이어서 해줘”라고 하면 된다.

TermSnap 코드맵은 위치와 관계를 계산으로 만든다. “어떤 파일들이 한 기능인가”와 “그 부품이 무엇을
책임지고 고칠 때 무엇을 함께 고쳐야 하는가”는 계산으로 나오지 않아 `codemap/component-map.json`에 써야 한다.
평소에는 그 부분을 고친 세션이 인계할 때 조금씩 쓴다(Mnemo 핸드오프). 아틀라스는 이미 있는 프로젝트에서
그 지도를 처음 한 번 채우거나, 구조를 크게 바꾼 뒤 다시 정리할 때 쓴다.

## 쓰는 때

| 상황 | 할 일 |
|---|---|
| 지도가 없거나 설명이 한 줄씩뿐인 기존 프로젝트 | 아틀라스 |
| 폴더를 크게 옮기거나 기능을 갈라 지도가 통째로 낡음 | 아틀라스 |
| 방금 고친 부품의 설명만 맞추면 됨 | Mnemo 핸드오프(`Component map:` 줄이 내민다) |
| `codemap/` 폴더가 없음 | 멈춘다. TermSnap 코드맵을 쓰는 프로젝트에서만 쓴다 |
| `codemap/`은 있는데 `codemap/components/`가 없음 | 멈춘다. TermSnap이 부품 지도를 내지 않는 버전이다 — 갱신을 안내한다 |

폴더 구조가 곧 기능 구조인 작은 프로젝트는 지도가 더할 것이 적다. 그렇게 보이면 멈추지 말고 2단계에서
뼈대를 보여 줄 때 그 점을 말한다. 계속할지는 사용자가 정한다.

## 누가 무엇을 하나

| 누가 | 하는 일 |
|---|---|
| TermSnap | 코드맵 계산, 지도 검증, 부품별 파일 목록(`codemap/components/owners.json`) |
| `scripts/atlas_work.py` | 읽을 묶음 나누기, 작업자 지시문 채우기, 근거 줄 대조, 장부 |
| 읽기 작업자(서브에이전트) | 묶음 하나를 읽고 자기 결과 파일 하나를 쓴다 |
| 메인 세션 | 뼈대, 범위 확인, 대조 결과 판단, 설명 압축, 지도 병합 |

지도 파일은 메인 세션만 쓴다. 그래서 작업자가 백그라운드로 도는 동안 메인은 다른 작업을 해도 된다.

## 명령을 부르는 법

`<module_root>`는 이 `SKILL.md`가 있는 폴더다. 스크립트 경로만 거기서 찾고, **실행은 대상 프로젝트
안에서** 한다. 스크립트는 현재 폴더에서 가장 가까운 Git 루트를 프로젝트로 본다. 다른 곳에서 부르거나
Git이 없으면 하위 명령 앞에 `--project-root <경로>`를 준다. Python은 `python --version`, `py --version`,
`python3 --version` 순으로 버전이 출력되는 첫 번째 것을 쓴다.

```bash
python "<module_root>/scripts/atlas_work.py" plan
python "<module_root>/scripts/atlas_work.py" --project-root "D:/work/app" plan
```

## 절차

이어서 하는 경우에는 아래 “중단과 재개”부터 읽는다.

### 1. 규칙을 읽는다

- `codemap/components/index.md` — 지도 작성 규칙과 예시의 정본이다. 여기 옮겨 적지 않는다.
- Mnemo의 `references/component-map.md` — 설명 쓰는 기준과 자주 막히는 곳. 프로젝트에
  `skills/mnemo/references/component-map.md`가 있으면 그것을, 없으면 현재 CLI의 활성 스킬 폴더에서 이름이
  `mnemo`로 끝나는 스킬의 것을 읽는다(어느 것이든 같은 문서다). 없으면 `NOT RUN — Mnemo 참조 문서 없음`을
  보고에 적고 위 정본만으로 진행한다.

그 문서의 “이번 세션이 다루지 않은 부품의 설명을 고치지 않는다”는 아틀라스에도 그대로다. 아틀라스가
읽고 설명을 쓰는 것은 깊게 읽은 부품뿐이고, 컨테이너는 자식 설명을 합칠 뿐이다(6단계).

### 2. 뼈대를 먼저 맞춘다

이 단계의 목적은 배정이다. 지도가 없으면 새로 쓰고, 있으면 오류를 고친다.

- **재료:** `codemap/index.md`의 카테고리, `codemap/files.md`의 파일 목록, `codemap/GRAPH_REPORT.md`의
  `Communities`. 이것만으로 어느 파일들이 한 기능인지 가려지지 않으면 설명서(README, 스킬·모듈 문서)와
  설치·빌드 스크립트의 파일 목록, 테스트 파일 이름까지 본다. 구현을 읽어 설명을 쓰는 것은 4단계의 일이다.
- **쓰는 것:** 시스템·컨테이너·부품과 범위. 여러 폴더에 걸친 기능부터 부품으로 잡는다. 설명은 비워 둔다.
  컨테이너에는 범위를 주지 않는 것이 기본이고, 넓은 폴더를 한 덩어리로 넘겨야 할 때만 준다(Mnemo 문서의
  “자주 막히는 곳”).
- **확인:** 새로 쓰거나 크게 고친 뼈대는 저장하기 전에 컨테이너·부품 이름과 범위를 사용자에게 한 번 보여
  준다. 지도를 처음 만드는 프로젝트라면 `codemap/`이 Git에서 빠져 있는지도 이때 알린다(빠져 있으면 지도도
  추적되지 않는다).

**다시 생성.** 지도를 저장해도 산출물은 TermSnap이 다시 만들어야 바뀐다. MCP `codemap_component_map`이
있으면 프로젝트 폴더 경로를 주어 호출한다(검증하고 산출물을 다시 쓴다). 없으면 사용자에게 TermSnap에서
이 프로젝트를 다시 열거나 코드맵을 다시 생성해 달라고 하고 기다린다. 다시 생성됐는지는 3단계의 `plan`으로
안다 — 멈추지 않으면 된 것이다.

**마치는 기준.** `plan` 첫 줄의 `지도 오류`가 0이다. 0이 아니면 `codemap/components/index.md`가 적은 오류를
읽고 지도를 고친 뒤 다시 생성한다. 미분류는 남아도 된다.

**다시 생성할 수 없으면 여기서 멈춘다.** `plan`이 낡은 산출물로는 묶음을 만들지 않는다. 저장한 뼈대와
`NOT RUN — TermSnap 다시 생성 못 함`을 보고하고 끝낸다. 다시 생성한 뒤에도 `plan`이 “지도가 아직 없다”나
“스텁이다”로 멈추면 TermSnap이 지도 JSON을 읽지 못한 것이다. 문법(쉼표, 따옴표)과 `format` 값을 정본의
예시와 맞춰 보고, 그래도 같으면 `NOT RUN — TermSnap이 지도를 읽지 못함`으로 멈춘다.

### 3. 읽을 범위를 정한다

```bash
python "<module_root>/scripts/atlas_work.py" plan
```

첫 줄에 부품 수·묶음 수·전체 미분류·지도 오류가, 그 아래에 부품별 크기·파일 수·묶음 수가 나온다. 맨
오른쪽이 부품 이름이다. “지도가 아직 없다”, “스텁이다”, “산출물이 지도보다 오래됨”으로 멈추면 2단계의
**다시 생성**부터 한다. 지도의 glob을 직접 풀어 파일 목록을 만들지 않는다.

전부를 같은 깊이로 읽지 않는다. 부품마다 셋 중 하나로 정한다.

| 등급 | 어떤 부품 | 처리 |
|---|---|---|
| 깊게 읽기 | 여러 폴더에 걸쳐 있거나, 설치·동기화·배포·테스트처럼 다른 부품과 맞물려 있다 | 작업자가 읽는다 |
| 그대로 두기 | 폴더 하나가 기능 하나이고 그 폴더에 자기 설명서가 있다 | 지도의 지금 설명을 손대지 않는다. 비어 있으면 비워 둔다 |
| 건너뛰기 | 조사·보관 문서, 타사 번들, 생성물 | 읽지 않는다 |

어느 쪽인지 애매한 부품은 “미정”으로 표시해 함께 보여 준다. 등급별 부품과 깊게 읽을 묶음 수를 사용자에게
한 번 보여 주고 확인받는다. 질문을 할 수 없는 실행(제우스 등)에서는 여러 최상위 폴더에 걸친 부품만 깊게
읽고, 그렇게 정했다는 것을 보고에 적는다.

확인받은 범위를 한 번에 장부에 적는다. 장부에는 깊게 읽을 부품의 묶음만 남는다.

```bash
python "<module_root>/scripts/atlas_work.py" plan --only olympus.installer olympus.mnemo --skip olympus.docs.research --no-open docs/research/ vendor/
```

- `--only`는 깊게 읽을 부품, `--skip`은 건너뛸 부품이다. 이름은 공백으로 나열하고, 이름 하나가 그 부품과
  그 아래 부품을 함께 고른다. 부모를 `--only`로 고르고 그 아래 하나를 `--skip`으로 빼도 된다.
- `--no-open`은 작업자가 열지 않을 경로다. 건너뛸 부품의 폴더(지도에서 그 부품의 범위를 본다)와 프로젝트가
  열지 말라고 정한 폴더나 파일을 준다. 계획기는 기본 금지 경로와 지정한 경로 아래 파일을 묶음과 지문 계산에서
  제외한다. `check`에서도 이 경로의 파일은 근거로 사용할 수 없다.
- `--only`에도 `--skip`에도 없는 부품이 “그대로 두기”다.
- 이 범위는 장부에 남는다. 다음에 `plan`을 인자 없이 부르면 같은 범위를 쓴다. 처음부터 다시 정하려면
  `plan --all`을 쓴다.

범위를 적은 뒤, 깊게 읽을 기능의 파일이 미분류에 남아 있지 않은지 `codemap/components/index.md`에서 본다.
남아 있으면 2단계로 돌아가 배정하고 다시 생성한다. 미분류 파일은 아무도 읽지 않는다.

### 4. 작업자에게 읽힌다

묶음 하나에 작업자 하나를 붙인다. 묶음 이름은 `status`가 보여 준다(예: `olympus.installer.mcp#1`).

```bash
python "<module_root>/scripts/atlas_work.py" status
python "<module_root>/scripts/atlas_work.py" brief "olympus.installer.mcp#1"
```

`brief`가 출력한 글 전체를 작업자에게 그대로 준다. 틀과 이유는
[읽기 작업자에게 주는 지시](references/reader-brief.md)에 있다.

- **작업자 유형:** 자기 결과 파일을 써야 하므로 파일을 쓸 수 있는 작업자를 쓴다 — Claude
  `general-purpose`, Codex `worker`, Antigravity `generalist`, Grok `general-purpose`.
- **모델:** 따로 정하지 않고 현재 CLI가 작업자에게 쓰는 모델로 돌린다. 사용자가 비용을 줄여 달라고 하면
  더 낮은 등급을 지정해도 된다.
- **동시 실행:** 한 번에 3개까지. 작업자도 같은 사용 한도를 쓴다.
- **백그라운드:** 작업자가 도는 동안 메인은 다른 일을 해도 된다. 결과 본문은 대화로 받지 않는다 —
  파일에 쓰고 한 줄만 돌려받는다.
- **위임할 수 없는 CLI:** 메인이 같은 지시로 묶음을 차례로 읽고 같은 모양의 결과 파일을 쓴다.

### 5. 근거를 대조한다

```bash
python "<module_root>/scripts/atlas_work.py" check
python "<module_root>/scripts/atlas_work.py" check "olympus.installer.mcp#1"
```

이름 없이 부르면 결과 파일이 있고 아직 통과하지 않은 묶음을 모두 대조한다. 묶음마다 첫 줄이 `[OK]` 또는
`[확인 필요]`다. 함께 고칠 것과 결함 후보의 근거를 모두 대조한다.
`brief`와 `check`는 실행 시점의 묶음 파일로 지문을 다시 계산한다. 결함 후보마다 확인 가능한
`파일:줄` 또는 `파일:시작-끝`이 하나 이상 있어야 한다.

| 출력 | 뜻 | 할 일 |
|---|---|---|
| `!! 파일 없음`, `!! 줄 범위 밖`, `!! 프로젝트 밖 경로` | 인용한 자리가 없다. 줄 범위 밖은 줄 번호가 그 파일의 줄 수를 넘은 것이다 | 그 주장을 버리거나, 메인이 직접 열어 맞는 줄을 확인한 뒤에만 쓴다 |
| `!! 결과의 digest가 … 다르다` | 파일이 바뀌기 전에 읽은 옛 결과다 | 다시 맡긴다. 이 결과는 쓰지 않는다 |
| `묶음 파일이 계획 이후 바뀌었다`, `묶음 파일을 읽을 수 없다` | 현재 파일로 계획 시점의 지문을 확인할 수 없다 | 파일 상태를 확인하고 `plan`을 실행한 뒤 새 `brief`로 다시 맡긴다 |
| `열람 금지 경로` | 지시문에 금지 파일이 배정됐거나 결과가 그 경로를 인용했다 | 배정이 겹치면 금지 경로 전체를 `plan --no-open`에 주어 다시 나눈다. 금지 경로를 인용한 주장은 제외한다 |
| `!!`로 시작하는 다른 줄 | 형식 문제 — 책임 문장 없음, 근거 없는 주장, 확신 표시 오류, JSON 아님 | 다시 맡긴다 |
| `[확인 필요]` | 위 문제가 하나 이상 있다 | 해당 행의 조치를 따른다 |
| `주의:` | 건수 초과, 근거가 한 곳뿐인 `verified`, 읽었는지 밝히지 않은 파일 | `[OK]`를 막지 않는다. 건수가 많으면 6단계에서 메인이 고른다 |

- 주장 문장이 아니라 **인용한 줄이 그 내용을 말하는지**를 본다.
- `verified`라도 묶음마다 한두 건은 직접 열어 본다. 열어 본 줄이 주장을 말하지 않으면 그 주장 하나만 버리고
  넘어가지 않는다 — 그 묶음의 나머지 주장을 모두 직접 열어 보거나 묶음을 다시 맡긴다.
- 다시 맡길 때는 같은 `brief`를 다시 주어 같은 결과 파일을 덮어쓰게 하고, 그 묶음만 이름을 주어 `check`한다.
  상태는 `check`가 다시 적는다.

### 6. 지도에 병합한다

한 부품의 묶음이 모두 대조된 뒤에 그 부품을 병합한다. 묶음 결과를 모아 부품의 `description`에 쓴다.
쓰는 기준은 Mnemo의 `component-map.md`를 따른다.

- **쓰는 자리:** 부품의 `description` 한 곳이다. 책임 한 문장 뒤에 “함께 고칠 것: …”을 이어 쓴다. 다른
  부품을 가리키는 결합도 여기에 쓴다. `relationships`는 더하거나 고치지 않는다.
- **분량:** 책임 한 문장과, 놓치면 실제로 깨지는 함께 고칠 것 서너 건. 함수 이름·줄 번호·개수는 넣지 않는다.
- **책임 문장:** 근거 줄이 없으므로, 그 묶음의 주장과 읽은 범위에 어긋나지 않는지 보고 쓴다. 묶음이 여럿이면
  묶음별 문장을 합쳐 부품 전체의 한 문장으로 만든다.
- **기존 설명:** 누가 썼는지는 지도에 남지 않는다. 책임 한 문장보다 길게 적힌 설명은 누군가 그 부품을
  고치며 쓴 것으로 보고 지우지 않는다. 이때는 분량 기준보다 보존이 먼저다 — 새로 확인한 것만 더한다.
  기존 문장과 작업자 결과가 어긋나면 작업자 문장으로 덮어쓰지 않는다. 메인이 그 파일을 직접 읽어 판정하고,
  판정하지 못하면 기존 문장을 두고 보고에 적는다.
- **어울리지 않는 파일:** 직접 확인한 뒤 배정을 옮긴다. glob에는 제외가 없으므로 원래 부품의 범위를
  나열로 풀어 쓰거나 그 파일을 중첩 부품으로 둔다(Mnemo 문서의 “자주 막히는 곳”).
- **컨테이너 설명:** 자식 부품이 모두 설명을 갖고 있을 때만(이번에 쓴 것이든 이미 있던 것이든) 자식 설명에서
  합친다. 코드를 다시 읽지 않는다. 자식 일부만 설명이 있으면 컨테이너는 지금대로 둔다.

저장한 뒤 2단계의 **다시 생성**으로 `지도 오류` 0을 확인하고, 반영을 마친 묶음을 하나씩 적는다. 주장을 모두
버린 묶음도 반영이 끝났으면 적는다.

```bash
python "<module_root>/scripts/atlas_work.py" mark "olympus.installer.mcp#1" merged
```

`mark … merged`도 완료를 기록하기 직전에 묶음 지문을 확인한다. 그사이 파일이 바뀌면
`plan`부터 재개하고, 바뀐 파일에 해당하는 설명을 다시 대조한다.
여기서 다시 생성하지 못하면 지도는 저장된 채로 두고 `검증 NOT RUN — TermSnap 다시 생성 못 함`을 보고한다.
배정을 옮긴 뒤 `plan`을 바로 다시 돌릴 필요는 없다.

### 7. 보고한다

- 깊게 읽은 부품, 그대로 둔 부품, 건너뛴 부품(`plan`이 보여 주는 `범위:` 줄이 깊게 읽기와 건너뛰기다)
- 대조 결과: 주장 수, `check`가 센 틀린 근거 수, 그중 직접 확인해 살린 수, 다시 맡긴 묶음
- 옮긴 배정, 기존 설명과 어긋나 그대로 둔 곳
- 하지 못한 것은 `NOT RUN — <이유>`로
- 결함 후보: `check`가 `결함 후보:`로 보여 준 것을 근거 줄과 함께 따로 적는다. 아틀라스는 고치지 않는다.

## 중단과 재개

장부는 `codemap/atlas/ledger.json`, 결과는 `codemap/atlas/results/`에 있다. 세션이 끊겨도 남는다.
이어서 할 때는 이 순서로 한다.

1. `plan`을 **인자 없이** 부른다. 지난 범위와 상한을 그대로 쓰고(`범위:` 줄에 “지난 범위를 그대로 씀”),
   그사이 달라진 묶음을 가려낸다.
   - “파일이 바뀌어 다시 읽을 묶음” — 그 묶음의 파일 구성이나 내용이 바뀌었다. 다시 읽힌다.
   - “근거로 인용한 파일이 바뀌어 다시 대조할 묶음” — 묶음 밖의 인용 파일이 바뀌었다. 5단계에서 인용 줄을
     다시 본다.
2. `status`로 묶음별 상태를 본다.

   이전 검사기로 통과한 미병합 결과는 `read`로 돌아가 새 검사로 대조한다. 이미 병합한 결과는 기록을 유지한다.

   | 상태 | 뜻 | 다음 |
   |---|---|---|
   | `pending` | 결과가 없거나 다시 읽어야 한다 | 4단계 — `brief`를 주어 맡긴다 |
   | `read` | 결과는 있고 다시 대조해야 한다 | 5단계 — `check` |
   | `needs-review` | 대조에서 `[확인 필요]`였다 | 5단계의 표대로 |
   | `checked` | 대조를 통과했고 아직 지도에 넣지 않았다 | 6단계 |
   | `merged` | 지도에 넣었다 | 끝 |

3. `check`를 인자 없이 부른다. 끊기기 전에 작업자가 써 둔 결과가 대조된다. 다시 읽을 묶음에 옛 결과 파일이
   남아 있으면 `digest`가 달라 `[확인 필요]`로 나온다 — 그 결과는 쓰지 않고 다시 맡긴다.
4. `pending`인 묶음을 4단계부터, 나머지를 위 표대로 이어 간다.

다음 실행은 바뀐 묶음만 읽는다. 이미 `merged`인 묶음은 인용 파일이 바뀌어도 되돌리지 않는다 — 그 뒤의
변화는 평소 유지(Mnemo 핸드오프)의 몫이다. `codemap/`이 Git에서 빠진 프로젝트에서는 장부도 추적되지
않는다 — 폴더를 지우거나 다른 컴퓨터로 옮기면 지도와 함께 사라진다.

## 하지 않는 것

- `check`를 돌리지 않은 결과 파일의 내용을 지도에 넣지 않는다. `[확인 필요]` 묶음은 `!!`가 붙은 주장을
  버리거나 직접 확인한 뒤에 나머지를 쓴다.
- 작업자에게 지도·기억·핸드오프를 열거나 쓰게 하지 않는다. 이미 쓰인 설명을 옮겨 적게 된다.
- 코드에 적혀 있지 않은 운영 지식을 지어내지 않는다. 그것은 고친 세션이 인계할 때 쓴다.
- 읽지 않은 부품의 설명을 짐작으로 채우지 않는다.
- TermSnap의 검증 규칙을 다시 구현하지 않는다. 산출물이 낡았으면 다시 생성한다.
- Git 추적 여부를 혼자 정하지 않는다.

## Python이 없을 때

`owners.json`을 직접 읽어 깊게 읽을 부품의 파일을 묶고, 지시 틀은 `references/reader-brief.md`의 안내대로
직접 채운다. 작업자 결과의 근거는 메인이 인용 줄을 직접 열어 확인한다. 장부는 쓰지 못하므로
`NOT RUN — Python 없음(장부·자동 대조 생략)`을 보고에 적는다.

숫자는 예시다.

```text
/atlas

→ check: 주장 61, 틀린 근거 2 → 하나는 직접 열어 살리고 하나는 버림

/atlas 이어서 해줘
→ plan(인자 없이): 지난 범위 그대로, 파일이 바뀐 묶음 1개가 다시 읽을 것으로
→ status → check → 남은 묶음 brief
```
