# 읽기 작업자에게 주는 지시

묶음 하나에 작업자 하나를 붙인다. 지시문은 손으로 채우지 않고 스크립트로 뽑아 그대로 준다.

```bash
python "<module_root>/scripts/atlas_work.py" brief "<묶음 이름>"
```

`<묶음 이름>`은 `status`가 보여 주는 이름이다(예: `app.core#1`). 출력된 글 전체가 작업자에게 줄 지시다.
메인 세션의 대화나 "이 부품은 아마 ~일 것"이라는 가설을 덧붙이지 않는다 — 가설을 주면 그 가설이
확인돼서 돌아온다.

작업자가 열지 않을 곳은 3단계의 `plan --no-open <경로…>`로 정해 장부에 남긴다. 건너뛰기로 정한 폴더와
프로젝트가 열지 말라고 정한 폴더(비밀, 대용량 데이터)를 준다. 폴더든 파일이든 저장소 루트 기준 경로다.
작업자는 목록 밖 파일도 검색해서 읽을 수 있으므로, 주지 않으면 그 안으로 들어간다. 한 묶음에만 더할 것이
있으면 `brief "<묶음 이름>" --no-open <경로…>`로 덧붙인다.

스크립트는 아래 틀의 `<<…>>` 자리를 장부 값으로 채운다. 틀은 여기 한 곳에만 있다.

| 자리 | 채워지는 값 |
|---|---|
| `<<ROOT>>` | 프로젝트 루트 절대경로 |
| `<<RESULT>>` | 그 묶음의 결과 파일 절대경로 |
| `<<COMPONENT>>`, `<<BATCH>>` | 부품 이름과 묶음 이름 |
| `<<DIGEST>>` | 그 묶음 파일들의 지금 내용 지문. 결과에 그대로 돌아와야 `check`가 받는다 — 파일이 바뀌기 전에 읽은 옛 결과를 가려낸다 |
| `<<FILES>>` | 그 묶음의 파일 전부. 메인이 고르거나 줄이지 않는다 |
| `<<NOTES>>` | 부품이 여러 묶음으로 나뉘었을 때, 상한보다 큰 파일이 있을 때 붙는 한 줄 |
| `<<NO_OPEN>>` | 장부에 남긴 열지 않을 곳과 `brief --no-open`으로 덧붙인 경로 |

## 지시 틀

```text
저장소 `<<ROOT>>`의 부품 하나(같은 기능을 이루는 파일 묶음)를 읽고, 결과를 파일 하나로 써 주세요.
쓰는 파일은 `<<RESULT>>` 하나뿐입니다. 다른 파일은 만들거나 고치지 마세요.

## 부품
- 이름: `<<COMPONENT>>` (묶음 `<<BATCH>>`)
- 읽을 파일(저장소 루트 기준):
<<FILES>>
<<NOTES>>

## 할 일
1. 위 파일을 각각 끝까지 읽습니다. 발췌만 보고 판단하지 않습니다. 다 읽지 못한 파일은 읽은 범위를 밝힙니다.
2. 이 부품이 무엇을 책임지는지 한 문장으로 씁니다. 폴더·파일 이름을 풀어 쓴 문장은 안 됩니다.
   함수 이름·줄 번호·개수 같은 구현 세부도 넣지 않습니다.
3. 이 부품을 고칠 때 함께 고쳐야 하는 것을 찾습니다. 같은 목록이나 규칙이 두 곳에 따로 있다, 테스트가 값을
   고정해 두었다, 한쪽이 쓰는 문구를 다른 쪽이 읽어 판정한다, 파일 목록이 따로 있어 거기에도 넣어야
   배포된다 같은 것입니다. 확인에 필요하면 위 목록 밖의 파일(테스트, 설치·빌드 스크립트, 이 부품을 불러 쓰는
   코드)을 검색해서 필요한 만큼 읽습니다.
4. 위 목록에 있지만 이 부품에 어울리지 않는 파일이 있으면 적습니다.
5. 읽다가 결함으로 보이는 것(두 구현이 같은 입력을 다르게 판정한다, 테스트가 한쪽만 본다, 문서와 코드가
   다르게 말한다)을 만나면 고치지 말고 따로 적습니다. 찾으러 다니지는 않습니다.

## 지킬 것
- 확인한 것만 씁니다. 직접 연 파일에서 근거를 본 것만 주장합니다. 함께 고칠 것이 확인되지 않으면 빈 목록이
  올바른 답입니다. "문서도 갱신해야 한다" 같은 일반론을 넣지 않습니다.
- 함께 고칠 것은 놓치면 실제로 깨지는 순서로 최대 5건만 씁니다.
- 주장마다 근거를 `경로:줄` 또는 `경로:시작-끝`으로 답니다. 경로는 저장소 루트 기준이고, 실제로 연 파일의
  실제 줄이어야 합니다. 위 목록 밖의 파일이어도 됩니다.
- 양쪽 위치를 모두 직접 읽었으면 `verified`, 한쪽을 검색 결과로만 봤거나 짐작이면 `inferred`입니다.
- 다음은 열지 않습니다: `codemap/component-map.json`, `codemap/components/`, `codemap/atlas/`의 다른 결과,
  `memory/`, `MEMORY.md`, `docs/handoffs/`, `conversations/`<<NO_OPEN>>.

## 결과 파일
`<<RESULT>>`에 아래 모양의 JSON 하나만 씁니다. 따옴표 안의 한글은 그 자리에 쓸 내용의 설명입니다.
`component`·`batch`·`digest`는 적힌 값을 그대로 옮깁니다. 해당하는 것이 없는 목록은 `[]`로 둡니다.
대화로는 "썼다"는 한 줄만 돌려줍니다.

{
  "component": "<<COMPONENT>>",
  "batch": "<<BATCH>>",
  "digest": "<<DIGEST>>",
  "responsibility": "이 부품이 책임지는 것 한 문장",
  "co_changes": [
    {"claim": "무엇을 고치면 무엇을 함께 고쳐야 하는가", "evidence": ["경로:줄", "경로:줄"], "confidence": "verified 또는 inferred"}
  ],
  "misfit_files": [
    {"path": "어울리지 않는 파일 경로", "why": "이유"}
  ],
  "defect_candidates": [
    {"note": "결함으로 보이는 것", "evidence": ["경로:줄"]}
  ],
  "files_read_fully": ["끝까지 읽은 파일 경로"],
  "files_read_partly": ["경로 (읽은 범위)"],
  "files_not_opened": ["경로 (이유)"],
  "unknowns": ["확인하지 못해 비워 둔 것"]
}
```

## 왜 이렇게 묻는가

- **근거 줄을 요구하는 이유:** 주장 문장은 그럴듯하게 쓸 수 있지만 줄 번호는 스크립트로 대조된다.
  `check`가 인용한 줄을 꺼내 주장 옆에 보여 준다.
- **열지 말 곳을 두는 이유:** 지도와 기억에는 이미 누군가 쓴 설명이 있다. 그것을 옮겨 적으면 읽지 않고도
  답이 채워진다.
- **최대 5건인 이유:** 건수를 묶지 않으면 문서가 값을 복제한다는 식의 자잘한 결합까지 10건 넘게 돌아온다.
  지도 설명에는 부품당 서너 건이 들어가고, 그 마지막 고르기는 여러 묶음을 합쳐 보는 메인이 한다.
- **읽은 범위를 묻는 이유:** 끝까지 읽은 파일과 검색으로만 본 파일을 구분해야 주장의 무게를 잴 수 있다.
- **결함 후보를 따로 받는 이유:** 읽다 보면 두 구현이 어긋난 곳이 보인다. 지도에 넣을 내용은 아니지만
  버리면 다시 찾아야 한다. 아틀라스는 이것을 고치지 않고 보고에만 싣는다.

## Python이 없을 때

위 틀을 직접 채운다. `<<ROOT>>`는 프로젝트 루트, `<<RESULT>>`는 그 묶음만의 파일 경로 하나
(`codemap/atlas/results/<부품>-<번호>.json`), `<<FILES>>`는 한 줄에 하나씩 `  - \`경로\`` 모양,
`<<NOTES>>`와 `<<NO_OPEN>>`은 해당할 때만 채우고 아니면 지운다. `<<DIGEST>>`는 계산할 수 없으므로 그 줄을
지우고, 읽힌 뒤 파일이 바뀌지 않았는지는 메인이 직접 확인한다.
