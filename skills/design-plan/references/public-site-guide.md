# 공개 사이트 — 사업·카피·화면·출시 인계

공개 사업·서비스·브랜드 사이트나 방문자의 문의·예약·구매 등 전환을 설계하는 경우에만 읽습니다.
기존 Experience Contract·Layout Blueprint·DESIGN.md를 보강하며 새 단계나 별도 장부를 만들지 않습니다.
관리 화면·인증 후 업무 UI·국소 스타일 수정에는 해당 페이지의 실제 과업만 적용합니다.

## 1. 브리프와 청사진

기존 요구·PRODUCT.md·spec·사용자 자료에서 사업/제공 서비스, 대상 방문자와 방문 상황, 원하는
행동, 가격·이용 조건, 망설이는 이유, 신뢰 근거를 확보합니다. 이미 있는 답은 다시 묻지 않습니다.
빠진 사실과 설계자가 정할 구조를 구분하고, 중요한 미정 결정은 기존 Open Decisions로 관리합니다.

지정한 경쟁사·레퍼런스는 기존 benchmark 절차로 분석합니다. 개수를 채우려고 사이트를 추가하거나
보지 않은 사이트를 분석했다고 쓰지 않습니다. 결과를 사이트맵, 페이지별 임무·섹션 순서·헤드라인,
DESIGN.md의 색·서체와 연결합니다. 시각 취향이 사업 사실이나 고객 요구의 증거를 대신하지 않습니다.

사이트의 주요 전환 목표를 일관되게 유지하되 페이지별 과업과 단계에 맞는 주 CTA를 정합니다.
모든 페이지에 같은 문구·버튼 하나를 강제하지 않습니다. 각 CTA에 문구·목적지·반복 위치와
누른 뒤의 실제 결과를 정의합니다. 문의 폼·예약·결제는 UI 성공 표시와 접수/저장/외부 처리의
완료 조건을 구분해 구현 담당에게 넘깁니다.

## 2. 카피와 브랜드 신뢰

`Product Facts`·`Content Integrity`·`Asset Provenance`가 사실·문구·자산 상태의 정본입니다.
오퍼·가격·조건·실적·후기·배경·브랜드 탄생 계기·가치의 근거와 공개 가능한 범위를 연결합니다.
없는 실적·고객 수·후기·수상·창업 이야기는 만들지 않습니다. 가설과 샘플은 기존 분류로 표시하고,
공개 화면에서는 교체하거나 제외합니다. 사실이 없을 때는 작업 방식·서비스 범위 등 확인한 정보로
신뢰를 설명합니다. 소개 페이지도 해당 사이트에서 필요한 경우에만 설계합니다.

페이지 목적에 맞춰 히어로의 핵심 약속·보충 설명, 실제 혜택, 증거, 방문자의 질문에 답하는 FAQ,
마무리 행동을 구성합니다. 혜택·증거를 세 개씩 채우거나 모든 페이지에 같은 블록을 넣지 않습니다.
소개 페이지는 필요한 배경·시작 계기·잘 도울 수 있는 고객·검증된 근거와 다음 행동을 짧게 연결합니다.
사진 캡션과 접근성 설명도 실제 자산의 내용·출처를 따릅니다.

정보는 방문자가 판단하는 순서로 배치하고 기존 텍스트 예산·덜어내기·첫 뷰포트 규칙을 지킵니다.
기획서의 분석 문장을 그대로 화면에 싣지 않습니다. 가격·조건·중요한 제한은 판단에 필요한 위치에
두고, 과장된 보장이나 측정하지 않은 전환율을 성과로 쓰지 않습니다.

## 3. 화면 구현과 아트 디렉션

아프로디테는 경험·카피·디자인 계약과 화면 코드·시각 검수에 책임을 집니다. 라우팅·인증·데이터·
API·업무 상태와의 연결은 앱 구현 파이프라인이 소유합니다. 포세이돈·다이달로스가 조율 중이면
같은 프론트 작업자에게 두 계약과 파일 소유권을 함께 전달하고 중첩 팀이나 별도 화면 사본을 만들지 않습니다.
시각 변경은 아프로디테의 렌더 비평으로 확인하고 기능 연결 후에도 그 계약을 보존합니다.

기존 스택·컴포넌트를 사용합니다. 단일 HTML은 요청한 산출물이나 적합한 프로토타입일 때만
선택합니다. 고정 내비게이션·hover·스크롤 모션은 과업과 디자인 방향에 필요할 때 적용하고,
모바일·키보드·reduced-motion에서도 동등한 행동과 정보를 제공합니다.

실제 렌더에서 여백, 글자 크기 비례·줄바꿈, 버튼 대비, 이미지 그리드, 섹션 리듬과 팔레트 일관성을
기존 비평 기준으로 확인합니다. 카피·조건·증거를 보존한 채 시각 문제를 고치며, 기능형 UI를
일률적으로 큰 여백·고급 서체·장식적 랜딩으로 바꾸지 않습니다.

## 4. 검색과 개인정보 입력

검색 유입이 범위에 있으면 페이지별 검색 의도·서비스/지역(해당 시), title·description·헤딩·
이미지 대체 텍스트와 공개/비공개 의도를 정합니다. 키워드·콘텐츠 주제는 실제 검색 자료와
작성자의 가설을 구분합니다. 자료가 없으면 후보로 남기고 검색 수요·순위 상승을 입증했다고
쓰지 않습니다. 블로그 주제는 요청·범위에 있을 때 필요한 만큼 제안합니다.

구현 후 `seo-audit`는 소스와 페이지별 의도의 정합성을, 미노스는 요청된 실제 렌더·링크 동작을
확인합니다. 정적 메타태그 점검을 실제 검색 노출이나 운영 URL 검증으로 바꾸어 보고하지 않습니다.

개인정보 입력·분석 도구·외부 전송이 있으면 확인한 코드와 운영자 사실을 테미스에 연결합니다.
테미스의 감사·방침 초안·미확인 항목을 받아 필요한 방침 링크와 확정된 동의/설정 UI 요구를
구현합니다. 방침 페이지의 존재를 실제 처리와의 정합성이나 법률 검토 완료로 간주하지 않습니다.
확인되지 않은 동의 의무·보유기간·처리업체를 디자인 단계에서 만들어내지 않습니다.

## 5. 기존 계약에 남길 인계

Experience Contract에 조건부 `## Public Site Delivery` 절을 둡니다. 사실·카피는 기존 정본을
링크하고, 다음 표에는 전달할 결정과 확인할 결과만 적습니다. 비해당 사이트에는 절을 추가하지 않습니다.

| 입력 | 남길 내용 |
|---|---|
| 페이지·행동 | 페이지 임무, 핵심 방문자, 주요 전환, CTA 목적지와 실제 완료/실패 조건 |
| 콘텐츠 | 오퍼·가격·혜택·FAQ·소개·증거의 정본 위치, 미확인/제외 내용과 보존 조건 |
| 검색·개인정보 | 페이지별 의도, 전문 감사 입력/결과 위치, 필요한 UI·기능과 미확인 사항 |
| 구현 소유권 | 화면 구현 담당, 기능 연결 담당, 수정 파일·경계와 관련 섹션/AC·QA ID |
| 출시 점검 | 요청된 출시 범위·대상 URL/환경, 필수 항목과 그 요구 출처·담당·검증 방법 |

새 AC·QA를 중복 정의하지 않습니다. 기존 섹션·체크리스트가 있으면 그 ID를 연결하고,
디자인만 요청됐으면 구현·출시 검증은 후속 작업으로 명시합니다. Prompt Contract의 FLOW·CTA·
FACTS·CONTENT_INTEGRITY·PRESERVE·SUCCESS에 해당 결정과 정확한 원본 경로를 반영합니다.

## 6. 점검 결과와 출시 인계

관련 실행 증거에는 대상 버전·URL/환경·확인 시각·수행한 검사·관측 결과·미실행 범위를 남깁니다.
같은 버전·조건의 유효한 증거는 재사용하고 변경·실패·미해결 의심이 있을 때 해당 범위를 다시 봅니다.

| 책임 | 확인·전달할 결과 |
|---|---|
| 젭마인 | 필요한 페이지·행동·기능과 공개 조건을 spec·섹션 AC·QA에 연결 |
| 아프로디테 | 청사진·사실 기반 카피·화면 구현·실제 렌더·경험 검증과 보존 조건 |
| 포세이돈/다이달로스 | 계약을 소비한 구현·기능 연결·통합 증거와 담당 파일 |
| 아르고스 | 설계·콘텐츠·UI 행동과 실제 구현의 일치, 미구현·미검증 구분 |
| 미노스 | 실제 CTA·폼·정상/실패·모바일·링크 동작, 접수/저장·부수 효과의 검증 범위 |
| SEO/테미스 | 전문 감사의 근거·대상·미확인 사항. 점수나 초안을 출시 승인으로 승격하지 않음 |
| 출시 점검/클리오 | 적용 가능한 검사 결과·필수 누락·후속 담당을 모아 요청된 범위의 준비 상태 판정 |

출시 점검은 페이지·폼·링크·성능·모바일, 요청된 운영 도메인·HTTPS·호스팅 설정, 필요한 방침과
전문 검토 상태를 확인합니다. preview에서 성공한 결과를 운영 환경의 성공으로 기록하지 않습니다.
첫 홍보·공유 항목은 요청됐을 때 대상·채널·자료·담당·시점을 포함한 계획으로 남깁니다.
자동 게시·메일 발송·배포·DNS 변경은 이 체크리스트의 실행 효과가 아니며 현재 요청의 권한을 따릅니다.
