# 실행 중 실행 방식 비교

포세이돈·다이달로스의 Lead/PM이 현재 작업의 재시도 분기에서 읽는 공통 계약이다.
현재 선택한 실행 엔진을 유지한다. 네이티브·메인 순차 경로는 그대로 사용하고, 이미 MCP를
선택했다면 같은 MCP 태스크·파일 락·외부 장부 경로에서 실행하며 Lead/PM이 비교를 판정한다.
이 문서를 읽는 것으로 MCP를 선택하거나 기존 락·소유권 경계를 우회하지 않는다.
변경 대상은 현재 태스크에 전달할 문맥·지시·작업 분할·도구 순서다. 설치된 스킬, 전역 설정,
모델·권한을 자동 변경하지 않는다. 실행자는 현재 에이전트이며 므네모는 경험과 근거를 제공한다.

## 진입 판단

실패 명령·출력·실제 변경을 먼저 확인한다. 횟수만으로 아키텍처 문제라고 판정하지 않는다.

| 관찰된 원인 | 다음 행동 |
|---|---|
| 구현 결함 또는 승인된 계약과 다른 테스트 | 해당 결함을 직접 수정하고 기존 검증을 실행. 실행 방식 비교는 생략 |
| 도구·서비스·입력 데이터 등 환경 문제 | 환경을 복구하거나 차단 조건을 기록. 환경 복구를 하네스 개선으로 채택하지 않음 |
| 필요한 문맥 누락, 잘못된 작업 분할·도구 순서 | 실행 기록에서 근거를 짚고 변경 가설 하나로 아래 비교 진행 |
| 원인 불명 또는 요구사항 모순 | 작은 재현·근거 확인부터 수행. 해소 전에는 실행 방식의 우열을 주장하지 않음 |

이미 해결된 단순 오류나 정상 작업에는 이 비교를 추가하지 않는다. 반복 실패가 없어도 실행 기록이
방식의 문제를 보여주면 비교할 수 있다. 관련 경험이 있으면 적용 조건을 현재 소스·입력과 대조해
가설에 사용한다. 과거 교훈을 현재 작업의 성공 증거로 대신 쓰거나 전체 기억을 주입하지 않는다.

## 비교 준비와 상한

1. Lead가 **가설 하나와 변경 하나**를 정한다. 예: 계약 파일을 읽지 않아 응답 형식을 추측했다면
   그 파일과 확인 순서를 태스크 입력에 포함한다. 작업자 교체나 동시성 축소도 근거가 있는 후보다.
2. 기존 activity log에 태스크/AC ID, 실패 근거, 원래 실행 지시와 변경안, 비교할 결과를 남긴다.
   승인된 요구사항·AC·테스트 기대값·트립와이어는 비교 도중 완화하지 않는다.
3. 비교 단위는 실패를 재현하는 최소 태스크로 제한한다. 기존 재시도·시간·토큰 상한 중 더 작은
   상한을 따르고 **가설당 후보 한 개**를 우선 실행한다. 기준점 재실행과 후보 실행도 같은 예산에
   포함한다. 작업자 교체·태스크 재분할로 이미 사용한 횟수를 초기화하지 않는다. 상한이 없으면
   같은 실패에 대한 추가 실행은 최대 2회이며, 필수 최종 검증을 위한 여유를 남긴다.
4. 기준점과 후보의 시작 코드·입력 파일/데이터·의존성·환경·모델/설정·도구·실행 한도를 확인한다.
   상태는 해시나 재현 가능한 참조로 기록한다. 소유권 검사에 쓰는 Git SHA만으로 실행 조건이
   같다고 판단하지 않는다. 기존 untracked 입력과 외부 상태도 비교에 영향을 주면 포함한다.
5. 이미 실행한 기준점은 위 조건과 실제 결과가 일치할 때만 재사용한다. 후보를 이전 시도의 수정이
   누적된 코드에서 실행하면 동일 시작점 비교가 아니다. 비교가 필요하면 허용된 격리 사본에서
   같은 시작 상태를 사용한다. 사용자 작업 트리를 reset/stash하거나 외부 부수 효과를 반복하지 않는다.
6. 동일 조건을 만들 수 없거나 예산이 부족하면 비교를 강행하지 않는다. 허용된 일반 복구는 계속할 수
   있지만 결과는 `unverified` 또는 `not-run`이다. 기존 트립와이어의 진행·중단 결정은 그대로 적용한다.

## 실행과 선택

기준점과 후보 모두 실제 과제를 수행한 산출물·명령 결과를 확인한다. 문서 리뷰, 절차 준수 점수,
과거 출력 열람만으로 후보 실행을 대신하지 않는다. 실행 후 같은 AC·검증 명령으로 결과와 회귀를
판정하고 시간·토큰 등 관측 가능한 비용을 함께 기록한다. 미측정 비용은 `unknown`으로 둔다.

Lead가 다음 두 상태를 **따로** 기록한다.

- `task`: `recovered | unresolved` — 실제 과제의 검증 결과. 전체 작업 완료는 기존 통합 게이트가 판단.
- `adjustment`:
  - `accepted`: 비교 조건이 같고 후보가 기준점보다 개선되며 필수 검사에 회귀가 없다. 동점이면
    명시한 비용 지표가 개선됐을 때만 채택한다. 비용 증가가 있으면 사전에 정한 상한 안인지 확인한다.
  - `rejected`: 후보의 회귀, 유효한 개선 없음, 또는 정한 비용 상한 초과.
  - `unverified`: 과제는 실행했으나 시작 상태·환경 등이 달라 효과를 분리할 수 없거나 관측 차이가 불확실.
  - `not-run`: 비교 실행을 하지 못함. 누락된 모듈·예산·도구 등 이유를 남긴다.

작은 차이나 변동이 의심되면 남은 예산 안에서 재확인하고, 불충분하면 `unverified`로 둔다.
한 태스크의 `accepted`는 그 태스크에서의 선택 근거이며 다른 과제에서의 일반화 증거가 아니다.
`recovered + unverified`도 가능하다. 이 경우 검증된 산출물은 사용할 수 있지만 방식 개선을 입증했다고
보고하지 않는다. 기각할 때는 실험의 변경만 제외하고 기존 사용자 변경과 검증된 산출물을 보존한다.
후보 선택 뒤 실제 통합 결과에는 기존 빌드·테스트·AC 게이트를 적용한다. 비교 점수가 완료 권한을 대신하지 않는다.

## 결과를 다음 실행으로 전달

Lead만 기존 activity log에 다음을 짧게 남긴다. 별도의 전역 장부나 새 스킬을 만들지 않는다.

```text
task / AC:
failure / hypothesis / change:
baseline / candidate: 시작 상태·입력·설정 참조, 실제 실행 명령과 산출물
comparison: 조건 일치 여부, 품질·회귀 결과, 비용 또는 unknown, 남은 예산
task: recovered | unresolved
adjustment: accepted | rejected | unverified | not-run
reason / applicable-when / reopen-when:
```

선택한 방식은 현재 작업의 해당 조건에서 사용한다. 이후 태스크에 전달할 때도 적용 조건을 다시 확인한다.
핸드오프 시 므네모에 이 로그의 정확한 경로와 적용 조건을 넘긴다. 기각·미확인 결과도 구분해 남기며
핸드오프를 기다리느라 현재 작업의 복구를 미루지 않는다. 영구적인 프로젝트 스킬 수정은 별도 개선
작업에서 별도 평가 사례로 검증한다. 이번 실행 결과만으로 설치된 스킬 정본을 덮어쓰지 않는다.
