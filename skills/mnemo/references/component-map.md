# 부품 지도 작성

TermSnap 코드맵은 계산으로 만들어진다. 심볼 위치, 폴더별 분류, 타입 관계까지가 그 범위이고
"어떤 파일들이 한 기능인가"와 "그 부품이 무엇을 책임지는가"는 계산으로 나오지 않는다.
이 둘을 담는 `codemap/component-map.json`만 에이전트가 쓰는 작성물이며, TermSnap은 검증하고
`codemap/components/index.md`·`owners.json`을 낸다.

**지도는 그 부분을 방금 고친 세션이 쓴다.** 어떤 부품이 무엇을 책임지고 고칠 때 무엇을 함께 고쳐야
하는지는 그 코드를 읽고 고친 세션이 가장 잘 안다. 열어 보지 않은 코드의 설명은 이름을 풀어 쓴 것에
그친다. 그래서 지도는 통째로 한 번에 쓰는 문서가 아니라, 작업한 순서대로 채워지는 문서다.

## 쓰는 시점

| 시점 | 쓰는 것 | 핸드오프 줄의 표식 |
|---|---|---|
| 핸드오프, 지도 없음 (`NONE — 지도 없음 · 이번 세션이 고친 파일 N`) | 이번 세션이 다룬 부분만 부품으로 적어 지도를 시작한다 | `→ 시작함: <부품>` |
| 핸드오프, 지도 있음 (`고친 부품: …`) | 고친 부품의 설명을 이번 변경에 맞게 확인·보강한다 | `→ 설명: <보강한 부품>` 또는 `→ 설명: 변경 없음` |
| 핸드오프, 지도 있음 (`이번 세션 미배정 N`) | 새 파일을 알맞은 부품에 넣는다 | `→ 배정함: <부품>` |
| 직접 요청 ("부품 지도 작성해줘") | 요청받은 범위. 전체를 원하면 아래 "통째로 쓸 때" | — |

쓰지 않을 이유가 있으면 같은 줄에 `→ 보류: <이유>`를 적는다. 폴더 구조가 곧 기능 구조인 프로젝트는
코드맵의 폴더별 카테고리가 이미 같은 답을 주므로 지도가 필요 없다.

## 재료

| 무엇 | 어디서 |
|---|---|
| 작성 규칙과 예시 JSON | `codemap/components/index.md`. 규칙의 정본은 TermSnap 출력이며 여기에 옮겨 적지 않는다. |
| 지도가 덮을 수 있는 파일 범위 | `codemap/files.md`. 폴더 목록이나 `git ls-files`가 아니라 이 목록이 기준이다. |
| 이번 세션이 다룬 기능의 경계 | 지금 쓰는 핸드오프의 `Feature Boundary`·`Files Modified` 표 |
| 자동 분류가 이미 주는 묶음 | `codemap/index.md`의 카테고리 표 |

지도가 없을 때의 `owners.json`은 소스 파일 수만 알려 주고 목록은 비어 있다. 파일 범위를 여기서 얻으려 하지 않는다.

## 작게 시작한다

TermSnap은 일부만 채운 지도를 받는다. 배정되지 않은 소스는 오류가 아니라 지표로 나온다.
그러니 처음에는 이번 세션이 다룬 부품 하나만 있어도 된다.

1. 시스템 하나, 역할로 이름 붙인 컨테이너 하나를 둔다. 컨테이너에는 coverage를 주지 않는다.
2. 이번 세션이 고친 파일들이 이루는 기능을 부품으로 적는다. 파일이 여러 폴더에 흩어져 있으면 그대로
   한 부품에 모은다 — 지도가 자동 분류보다 나은 지점이 여기다.
3. coverage는 그 기능의 파일을 다 덮게 쓴다. 이번에 고친 파일만 넣지 말고, 같은 기능인 줄 아는 파일까지.
   모르는 파일은 넣지 않는다.
4. 설명은 `Feature Boundary`에 적은 내용을 옮긴다. 아래 기준을 따른다.

다음 세션들이 같은 방식으로 자기가 다룬 부품을 더한다. 컨테이너가 하나로 모자라면 그때 나눈다.

## 설명 쓰는 기준

- 이름을 풀어 쓰지 않는다. "무엇을 책임지는가"를 한 문장으로 쓴다.
- **고칠 때 함께 고쳐야 하는 것**을 적는다. 예: "참조 문서를 추가하면 배포 목록에도 넣어야 다른 CLI로 간다."
  이번 세션에서 실제로 놓칠 뻔했거나 테스트가 잡아 준 결합이 여기 들어갈 내용이다.
- 확인한 것만 쓴다. 열어 보지 않은 부품의 설명을 짐작으로 채우지 않는다 — 비워 두면 다음에 그 부품을 다루는
  세션이 쓴다.
- 구현 세부(함수 이름, 줄 번호, 개수)는 쓰지 않는다. 코드가 바뀌면 낡는다.
- 이미 있는 설명을 보강할 때는 틀려진 문장을 고치고 새로 알게 된 결합을 더한다. 통째로 다시 쓰지 않는다.

## 검증

MCP `codemap_component_map`이 있으면 호출한다. 없으면 TermSnap에서 프로젝트를 다시 열거나 코드맵을 다시
생성한 뒤 `codemap/components/index.md`의 오류·미분류를 읽는다. `codemap/`은 파일 감시 밖이라 지도를
저장하는 것만으로는 산출물이 바뀌지 않는다.

핸드오프 중에 검증하지 못했으면 표식 뒤에 `검증 NOT RUN — <이유>`를 붙인다. 다음 핸드오프의 줄이
`지도 오류 N`이나 `산출물이 지도보다 오래됨`으로 이어서 알려 준다. 작성했다는 사실을 검증 통과로 말하지 않는다.

## 자주 막히는 곳

- **glob이 아무것도 못 잡으면 오류다.** 빈 폴더, gitignore로 코드맵에서 빠진 폴더가 그렇다.
- **"나머지 전부"를 쓸 수 없다.** glob에 제외가 없어서, 넓은 glob은 형제 부품과 겹침 오류가 된다.
  형제끼리는 폴더를 나열하고, 넓은 범위가 필요하면 컨테이너에 coverage를 주고 부품을 그 안에 중첩한다
  (자식이 조상 범위 안에 있으면 겹침이 아니다).
- **파일마다 주인은 하나다.** 여러 기능이 함께 쓰는 파일은 공유 부품 하나로 모은다.
- **형제가 여럿인데 밖과 관계가 하나도 없는 요소는 경고가 나온다.** 실제 의존이 있으면 적고, 정말 독립된
  묶음이면 경고를 받아들인다. 경고를 없애려고 관계를 지어내지 않는다.
- **관계 대상은 전체 경로로 적는다.** 짧은 경로는 범위에 따라 다른 요소를 가리키거나 못 찾는다.
- **코드맵 파일 목록에는 로컬 전용 파일도 있다.** 압축 산출물, 개인 실행 스크립트처럼 추적하지 않는 파일은
  배정하지 않는다. 전부 배정이 목표가 아니다.
- **예시에 없는 필드를 쓰지 않는다.** 파일 수·커버리지·줄 번호 같은 계산값과 뷰는 작성 대상이 아니다.

## 통째로 쓸 때

사용자가 전체 지도를 요청했을 때만 한다. 얻는 것은 파일 배정의 완성이고, 열어 보지 않은 부품의 설명은
여전히 얕다 — 그 사실을 보고에 적는다.

1. 여러 폴더에 걸친 기능부터 찾아 부품으로 잡는다.
2. 컨테이너를 역할로 나눈다. 폴더 모양으로 나누면 걸친 기능이 둘로 쪼개진다.
3. 폴더 하나로 끝나는 덩어리는 주제별 부품에 `폴더/**` 한 줄로 넘긴다. 주제 분류는 이미 있는 분류(문서의
   카테고리 표 등)를 따르고 새 기준을 만들지 않는다.
4. 이번 세션에서 실제로 읽은 부품만 설명을 깊게 쓰고, 나머지는 확인되는 범위로만 적는다.

## 하지 않는 것

- TermSnap 검증기를 다시 구현해 배포하지 않는다. 규칙이 두 곳에 생기면 어긋난다. 작성 중에 glob이 무엇을
  잡는지 보려고 일회성 점검을 쓰는 것은 괜찮지만, 판정의 정본은 TermSnap 산출물이다.
- 함수 단위 설명을 지도에 넣지 않는다. 그것은 함수 위 주석에 둔다 — 코드와 함께 고쳐지고 읽을 때 같이 보인다.
- 이번 세션이 다루지 않은 부품의 설명을 고치지 않는다.
- Git 추적 여부를 혼자 정하지 않는다. `codemap/`이 gitignore인 프로젝트에서는 지도도 추적되지 않아
  폴더를 지우거나 다른 컴퓨터로 옮기면 사라진다. 지도를 처음 만들 때 이 사실을 사용자에게 알리고
  프로젝트의 방식을 따른다.
