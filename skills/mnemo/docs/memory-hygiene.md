## 기억 종합 진단 (Mnemo Doctor)

기억이 현재 구조에서 어긋난 곳을 한 번에 봅니다. **기억은 git 추적 밖이라 diff로 썩음을
볼 수 없으므로**, 드러내는 것 자체가 이 도구의 값입니다.

```bash
python scripts/mnemo_doctor.py              # 진단만 (아무것도 쓰지 않음)
python scripts/mnemo_doctor.py --fix        # 기계적으로 안전한 것만 수정
```

| 점검 | 보는 것 | `--fix` |
|------|---------|---------|
| 저장 구조 | MEMORY.md / memory / conversations / docs/handoffs | — |
| 인덱스 예산 | 100줄·5KB 한도 초과 | — |
| 인덱스 링크 | `MEMORY.md` → `memory/*.md` 링크 끊김 (**FAIL**) | — |
| 항목 메타데이터 | `tags` / `date` / `source` 결손 | — |
| 상세 파일 크기 | 40KB 초과 상세 기억, 분할본·단일 본문 공존 (안내 색인 제외) | — |
| 수명주기 링크 | `superseded-by` / `supersedes` 대상 존재 (역방향 연결 완전성은 별도 확인) | **✅ `#slug` → `[[NNN-slug]]`** — 같은 디렉터리에서 제목 slug·파일명이 **정확히 하나**와 일치할 때만. 추측 없음, 파일별 `.bak-<시각>` |
| 정제 기준값 | 회전 후 delta 음수 (**FAIL**) | **✅ 보정** |
| 기록 안의 절대경로 | 핸드오프 `Project:`·도구 로그 Edit/Write 줄·관찰 로그 경로 필드에 남은 루트 안 절대경로. 기억 본문은 보고만 | **✅ 루트 기준 상대경로** — 기준은 현재 루트뿐. 다른 위치를 가리키는 헤더·경로(분리된 저장소·전신 프로젝트·워크트리 흔적)는 그대로 두고 개수만 보고, 파일별 `.bak-<시각>`, 관찰 로그 줄 수 보존 |
| 관찰 분류 | 옛 훅이 오분류한 관찰 잔존 | — |
| 코드 앵커 | 현재 경로 확인 실패와 별도 문맥 확인 대상 구분 | — |
| 핸드오프 | 개수·최신본·`Origin` 유무 | — |
| 역사 복원 | 기록 범위·계보 폭·체인 연결·설계 산출물 | — |
| 기록 커버리지 | 프로젝트 시작 대비 기록 공백, git 커밋 품질 | — |

**처음 보는 프로젝트에서도 "여기까지 어떻게 왔는가"를 먼저 말합니다.** 구조만 보면
"태그가 54개 비었다"까지밖에 못 갑니다. `역사 복원` 항목이 기록 범위, 계보로 되살릴 수
있는 파일 수, 핸드오프 체인 연결 상태, 남아 있는 설계 산출물을 함께 보고합니다.
체인이 끊겨 있으면 **순서는 날짜로, 인과는 파일 계보로** 따라가라고 경로를 알려줍니다.

`기록 커버리지`는 다른 질문에 답합니다 — **얼마나 멀리까지 남아 있나**입니다. 기억과
핸드오프는 도입 시점부터 시작하므로 초기 구간은 통째로 비어 있기 마련입니다.
`memory/`·`docs/`가 git 추적 밖이라 이 비대칭을 놓치기 쉬운데, **그 공백을 메울 수 있는
것은 git 커밋뿐**입니다. 그래서 공백 구간과 함께 커밋 메시지의 Conventional 비율을
보고합니다 — 기계적으로 읽을 수 있는지가 복원 가능성을 가릅니다.

**`--fix`가 고치는 것은 셋뿐입니다** — 정제 기준값(산술 불일치), 기록 안의 루트 내부 절대경로(핸드오프
헤더·도구 로그·관찰 로그를 루트 기준 상대경로로, 프로젝트를 옮겨도 유효하도록), 그리고 태그 이름으로 가리키던
lifecycle 링크(`#slug`)를 항목 번호(`[[NNN-slug]]`)로 바꾸는 것. 후자는 같은 디렉터리에서
제목 slug나 파일명(번호 뗀 것)이 **정확히 하나**와 일치할 때만 실행되고, 앞부분만 같은
축약 참조·둘 이상에 맞는 참조는 그대로 두고 보고합니다. 잘못 이어진 링크는 경고가 사라져
끊긴 링크보다 나쁘기 때문입니다. 태그는 검색용이라 세션마다 바뀌지만 번호는 안 바뀝니다 —
그래서 링크는 번호로, 검색은 태그로 합니다.

나머지는 판단이 필요합니다 — 사라진 앵커가 "경로를 고칠 것"인지 "결정이 끝나 `SUPERSEDED`할
것"인지는 도구가 정할 수 없습니다.
진단만 돌릴 때는 **파일을 하나도 쓰지 않습니다**(테스트로 강제).

판정 로직은 복제하지 않고 `check_memory_anchors.py`·`reclassify_observations.py`를
그대로 호출합니다. 닥터가 따로 판정하면 둘이 갈라집니다.

`상세 파일 크기`는 인덱스에만 예산이 있고 **상세 기억에는 상한이 없다는 비대칭**을 잡습니다.
`memory-compact`는 `MEMORY.md` 전용이라 `memory/*.md`는 제한 없이 자랍니다. 한 항목을
보려고 200KB를 읽게 되면 점진적 공개가 무의미해집니다. 분할 구조는 새로 만들 것이 아니라
**이미 `gotchas/`·`learned/`가 쓰는 '여러 파일 + `index.md`'를 따르면** 됩니다.

종료 코드는 `0`(FAIL 없음) / `1`(FAIL 있음) / `2`(프로젝트 루트 확인 실패)입니다.

## 기억 앵커 검사

기억 항목이 인용한 코드 경로(`` `src/Relay.cs` ``)가 아직 실재하는지 확인합니다.
`memory/`·`codemap/`·`docs/`는 대개 git 추적 밖이라 **diff로는 썩음을 볼 수 없습니다.**
앵커 검사가 조용히 썩는 문제를 드러나는 문제로 바꿉니다.

```bash
python scripts/check_memory_anchors.py                    # memory/ 전체
python scripts/check_memory_anchors.py --file memory/architecture.md
python scripts/check_memory_anchors.py --no-codemap       # 이동 힌트 끄기
```

- **라인 번호는 검증하지 않습니다.** 라인은 늘 밀리므로 확인하면 신호가 아니라 소음이 됩니다.
- **파일명만 적힌 앵커**(`` `GRAPH_REPORT.md` ``)는 "루트의 그 파일"이 아니라 "그 이름의 파일"로 풉니다.
- **CodeMap이 있으면 이동 후보를 제안합니다.** 판정은 파일시스템이 하고 CodeMap은 후보만 내며,
  제안 전에 디스크에서 다시 확인합니다 (CodeMap 자체가 stale일 수 있음).
- **아무것도 고치지 않습니다.** 경로 수정이나 `SUPERSEDED` 표시는 사람이 판단합니다.
- 홈 경로는 현재 사용자의 실제 경로로 확인합니다. 예시·템플릿·패키지명·명시적 금지·
  과거 결정의 참조는 현재 파일 누락으로 단정하지 않고 별도 문맥 확인 대상으로 표시합니다.
  일반 `SKILL.md`·`package.json`처럼 이름만 같은 파일을 이동 후보로 제시하지 않습니다.
- 메타데이터는 색인이 아닌 항목의 범위에서 검사합니다. 긴 교체 설명 뒤 필드도 읽되,
  코드 예제와 하위 항목의 필드를 현재 항목의 메타데이터로 사용하지 않습니다.

종료 코드는 `0`(직접 검사 대상에서 누락 없음; 별도 문맥 확인은 남을 수 있음) /
`1`(현재 경로 확인 실패) / `2`(루트 확인·파일 읽기 등 검사 실패)입니다.

## 관찰 오분류 복구 (1회성)

옛 훅은 "출력 어딘가에 error/fail이라는 단어가 있는가"로 실패를 판정했습니다. Edit/Write의
응답은 편집한 소스를 그대로 되돌려주고 Bash 출력에는 `cat`으로 읽은 코드가 흘러들어서,
`Failed(` 호출이나 `{Info, Warning, Error}` enum 때문에 **성공한 작업이 `gotchas`에 쌓였습니다**
(실측 98~99%). 훅은 고쳐졌고, 이 스크립트는 이미 쓰인 것을 되돌립니다.

```bash
python scripts/reclassify_observations.py              # dry-run (기본)
python scripts/reclassify_observations.py --apply      # 백업 후 이동
```

**프로젝트 단위입니다** — 관찰은 `<프로젝트>/memory/`에 쌓이고 `~/.claude`에는 없습니다.
프로젝트마다 따로 돌려야 합니다. `--apply`는 항상 `observations.jsonl.bak-<시각>` 백업을
먼저 만들며, `*.jsonl`이 아닌 이름이라 수확·정제가 다시 읽지 않습니다.

옮긴 기록에는 `reclassified_from: tool_error`가 남습니다. 오류 정규식에 맞지 않는다는
이유만으로 성공으로 바꾸지 않습니다. 명시적인 성공 상태나 알려진 편집 성공 응답만
이동 대상으로 삼고, 실패·불명확한 기록·`turn_error`·파싱 불가한 줄은 보존합니다.
이동은 두 파일 사이의 재배치이므로
`.mnemo-distill-offset`의 기준값도 같이 옮겨 **정제 임계(delta)를 그대로 유지**합니다.

> 백업은 `memory/`에 생기고 이 디렉터리는 보통 git 추적 밖입니다. `git clean -xdf`로 지워질
> 수 있으니 되돌릴 가능성을 남기려면 결과를 확인한 뒤 따로 보관하세요.

## 상세 기억 분할

`MEMORY.md`에는 100줄·5KB 예산과 `memory-compact`가 있지만 **상세 파일에는 상한이 없습니다.**
`memory/architecture.md`가 224KB/160항목까지 자란 실측이 있고, 그 크기에서는 항목 하나를
보려고 파일 전체를 읽게 되어 점진적 공개가 무의미해집니다.

```bash
python scripts/split_memory_file.py memory/architecture.md            # dry-run
python scripts/split_memory_file.py memory/architecture.md --apply    # 백업 후 분할
```

- 구조는 새로 만들지 않고 **`gotchas/`·`learned/`가 이미 쓰는 "항목별 파일 + `index.md`"**를 따릅니다.
  `##` 섹션은 `index.md`의 Section 컬럼으로 보존됩니다.
- 항목 단위로 나눕니다 — 섹션 단위는 한 섹션이 78%를 차지한 실측에서 거대 파일을 남겼습니다.
- 원본은 `.bak-<시각>`으로 백업 후 **제거**합니다. 분할본과 단일본이 함께 있으면 정본이 모호하고,
  훅 스캐폴드가 단일본을 되살리지 않도록 `<카테고리>/index.md` 존재를 확인합니다.
- `MEMORY.md`의 마크다운 링크는 `memory/X/index.md`로 갱신하고, **링크가 아닌 형태의 언급**
  (`a=architecture.md` 같은 약어 범례)은 자동으로 고치지 않고 위치를 경고합니다. 분할 뒤
  `MEMORY.md`의 코드는 다른 카테고리처럼 `a:N`으로 항목을 직접 지정하게 바꿉니다.
- 섹션 설명·코드 펜스는 보존하고 상대 링크를 새 위치 기준으로 옮깁니다.
  확인 가능한 항목 앵커는 해당 파일로 연결하며 원본과 `MEMORY.md`를 함께 백업합니다.
  이미 내용이 있는 분할 디렉터리와의 병합, HTML/wiki 링크 재작성은 지원하지 않습니다.

## 변경 계보 수확

핸드오프의 `Files Modified` × 그 세션의 결정을 이어 붙여 **"이 파일이 언제, 왜, 어떻게
바뀌어 왔는가"**를 뽑습니다. 설계 파이프라인 없이 즉흥으로 작업해도 핸드오프는 남으므로,
`specs/`가 없는 프로젝트에서도 계보가 쌓입니다.

```bash
python scripts/harvest_lineage.py --file Relay.cs    # 구현 착수 전 조회 (주 용도)
python scripts/harvest_lineage.py                     # 전체 색인 (stdout)
python scripts/harvest_lineage.py --out memory/change-lineage.md
```

**파생 색인입니다.** 핸드오프를 고치지 않고 매번 새로 만들므로, 손으로 관리하는 기능
목록과 달리 썩지 않습니다. `--out` 없이는 아무것도 쓰지 않습니다.

**입력이 없을 때는 실패가 아니라 결과입니다** — 핸드오프가 없거나, `Files Modified`가
없거나, 조회한 파일의 계보가 없으면 이유를 설명하고 종료 코드 0으로 끝납니다.
"없음 확인"도 착수 판단의 근거이기 때문입니다. 실패(2)는 프로젝트 루트를 못 정할 때뿐입니다.

이유는 `Decisions` → `Assumptions` → `Origin`(최초 요구) → 세션 주제 순으로 내려가며,
결정이 아닌 출처는 `[가정 추정]`·`[요구 추정]`·`[주제 추정]`으로 **표시합니다.
이유를 지어내지 않습니다.**
