# 점수 모델 — 두 축을 절대 평균내지 않는다

> 이 문서는 `scripts/score.py`의 정본입니다. 가중치를 바꾸면 스크립트와 이 표를
> 함께 고쳐야 하며, `scripts/test_score.py`가 규칙 위반을 잡아냅니다.

---

## 왜 점수가 둘인가

검색 순위는 잘 나오는데 AI가 인용하지 못하는 사이트가 있고, 그 반대도 있습니다.
하나의 숫자로 뭉개면 그 사실이 사라집니다. 그래서 **검색 SEO 점수**와
**AI 가시성 점수**를 끝까지 따로 계산하고, 리포트에도 따로 씁니다.

| 축 | 측정 대상 | 주 영역 |
|----|----------|--------|
| **검색 SEO** | Google/Bing 색인·순위 | 1~7 |
| **AI 가시성** | AI 크롤러 접근 + 답변 발췌 + 인용 | 8~10 (+ 4, 7 공유) |

두 점수를 평균한 "종합 점수"는 만들지 마세요.

---

## 계산식

```
영역값 = 100 × Σ(상태계수 × 심각도가중치) / Σ(심각도가중치)
축점수 = Σ(영역값 × 영역가중치) / Σ(활성 영역가중치)
```

### 상태 계수

| status | 계수 | 의미 |
|--------|------|------|
| `pass` | 1.0 | 통과 |
| `warn` | 0.5 | 부분 충족 |
| `fail` | 0.0 | 미달 |
| `na` | **제외** | 이 프로젝트에 해당 없음 |
| `unknown` | **제외** | 정적 분석으로 판정 불가 |

### 심각도 가중치

| 등급 | 가중치 |
|------|--------|
| P0 | 5 |
| P1 | 3 |
| P2 | 2 |
| P3 | 1 |

## na 제외와 재정규화 (중요)

`na`는 **분자와 분모 양쪽에서 빠집니다.** 통과로도 치지 않고 감점도 하지 않습니다.

> 블로그가 `Product` 스키마를 안 쓴다고 깎이면 안 됩니다.
> 사내 대시보드에 "팩트 밀도가 낮다"는 감점은 무의미합니다.

한 영역의 항목이 **전부** `na`면 그 영역은 분모에서 통째로 빠지고, 남은 영역들로
재정규화됩니다. 점수는 항상 "활성 가중치 합계 기준"으로 나옵니다.

리포트에는 제외 건수를 반드시 표시하세요 — 점수의 신뢰 구간을 밝히는 역할입니다.

### 사이트 유형별 기본 na 판정

Step 1 정찰에서 유형을 판정한 뒤 적용합니다.

| 유형 | na로 두는 항목 |
|------|---------------|
| 앱/대시보드 (콘텐츠 없음) | 영역 9 전체, 영역 10의 팩트·출처·저자 항목 |
| 블로그/문서 | 영역 4의 Product/Offer |
| 단일 언어 | 영역 2의 hreflang, 영역 3의 다국어 canonical |
| 비커머스 | 영역 4의 Product, Offer, AggregateRating |
| 사내/비공개 | 영역 8 전체 (AI 크롤러 노출이 목표가 아님) |

## P0 상한 (severity 게이팅)

**해당 축에 걸린 P0이 하나라도 `fail`이면 그 축은 40점(F)으로 상한 처리됩니다.**
다른 항목이 아무리 좋아도 마찬가지이며, 결과에 `capped: true`와 원인 ID가 붙습니다.

`Disallow: /` 하나로 색인에서 사라지는 사이트가 "87점 B등급"으로 표시되면
점수가 거짓말을 하는 것이기 때문입니다.

- 상한은 **상한이지 하한이 아닙니다.** 이미 40점 미만이면 그대로 둡니다.
- 축은 독립적입니다. `GPTBot` 차단(영역 8)은 AI축만 캡하고 검색축은 건드리지 않습니다.

## 배점 근거가 바뀐 항목

### llms.txt — 가중치 0 (보고만 함)

**점수에 반영하지 않습니다.** 존재 여부는 리포트에 적되 가감점은 없습니다.

근거: Google이 AI 검색 최적화 안내에서 `llms.txt`를 실효성 없는 항목으로 분류했고,
이를 근거로 삼은 두 개의 독립 구현(`AgriciDaniel/claude-seo`,
`Hainrixz/claude-seo-ai`)이 각각 "myth"와 "weight 0"으로 동일하게 처리하고 있습니다.
채택률 자체도 크롤러 측 지원이 확인되지 않았습니다.

> 다만 Google 원문을 직접 확인한 것은 아니며, 서드파티 두 곳의 독립적 합의까지가
> 확인된 사실입니다. 반대 근거가 나오면 이 항목부터 재검토하세요.

### FAQPage 스키마 — P1에서 P2로

Google이 FAQ 리치 결과 노출을 대부분의 사이트에서 축소한 이후, "Featured Snippet
선점"은 더 이상 기대 효과로 쓸 수 없습니다. 다만 질문-답변 쌍을 명시적으로 구조화하는
것은 **AI 발췌에 여전히 유효한 신호**이므로 항목 자체는 남기고 등급만 낮춥니다.

리포트에서 "리치 결과를 받게 된다"고 쓰지 마세요.

### AEO/GEO는 별개 분야가 아니다

GEO 소견은 "AI 검색 표면에 적용된 SEO 기본기"로 서술하세요. 커뮤니티 권고가
Google 1차 자료와 충돌하면 1차 자료를 따르고, 충돌 사실을 리포트에 적습니다.

## findings 스키마

`scripts/score.py`의 입력 형식입니다.

```json
{
  "findings": [
    {
      "id": "A8-1",
      "area": 8,
      "severity": "P0",
      "status": "fail",
      "axis": ["ai"],
      "evidence": "public/robots.txt:12 — Disallow: / for GPTBot",
      "note": "의도적 차단인지 확인 필요"
    }
  ]
}
```

| 필드 | 필수 | 설명 |
|------|------|------|
| `id` | O | `A{영역}-{번호}` |
| `area` | O | 1~10 |
| `severity` | O | P0~P3 |
| `status` | O | pass / warn / fail / na / unknown |
| `axis` | O | `["search"]`, `["ai"]`, 또는 둘 다 |
| `evidence` | 권장 | `file:line` 형식의 근거 |
| `note` | 선택 | 판단 보류 사유 등 |

`evidence` 없이 `fail`을 쓰지 마세요. 근거를 못 찾았으면 `unknown`입니다.
