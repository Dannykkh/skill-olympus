# 아프로디테 텍스트 다이어트 평가

2026-11-11 · Claude · `skills/design-plan`, `skills/frontend-design` 미커밋 변경 기준

`docs/research/2026-11-04-aphrodite-eval/`의 예제(`fixture/projectflow`)와 블라인드 작업자 지시문을 그대로 썼다.
달라진 것은 실행 폴더 경로뿐이다. 비교 기준은 그 평가의 `runs/after/S1`, `runs/after/S2`다.
S3은 와이어프레임 전에 멈추는 시나리오라 돌리지 않았다.

## 실행

| 실행 | 요청 | 규칙 상태 |
|---|---|---|
| S1 | `/aphrodite --plan-only 첫 화면이 너무 휑해. 대시보드답게 좀 채워줘.` | 텍스트 예산 + 덜어내기 1차 |
| S2 | `/aphrodite docs/plan/projectflow --plan-only` | 위와 같음 |
| S2b | S2와 같음 | 덜어내기에 "골격은 빼지 않음"·빈 자리 점검을 더한 2차 |

## 결과 (대표 화면: 프로젝트 0개인 홈)

빈 자리 비율은 캡처(1280×800)를 눈으로 본 어림값이다. S2b는 작업자가 691/800까지 채웠다고 기록했다.
11-04 실행은 와이어프레임 파일이 남아 있지 않아 Layout Blueprint 문서의 서술로 대조했다.

## 판정

- **텍스트는 줄었다.** 세 실행 모두 홈의 설명 문장이 0개이고, 머리는 제목과 보조 하나다. 명료성을 설명 문구가
  아니라 라벨 수정으로 통과시켰다(S1: `첫 할 일` → `첫 할 일 배정`).
- **1차 규칙은 블록을 과하게 뺐다(S2).** "댈 수 없는 블록은 빼거나 접고"가 anatomy `Dashboard` 첫 실행 변형의
  "앞으로 채워질 구역"과 부딪혔고, S2 작업자는 그 구역을 뺐다. 같은 블록을 S1은 남겼다. 규칙이 실행마다 다르게 읽혔다.
- **2차 규칙에서 갈림이 사라졌다(S2b).** 채워질 구역을 구조 요소로 남겼고, 처음 그린 화면의 아래 32%가 비자
  설명이 아니라 미리보기 크기로 채웠다. 설명 문장은 다시 늘지 않았다.
- **지난 평가 항목은 유지됐다.** 세 실행 모두 상류 문서 3개를 읽었고, 계층을 `strategy`로 판정했고, 팀 성과
  KPI 대시보드를 출처와 함께 제외로 적었고, 첫 화면이 KPI 카드형이 아니다. 읽은 하네스 문서 줄 수(R7)는 세지 않았다.

## 한계

- 시나리오당 1~2회 실행이다. 같은 규칙으로 여러 번 돌려 흔들림을 재지 않았다.
- 예제가 첫 실행 대시보드 하나뿐이다. 랜딩(Hero·Feature·Pricing)과 데이터가 찬 대시보드에서는 확인하지 않았다.
  텍스트 예산의 수치(머리 = 제목 + 보조 하나 + 주 행동, 블록 설명 기본 0)는 마케팅 화면에서 검증되지 않은 가정이다.
- "절반 가까이 비면 과하게 뺀 것"은 S2 한 건에서 나온 어림 기준이다.
- Phase 2까지만 돌렸다. 시각 방향·구현 단계에서 설명 문구가 다시 붙는지는 보지 않았다.
- 판정은 평가자(메인) 한 명의 캡처 관찰이다. 사람 사용자 확인이 아니다.

### 확인 실행 S2c

위 일곱 가지를 고친 뒤 S2와 같은 지시문으로 한 번 더 돌렸다.

- Layout Blueprint 첫 줄 `Mode: 없음 — 첫 실행`, `화면 유형: NOT APPLICABLE — 데스크톱 우선`. 양식 절을 읽었다.
- After를 `board-created (board의 프로젝트 생성 완료 상태)` 형식으로 적었고 사이트맵에 화면으로 더하지 않았다.
- 계약 검증기: 오류는 scope 미결 한 줄("댓글을 MVP에 넣는가")뿐, 누락·빈 절 없음. 작업자가 `결정 대기`로 보고했다.
  "프로젝트 이름 바꾸기"는 Object Flows의 Edit 칸으로 들어가 scope 미결로 올라오지 않았다.
- 일곱 가지는 모호점 목록에 다시 올라오지 않았다. 홈의 설명 문장은 빈 상태 한 줄뿐이고 채워질 구역이 남았다.

S2c가 새로 짚은 것 네 가지도 고쳤다. 이 네 가지는 다시 돌려 확인하지 않았다.

| 모호점 | 정한 내용 | 위치 |
|---|---|---|
| After 상태를 2-5에서 어디까지 그리나 (#6의 부작용) | 데스크톱·모바일 둘 다는 대표 화면만. 상태·After는 한 뷰포트의 상태 시트 한 장 | SKILL 2-5 |
| Role Variants의 미결 칸에 무엇을 적나 (S2도 지적) | 권장값 + `(미결)`, 같은 이름으로 Open Decisions(structure) | SKILL 4-1-1 |
| 폴더만 받은 요청의 계층과 대표 화면 | strategy, 대표 화면은 P1을 푸는 첫 화면 | SKILL 0-1 |
| 상류 문서끼리 어긋날 때 | 한쪽을 고르지 않고 두 원문을 인용해 Open Decisions에 | SKILL 0-1 규칙 3 |

남은 것: 쓰기 범위가 `docs/design-refs/`뿐인 실행에서 루트 `PRODUCT.md`를 만들 수 없다는 지적은 평가 지시문의 제약에서
나온 것이라 고치지 않았다. 상류 문서에 사용자 확인 기록이 없어 모든 결정이 `AI 권장`이 된다는 지적(S2)은 젭마인
쪽 기록 형식의 문제라 여기서 다루지 않았다.
