## 블록 순서와 근거

`owner`, 프로젝트 0개. 순서는 역할·상태가 달라도 같고 노출만 달라집니다.

| # | 블록 | 답하는 질문 | 기여하는 성공 조건·과업 단계 | 필수 요소 |
|---|---|---|---|---|
| 0 | Sidebar | 여기가 어디인가, 어디로 갈 수 있나 | 현재 위치, P2(내비 `팀원`) | 팀 이름, `홈`(활성 1개)·`프로젝트`·`팀원`·`설정`, 하단 사용자 |
| 1 | 화면 머리 | 얼마나 남았나 | 조건 8(`시작 단계 1/3` 확인) | 제목 `홈` + 보조 `시작 단계 0/3`. 주 행동은 블록 2 안에 있음 |
| 2 | 시작 단계 | 지금 무엇을 하나, 그다음은 | 조건 1·2·3·5, 주 과업의 시작 | 1행: 채운 번호 원, 제목 `첫 프로젝트`, 라벨 `프로젝트 이름`, 입력란, solid `프로젝트 만들기` / 2행 `팀원 초대` / 3행 `첫 할 일 배정` |
| 3 | 내 할 일 칸 (2/3) | 배정된 일은 어디서 보나 | 팀원의 주 과업, 조건 7 | 제목, 빈 상태 한 줄 |
| 4 | 프로젝트 칸 (1/3) | 만든 것은 어디에 생기나 | 조건 8, 흐름 고리 After의 홈 쪽 증거 | 제목, 빈 상태 한 줄 |

- 그리드: 사이드바 240px 고정 + 본문 1열(최대 880px, 좌 여백 64px). 아래 두 칸은 2/3 : 1/3.
- 첫 뷰포트: 다섯 블록 전부. 데스크톱은 아래 120px, 모바일은 96px이 비고 스크롤 없음.
- 강조: 화면 전체에서 solid 버튼 1개, 채운 번호 원 1개, 활성 내비 1개.
- 모바일: 사이드바 → 상단 바 + 드로어, 입력란과 버튼은 풀폭 두 줄, 칸은 내 할 일 → 프로젝트 한 열. 상세는 계약 `Mobile Transformations`.

## 덜어내기

"휑하다"에 채울 후보를 과업 단계에 대 보고, 댈 수 없는 것은 뺐습니다. 후보별 판정 이유는 brief의 여섯 질문 표에 있습니다.

| 뺀 것 | 이유 |
|---|---|
| KPI 카드 행(프로젝트 수·완료율·팀원 수) | 상류 제외 항목. 0건이라 0만 보임. anatomy "0으로 채운 KPI·빈 차트 금지" |
| 차트·최근 활동 피드 | 데이터 0건. 어느 성공 조건에도 닿지 않음 |
| 환영 문단, 제품 소개, 일러스트 | 과업 단계 없음. 머리의 텍스트 예산(제목 + 보조 하나) 초과 |
| 사용법 카드·튜토리얼 | 시작 단계가 같은 일을 함 |
| 0/3 화면의 `초대하기` 보조 버튼 | 행동을 하나로. 초대는 2단계 차례에 primary가 되고 그 전에는 내비 `팀원` |
| 2·3행의 "프로젝트를 만든 뒤" 같은 잠금 설명 | 번호가 순서를 말함 |
| 진행률 링·퍼센트 | `시작 단계 0/3` 글자 하나로 충분 |
| 시작 단계 블록의 제목 줄 | 머리의 `시작 단계 0/3`이 그 역할 |
| 빈 칸 안의 CTA 반복 | solid 1개 규칙. 주 행동은 시작 단계에만 |

남긴 설명 문구: **0개.** 화면의 글자는 제목·라벨·버튼·상태뿐입니다.
남긴 예외 문구(빼지 않는 것): 빈 상태 `배정된 할 일이 없습니다`·`아직 프로젝트가 없습니다`(빈 상태 안내), `member` 빈 상태의 `팀 소유자 한지원`(회복 경로 — 누구에게 요청할지), 입력 오류 `프로젝트 이름을 입력하세요`, 조회 실패 `홈을 불러오지 못했습니다`.

빈 자리는 채우지 않고 주인공 크기에 썼습니다. 시작 단계 1행이 높이 200px, 입력란 56px로 화면에서 가장 큽니다.

## 다섯 기준 판단

| 기준 | 캡처에서 관찰한 근거 | 판정 | 고친 결정 |
|---|---|---|---|
| 위계 | 회색만으로도 가장 진한 것은 `홈`, `첫 프로젝트`, 입력란 테두리, `프로젝트 만들기`뿐. 1차 캡처에서는 빈 칸 두 개(140px)가 1행과 비슷한 무게였음 | 통과(수정 후) | 데스크톱 빈 칸 높이 140 → 96px. 상태 시트의 `member` 빈 칸도 같은 높이로 |
| 구조 | 머리 → 지금 할 일 → 다음 단계 → 결과가 놓일 칸. 팀 리더 카드의 질문 순서(무엇부터 → 얼마나 → 어디에)와 같음 | 통과 | 칸 비율을 내 할 일 2/3 : 프로젝트 1/3로 고정. 역할별로 뒤집지 않음(공용 권한차등은 순서 유지) |
| 흐름 | 진입(0/3) → 입력 → `project-wizard` → `project-created` → 홈 1/3(시트 4)까지 이어짐. 실패는 시트 2(입력)·3(조회)에서 같은 자리 복구. 마법사 안의 생성 실패는 이 화면 밖 | 통과(조건부) | 마법사 단계와 생성 실패 화면은 `01-onboarding`에서 그려야 함 — `Open Decisions` |
| 일관성 | 지금 = 채운 번호 원 + 굵은 제목 + 입력 + solid, 남음 = 빈 번호 원 + 회색, 완료 = 체크 + 회색 + 결과 이름. 시트 4의 2단계가 1단계와 같은 모양. 빈 칸은 점선, 채워진 칸은 실선 | 통과 | 없음 |
| 명료성 | 설명 문장이 없는 상태로 읽어 봄. 3행 `첫 할 일`이 "제일 먼저 할 일"로도 읽혀 1행과 부딪힘 | 통과(수정 후) | 3행 이름 `첫 할 일` → `첫 할 일 배정`. 설명을 더하지 않고 라벨을 고침 |

남은 약점: `시작 단계 0/3`은 14~15px 보조 글자라 스크린리더에는 "3단계 중 0단계 완료"로 읽히게 해야 함(계약 `Accessibility Contract`). 3단계 중 3행만 동사형(`배정`)이라 이름 꼴이 완전히 같지는 않음 — 오독을 막는 쪽을 택함.

## 역할 처리 (공용 권한차등)

spec 역할 표의 `화면` 열이 둘 다 `공용 권한차등`이라 별도 화면을 만들지 않았습니다. 변형표 정본은 계약 `Role Variants`.

- `owner`: 위 블록 전부.
- `member`: 블록 1의 보조 글자와 블록 2 전체가 숨김. 블록 3·4가 머리 바로 아래로 올라옴(시트 5·6).
- `member`에서 CTA가 사라지는 것을 확인함. 대신 프로젝트 빈 칸에 `팀 소유자 한지원`을 둠.

## 상태별 구조

| 상태 | 구조 변화 | 시트 |
|---|---|---|
| loading | 머리 제목은 그대로, 각 블록 자리에 뼈대. 블록 높이는 내용과 같게 잡아 밀림 없음 | 1 |
| error (입력) | 1행 안, 입력란 아래에 오류 한 줄. 다른 블록 그대로 | 2 |
| error (조회) | 머리 아래에 문구 + `다시 시도`만. 이 상태의 solid는 `다시 시도` 하나 | 3 |
| `owner` 1/3 | 1행이 한 줄로 접히고(체크 + 프로젝트 이름) 2행이 펼쳐짐. primary가 `초대 보내기`로 옮겨 감. 프로젝트 칸은 실선 행 | 4 |
| `owner` 2/3 | 같은 규칙으로 3행이 펼쳐지고 primary는 `할 일 추가` | 그리지 않음 — 시트 4와 같은 모양 |
| `owner` 3/3, `member` 배정 있음 | 시작 단계 없음. 내 할 일 행(제목 + 프로젝트 · 마감) | 6 |
| `member` 빈 상태 | 시작 단계 없음. 두 빈 칸 | 5 |
