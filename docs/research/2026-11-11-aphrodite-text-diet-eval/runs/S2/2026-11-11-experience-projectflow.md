## Page Goal

- 사용자가 이 화면에서 달성할 결과: 프로젝트가 0개인 계정이 홈에서 바로 첫 프로젝트를 만들고, 팀원을 초대하고, 첫 할 일을 배정해 보드에 도착한다.
- 제품이 얻어야 하는 결과: 가입 후 24시간 안에 첫 프로젝트를 만드는 계정 비율 60% 이상 (현재 30%, spec 공유 전제).
- 관찰 가능한 성공 조건:
  1. 프로젝트 0개인 owner가 홈에 들어오면 1280×800과 390×844의 첫 뷰포트에 `프로젝트 이름` 입력 칸과 `프로젝트 만들기` 버튼이 스크롤 없이 보인다.
  2. 홈에서 이름을 넣고 Enter 또는 버튼 1회로 프로젝트가 만들어지고 `팀원 초대` 단계가 열린다. 그 사이에 다른 화면이 없다.
  3. 홈에서 보드 도착까지 필수 입력은 프로젝트 이름 하나다. 2·3단계는 `나중에 하기`로 넘어갈 수 있다.
  4. 3단계를 마치면 보드의 `할 일` 열에 방금 배정한 카드 1건이 있고, 초대한 사람마다 `초대 보냄`이 붙어 있다.
  5. 저장이 실패하면 입력값이 남아 있고 같은 버튼으로 다시 시도할 수 있다.
  6. 프로젝트 0개인 홈에 0으로 채운 KPI, 빈 차트, 설명 문단, 환영 카드가 없다.
  7. member에게는 팀 설정·팀원 내보내기·팀원 초대·프로젝트 만들기 요소가 보이지 않고, 프로젝트가 0개여도 홈이 비어 있지 않다.

## Audience and Tasks

- 주요 사용자와 사용 상황: 팀 리더(`owner`) — 방금 가입해 프로젝트가 0개인 계정으로 처음 들어온 5~20명 팀의 리더. 핵심 사람이다.
- 최우선 과업: 프로젝트 이름 입력 → 팀원 초대 → 첫 할 일 배정.
- 시작 조건과 완료 조건: 시작 — 이메일 링크로 로그인했고 프로젝트 0개. 완료 — 보드에 담당자가 붙은 카드 1건이 보인다.
- 주요 불안·마찰·실패 가능성: 빈 화면에서 무엇을 할지 모름(P1), 몇 단계인지 모름, 남의 이메일을 넣는 순간의 망설임, 초대가 갔는지 모름, 저장 실패로 입력을 잃을 걱정.

## Header and Navigation

- 브랜드·현재 위치·전역 이동·주 행동의 순서: 사이드바의 제품 이름·팀 이름 → 전역 이동(`홈` · 프로젝트 이름들 · `팀원` · `설정`) → 본문 `h1` → 보조 한 가지 → 주 행동.
- 머리에서 내린 것: 환영 문구와 제품 소개(삭제), 단계 설명 문장(단계 이름 3개가 대신함), "이름은 나중에 바꿀 수 있습니다" 도움말(삭제 — 프로젝트 편집 범위가 미결이라 약속할 수 없다), 홈의 `홈` 제목(프로젝트 0개일 때는 `첫 프로젝트 만들기`가 제목이고 위치는 사이드바가 알린다).
- 데스크톱 내비게이션: 좌측 고정 사이드바. 활성 항목 1개. 프로젝트가 0개면 프로젝트 묶음을 그리지 않는다. `설정`은 owner에게만 있다.
- 모바일 대체 구조: 상단 바(제품 이름 + `메뉴` 버튼)와 메뉴를 누르면 열리는 서랍. 첫 실행 화면에서는 본문이 상단 바 바로 아래에서 시작한다.

## Core Message

- 핵심 약속: 첫 프로젝트 만들기
- 설명: 없음 — 제목으로 충분
- 증거: 단계 이름 3개(프로젝트 · 팀원 초대 · 첫 할 일)와 입력 칸 하나. 요구하는 것이 눈에 보이는 만큼뿐이다.

## Section Order

1. 본문 제목 `첫 프로젝트 만들기`: "여기서 뭘 하나"에 답한다.
2. 단계 표시(프로젝트 · 팀원 초대 · 첫 할 일): "얼마나 걸리나"에 답한다. 제목 바로 아래에 있어야 입력 전에 부담을 가늠한다.
3. `프로젝트 이름` 입력 칸: 과업의 첫 조작이다. 화면에서 가장 큰 요소다.
4. `프로젝트 만들기` 버튼: 입력 바로 아래에서 끝낸다.
5. (2단계) 이메일 입력 → 받을 사람 행 → `N명 초대하기` · `나중에 하기`: 보내기 전에 누구에게 가는지 확인한다.
6. (3단계) 할 일 → 담당자 → `배정하기` · `나중에 하기`: 무엇을 먼저 정하고 누구에게 줄지 고른다.
7. (보드 도착) 상태 알림 → 프로젝트 이름 → 팀원 줄 → 열 3개: 방금 한 일의 결과를 본다.

## CTA Strategy

- Primary: `프로젝트 만들기` — 목적지 setup-invite — 프로젝트 0개인 홈의 첫 뷰포트에 1회. 이후 화면의 primary는 화면마다 하나다: setup-invite `N명 초대하기`(N은 받을 사람 수. 0명일 때는 `초대하기`이고, 누르면 비활성 대신 이메일 칸에 오류를 보인다) → setup-task `배정하기` → board `할 일 추가`. 프로젝트가 생긴 뒤의 홈은 `새 프로젝트`.
- Secondary: `나중에 하기` — setup-invite, setup-task에만. 밑줄 글자로 둔다. board 팀원 줄 끝의 `팀원 초대`는 테두리 버튼이다.
- 반복 규칙: 채운 버튼은 화면당 하나. 같은 목적의 버튼을 한 화면에 두 번 두지 않는다(보드의 `할 일 추가`는 머리에만 있다).
- 완료·실패 피드백: 단계가 끝나면 단계 표시의 번호가 ✓로 바뀌고 사이드바에 프로젝트 이름이 생긴다. 보드에 도착하면 `초대 메일 2통을 보냈습니다.` 상태 알림이 한 번 보인다. 실패하면 같은 칸 아래에 오류 문구가 붙고 입력과 버튼은 그대로다.

## Trust Strategy

- 사용자가 불안을 느끼는 지점: 남의 이메일 주소를 넣고 보내는 순간, 보낸 뒤 실제로 갔는지 모르는 순간, 저장 실패.
- 그 직전에 제시할 근거: 보내기 전에 받을 주소를 행으로 보여 주고 `지우기`를 둔다. 버튼에 인원 수를 쓴다(`2명 초대하기`). 보낸 뒤 사람마다 `초대 보냄` 상태가 붙는다.
- 출처·날짜·검증 가능성: 모두 사용자가 방금 넣은 값과 시스템 상태다. 외부 주장이 아니어서 화면에서 바로 대조된다.
- 근거가 없을 때 생략할 요소: 보안·개인정보 문구, 사용 팀 수, 후기, 인증 배지. 근거 자료가 없으므로 싣지 않는다.

## Desktop Structure

- 기준 뷰포트: 1280×800
- 첫 뷰포트: 좌측 사이드바 232px + 본문 1열. 본문 왼쪽 위에서 제목 → 단계 표시 → 입력 칸(폭 560px, 높이 56px) → 버튼이 한 줄기로 내려온다. 버튼 아래는 비워 둔다.
- 그리드·pane·콘텐츠 위계: 입력 칸 > 제목 > 버튼 > 단계 표시 > 라벨. 보드는 본문 전체 폭에 열 3개(같은 폭).
- 스크롤 흐름과 밀도 변화: 첫 실행 3단계는 스크롤이 없다. 보드에서 카드가 늘면 열 안에서 세로로 쌓인다.

## Mobile Transformations

| Desktop element | Operation | Mobile result | Reason |
|---|---|---|---|
| 좌측 사이드바 | replace | 상단 바(제품 이름 + `메뉴`)와 서랍 | 첫 뷰포트를 입력 칸에 쓴다. 첫 실행에는 갈 곳이 적다 |

| 입력 칸(560px) | retain | 화면 폭 전체 | 과업의 첫 조작이다 |
| primary 버튼(글자 폭) | compress | 폼 안에서는 화면 폭 전체, 보드 머리에서는 글자 폭·높이 44px | 폼은 엄지로 끝내야 하고, 보드에서는 방금 만든 카드보다 커지면 안 된다 |
| `나중에 하기`(버튼 옆) | reorder | primary 아래 가운데 | 가로 폭이 모자라고, 주 행동 다음에 읽혀야 한다 |
| 보드 팀원 줄(이름 3개) | compress | `팀원 3명 · 초대 보냄 2` 한 줄 + `팀원 초대` | 이름을 다 늘어놓으면 카드가 첫 뷰포트 밖으로 밀린다 |
| 보드 열 3개 | replace | 열 전환 세그먼트(`할 일 1` · `진행 중 0` · `완료 0`) + 한 번에 열 하나 | 가로 스크롤 보드는 카드 제목이 잘린다. 건수는 세그먼트가 보여 준다 |
| 카드 끌어 옮기기 | replace | 카드를 눌러 task-detail에서 상태를 고른다 | 좁은 화면과 키보드에서 끌기는 믿을 수 없다 |

| permission | member가 `/settings` 직접 진입 | 403 화면: `이 화면을 볼 수 없습니다.` | 홈으로 가기 | 홈으로 돌아간다 |
| stale (초대 링크 만료) | 만료된 초대 링크로 진입 | `초대 링크가 만료되었습니다.` + 초대한 사람 이름 | 없음 — 초대한 사람에게 다시 요청 | owner가 members에서 `다시 보내기` |

## Performance Budget

- 첫 화면 필수 자산: HTML·CSS·앱 스크립트, 한글 폰트 1종(가변 폰트 1파일).
- 지연 가능한 자산: board·task-detail·members 화면 코드(1단계를 제출한 뒤 불러온다).
- 폰트 weight·이미지·영상·모션 예산: weight 2개(400·700), 이미지 0, 영상 0, 장식 모션 0, 상태 모션 2개 이하(단계 전환, 카드 등장).
- 저성능 기기와 느린 네트워크 폴백: 폰트가 늦으면 시스템 한글 폰트로 먼저 그린다. 프로젝트 수 확인이 늦어도 입력 칸을 빈 목록으로 잘못 그리지 않는다.

## Accessibility Contract

- 문서·랜드마크·헤딩 읽기 순서: 전역 이동(nav) → main → `h1` → 단계 표시(목록, 현재 단계 `aria-current="step"`) → 폼. 보드는 `h1` → 열 제목 `h2` → 카드.
- 키보드·포커스·Escape 동작: 프로젝트 0개인 홈은 입력 칸에 자동 포커스. Enter로 제출. 단계가 바뀌면 새 `h1`로 포커스를 옮긴다. 모바일 서랍과 task-detail 패널은 Escape로 닫고 연 버튼으로 포커스가 돌아간다.
- 레이블·오류 연결·상태 알림: 모든 입력에 보이는 라벨. 오류는 `aria-describedby`로 입력에 묶고 `role="alert"`. 보드 도착 알림은 `role="status"`.
- 대비·색 외 신호·터치 타깃: 본문 대비 4.5:1 이상. 현재 단계는 색과 굵기와 채운 번호로, 완료는 ✓로 알린다. 조작 요소 높이 44px 이상(와이어프레임의 `지우기`·`팀원 초대` 36px은 Phase 4에서 44px로 올린다).
- reduced-motion과 대체 경험: 단계 전환과 카드 등장은 `prefers-reduced-motion`이면 즉시 바뀐다. 카드 끌어 옮기기에는 task-detail의 상태 선택이 항상 대체 조작으로 있다.

## Prompt Contract

GOAL — 프로젝트 0개인 계정이 홈에서 바로 첫 프로젝트를 만들고 팀원 초대와 첫 할 일 배정을 거쳐 보드에 도착한다.
AUDIENCE — 방금 가입한 5~20명 팀의 리더(owner). 조급하고, 아니면 바로 닫는다. 보조: 초대받은 팀원(member).
TASK — 프로젝트 이름 입력 → 팀원 초대 → 첫 할 일 배정. 필수 입력은 이름 하나.
FLOW — home(0개) → setup-invite → setup-task → board. 2·3단계는 `나중에 하기`. 실패는 같은 칸에서 알리고 같은 버튼으로 다시 시도.
HEADER — 사이드바(제품·팀 이름, 홈, 프로젝트 이름들, 팀원, 설정) + 본문 `h1` + 보조 한 가지 + primary 1개. 환영 문구·설명 문단 없음.
MESSAGE — 제목 `첫 프로젝트 만들기`. 설명 문장 없음. 단계 이름 3개가 남은 일을 알린다.
FACTS — `Product Facts` 해당 없음. 화면의 이름·건수·상태는 `Scenario Facts`만 인용하고 표에 없는 날짜·숫자·상태를 지어내지 않는다.
CONTENT_INTEGRITY — 시나리오 데이터는 prototype. 60%·"5분" 수치와 고객 수·후기·배지는 화면에 싣지 않는다.
SECTION_ORDER — 제목 → 단계 표시 → 입력 칸 → primary. 2단계: 이메일 → 받을 사람 행 → primary·나중에 하기. 3단계: 할 일 → 담당자 → primary·나중에 하기. 보드: 상태 알림 → 프로젝트 이름 → 팀원 줄 → 열 3개.
CTA — `프로젝트 만들기` → `N명 초대하기` → `배정하기` → `할 일 추가`. 채운 버튼은 화면당 하나.
TRUST — 보내기 전에 받을 주소 행과 `지우기`, 버튼의 인원 수, 보낸 뒤 `초대 보냄`. 근거 없는 보안·실적 문구 금지.
ASSETS — 폰트만. Pretendard Variable은 로드와 라이선스 확인 전까지 시스템 한글 폰트.
LAYOUT — [layout](2026-11-11-layout-projectflow.md)의 블록 순서와 와이어프레임을 따른다. 좌측 사이드바 + 본문 1열, 입력 칸이 가장 크다.
RESPONSIVE — `Mobile Transformations` 표대로. 사이드바는 상단 바와 서랍, 보드 열은 세그먼트, 보드 머리 버튼은 글자 폭.
STATES — `States` 표 전체. 특히 owner·member의 프로젝트 0개 모습과 저장 실패.
PERFORMANCE — 이미지 0, 장식 모션 0, 상태 모션 2개 이하, 폰트 1파일.
ACCESSIBILITY — 입력 자동 포커스, Enter 제출, 단계 전환 시 `h1` 포커스, 오류는 입력에 연결, 끌기의 대체 조작.
PRESERVE — `DESIGN.md` 토큰, 역할 ID `owner`·`member`, 기존 이메일 링크 인증.
EXCLUDE — KPI 대시보드, 0으로 채운 통계, 빈 차트, 시간 추적, 리포트 내보내기, Slack 알림, 샘플 프로젝트, 환영 카드, 제품 투어, 조작법 설명 문구.
SUCCESS — `Page Goal`의 성공 조건 1~7.
