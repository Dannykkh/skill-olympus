# Design Brief — 플로우보드 첫 실행 경험

- 작성일: 2026-11-11
- Source Mode: product-derived (URL·스크린샷·영상·HTML 벤치마크 없음)
- 실행 범위: Phase 0~2 (2-5 와이어프레임 판단 게이트까지). Phase 3 이후는 실행하지 않음
- 상류 정본 폴더: `docs/plan/projectflow/`
- Product Design Gate: NOT APPLICABLE — `--plan-only`이고 런타임이 Codex가 아님

## 무엇을 만드는가

가입 직후 프로젝트가 0개인 계정이 처음 보는 홈과, 거기서 시작해 첫 프로젝트 → 팀원 초대 → 첫 할 일 배정 → 보드에 이르는 화면 흐름이다. 현재 구현(`src/pages/Home.tsx`)은 제목 "홈"과 "아직 프로젝트가 없습니다." 한 줄뿐이며, 이것이 P1이 말하는 빈 화면이다.

대표 화면은 **홈의 첫 실행 모습**으로 정했다. 요청이 화면을 지목하지 않았고, 성공 기준(첫 프로젝트 생성률)이 걸린 화면이 여기이기 때문이다.

## 누가 어떤 상황에서 쓰는가

상류의 사용자 구분(spec 이해관계자 표의 팀 리더·팀원)과 이름을 그대로 쓴다.

### 사람 카드 1 — 팀 리더 (역할 ID `owner`) · 핵심 사람

- 누구인가: 한서윤, 34세. 8명 규모 브랜드 디자인 스튜디오의 프로젝트 리드. 일정은 엑셀과 메신저로 관리해 왔고 오늘 처음 가입했다
- 처음 오는 이유와 마음: 새 프로젝트가 시작돼 도구를 바꿔 보려는 참이다. 막막하고, 시간을 오래 쓸 생각이 없다. 쓸 만한지 몇 분 안에 판단하려 한다
- 알고 싶은 것
  1. 지금 여기서 무엇부터 하면 되지? → 홈 첫 실행의 프로젝트 이름 입력과 주 행동
  2. 몇 단계나 남았지? → 단계 표시
  3. 만들면 무엇이 생기지? → 보드 미리보기
  4. 팀원은 어떻게 데려오지? → 2단계 팀원 초대, 이후에는 보드 머리와 팀원 화면
  5. 누가 무엇을 맡았는지 한눈에 보이나? → 보드
- 성공한 순간: 보드에 첫 할 일이 팀원 이름과 함께 놓인 것을 본 때
- 주로 쓰는 화면: 홈, 보드, 팀원

### 사람 카드 2 — 팀원 (역할 ID `member`)

- 누구인가: 오준호, 29세. 같은 스튜디오의 디자이너. 초대 메일의 링크로 처음 들어온다
- 처음 오는 이유와 마음: 리더가 불러서 왔다. 또 새 도구인가 싶어 귀찮고, 자기 일만 빨리 알고 싶다
- 알고 싶은 것
  1. 내가 맡은 일이 뭐지? → 홈의 내 할 일
  2. 어느 프로젝트의 일이고 누가 맡겼지? → 내 할 일 행의 프로젝트 이름·배정한 사람
  3. 다른 사람들은 무엇을 하고 있지? → 보드
- 성공한 순간: 맡은 할 일을 "진행 중"으로 옮긴 때
- 주로 쓰는 화면: 홈(내 할 일), 보드, 할 일 상세

핵심 사람은 **팀 리더**다. 성공 기준이 "가입 후 24시간 안에 첫 프로젝트를 만드는 계정 비율"이고, 팀원은 팀 리더가 초대해야만 생긴다.

## 최우선 과업과 완료 조건

- 과업: 첫 프로젝트를 만들고, 팀원을 초대하고, 첫 할 일을 배정한다 (spec 공유 전제)
- 완료 조건: 보드에 프로젝트 이름과 담당자가 있는 할 일 1건이 보인다
- 최소 완료: 프로젝트 생성까지. 성공 기준이 세는 것이 이것이므로 1단계에서 프로젝트를 바로 저장하고, 2·3단계는 건너뛸 수 있게 한다

## 망설이거나 불신하는 지점

| 지점 | 무엇이 불안한가 | 대응 |
|---|---|---|
| 홈 첫 진입 | 빈 화면이라 무엇을 할지 모름 (P1) | 첫 화면의 주인공을 프로젝트 이름 입력으로 둠 |
| 팀원 초대 | 내 이름으로 어떤 메일이 가는지 모름 | 버튼에 받는 사람 수를 적고, 메일에 담기는 것을 한 줄로 밝힘 |
| 첫 할 일 배정 | 아직 들어오지 않은 사람에게 맡겨도 되는지 모름 | 담당자 선택지에 "초대 대기"를 붙여 고를 수 있음을 보임 |
| 건너뛰기 | 나중에 다시 할 수 있는지 모름 | 초대는 보드 머리와 팀원 화면에 늘 있음 (P2) |

근거 없는 고객 수·후기·배지는 만들지 않는다. "가입 5분 안에 첫 보드"(interview 차별화)는 검증된 수치가 아니므로 화면에 시간으로 약속하지 않는다.

## 제약

- 기술: React 18 + Vite SPA, REST API, 인증은 이메일 링크 (spec 기존 환경). 새 의존성 없이 구현 가능한 구조만 쓴다
- 범위: 팀 성과 KPI 대시보드, 시간 추적, 리포트 내보내기, Slack 알림은 만들지 않는다
- 표현: `DESIGN.md` — 좌측 내비 + 본문 1열, 강조 버튼 1개, primary 색은 주 행동과 현재 위치에만
- 접근성: 키보드만으로 3단계를 끝낼 수 있어야 하고, 오류는 필드와 연결된 글로 알린다
- 기기: 데스크톱 업무 웹앱으로 판정했다(README "프로젝트 관리 웹앱"). 한국 사용자 대상 모바일 앱이 아니므로 `korean-mobile-app.md` 4~8절은 적용하지 않고, 좁은 화면은 반응형 변환으로 다룬다

## 관찰 가능한 성공 기준

1. 프로젝트 0개인 계정의 홈 첫 뷰포트(1280×800, 390×844)에 프로젝트 이름 입력과 "프로젝트 만들기"가 보인다
2. 이름 입력 → 버튼 한 번으로 프로젝트가 만들어지고 2단계로 넘어간다
3. 빈 이름·저장 실패에서 입력을 잃지 않고 같은 화면에서 다시 시도할 수 있다
4. 2·3단계를 건너뛰어도 보드에 도달한다
5. 홈에 KPI·차트·0으로 채운 숫자가 없다
6. 제품 지표: 가입 후 24시간 안에 첫 프로젝트를 만드는 계정 60% 이상 (spec, 현재 30%)

## 상류 제외 결정과의 충돌 점검

요청은 제외 항목(KPI 대시보드·시간 추적·리포트 내보내기)을 직접 지목하지 않는다. 홈은 anatomy `Dashboard` 계열이지만 핵심 사람이 현황을 확인하는 사람이 아니라 첫 프로젝트를 만들어야 하는 신규 사용자이므로 KPI 행을 두지 않고 `Dashboard`의 첫 실행 변형을 쓴다. 멈출 사유는 없다.

## 레퍼런스와 시장 관례

- 벤치마크: 없음. 구조 근거는 제품 세계의 실물인 칸반 보드(세 칸으로 나눈 판과 그 위의 카드)에서 가져왔다. 홈 첫 실행의 "보드 미리보기"가 그 판을 빈 채로 먼저 보여 준다. 색·재질·타이포의 근거 유도는 Phase 3에서 한다
- 시장 관례: NOT APPLICABLE — 한국 사용자 대상 모바일 앱이 아님

## 사용자에게 확인이 필요한 것

이 실행은 질문할 수 없어 권장안으로 진행했다. 결정 장부는 `2026-11-11-experience-projectflow.md`의 `## Open Decisions`다.

1. (scope) 프로젝트 이름 고치기·프로젝트 지우기를 MVP에 넣는가
2. (structure) 팀원(`member`)이 프로젝트를 만들 수 있는가, 팀원을 초대할 수 있는가
3. (structure) 초대를 아직 수락하지 않은 사람에게 할 일을 배정할 수 있는가
4. (structure) 가입할 때 이름·팀 이름을 받는가. 받지 않으면 사람을 무엇으로 표시하는가
5. 대표 화면을 홈 첫 실행으로, 기기를 데스크톱 우선으로 본 판정이 맞는가
