## 요청 해석 — "대시보드답게 채워줘"와 전략 문서의 충돌

요청을 문자 그대로 읽으면 KPI 타일·차트로 화면을 채우는 일이지만, 프로젝트 정본 셋이 이를 막습니다.

| 근거 | 원문 | 함의 |
|---|---|---|
| `docs/athena/projectflow.md` 삭제 권고 | "팀 성과 KPI 대시보드 — 프로젝트가 쌓이기 전에는 보여줄 데이터가 없고 초기 사용자 과업과 무관 — 복구 시점: 활성 팀 100개 이후" | 팀 성과 지표·차트는 넣지 않음 |
| `docs/plan/projectflow/interview.md` | "MVP 범위: … 제외 — 팀 성과 KPI 대시보드, 시간 추적, 리포트 내보내기", "첫 경험 완성도 vs 관리자용 분석 기능 → 첫 경험을 선택" | 첫 화면은 첫 경험을 위한 화면 |
| `docs/plan/projectflow/spec.md` P1 | "가입 직후 계정에는 프로젝트가 0개라 빈 화면에서 무엇을 할지 몰라 이탈 — 가입자 70%가 첫 프로젝트 전에 이탈" | "휑함"의 실제 원인은 데이터 부족이 아니라 **다음 행동이 없음** |

**채택한 해석**: "대시보드답게"를 *지표 진열*이 아니라 *내 일과 팀의 현재 상태를 한눈에 보고 바로 다음 행동을 고르는 화면*으로 읽습니다. 홈은 두 상태를 1급으로 설계합니다.

1. **프로젝트 0개 (새 owner)** — "첫 보드까지 3단계" 진행판이 주인공. spec의 목표 문장(첫 프로젝트 → 팀원 초대 → 첫 할 일 배정)을 그대로 단계로 씀. 팀원 초대를 홈에 꺼내 P2("초대 경로가 설정 메뉴 깊숙이")를 함께 해결. 아래에는 나중에 채워질 대시보드 구역(내 할 일·프로젝트·팀)을 점선 빈 칸("아직 없음")로 보여 줌.
2. **프로젝트 있음** — 같은 구역이 사용자 자신의 데이터로 채워짐: 내 할 일 현황(마감 지남·오늘 마감·이번 주) → 마감 순 내 할 일 → 프로젝트 목록 → 팀.

넣지 않는 것: 팀 성과 KPI, 완료율·속도 차트, 팀원 비교, 시간 추적, 리포트 내보내기, 근거 없는 수치·후기·배지.
이 해석은 사용자 확인이 필요한 결정입니다(아래 "미해결 질문" 1번). 사용자가 팀 성과 KPI를 명시적으로 원하면 athena 결정을 뒤집는 일이므로 별도 확인 후 다시 설계합니다.

## 1-1. 디자인 브리프

### 무엇을 만드는가
플로우보드(5~20명 소규모 팀용 프로젝트 관리 웹앱, React 18 + Vite SPA)의 로그인 후 첫 화면 `홈`. 현재 `src/pages/Home.tsx`는 제목과 빈 상태 한 줄뿐입니다.

### 누가 어떤 상황에서 쓰는가
spec.md 시스템 역할을 그대로 씁니다(새 역할명을 만들지 않음).

| 역할 ID | 표시명 | 홈에 오는 상황 | 머릿속 질문 |
|---|---|---|---|
| `owner` | 팀 소유자 | 이메일 링크로 가입한 직후, 프로젝트 0개. 팀을 만들어 보려고 왔지만 무엇부터 할지 모름 | "뭘 먼저 하지?", "팀원은 어떻게 부르지?", "얼마나 걸리지?" |
| `owner` (사용 중) | 팀 소유자 | 아침에 열어 오늘 처리할 일과 밀린 일을 확인 | "오늘 내가 할 일은?", "마감 놓친 게 있나?", "프로젝트들은 굴러가나?" |
| `member` | 팀원 | 초대 메일 링크로 처음 들어옴. 배정된 할 일이 아직 없을 수 있음 | "내가 할 일이 있나?", "어디서 보지?" |

핵심 사람: **프로젝트 0개인 새 owner**. spec 성공 기준(가입 24시간 내 첫 프로젝트 생성 30% → 60%)과 P1 이탈이 이 사람에게서 일어나기 때문입니다.

### 최우선 과업과 완료 조건
- 새 owner: 홈에서 프로젝트 생성 마법사로 들어가 첫 프로젝트를 만든다. 완료 = 새 프로젝트 보드가 열림. 이어서 팀원 1명 이상 초대, 첫 할 일 배정.
- 사용 중 owner·member: 마감이 지난 일과 오늘 마감인 일을 찾아 처리한다. 완료 = 할 일을 완료로 표시하거나 해당 보드의 할 일 상세로 이동.

### 망설이거나 불신하는 지점
- 빈 화면에서 다음 행동을 찾지 못함 (P1).
- 팀원 초대가 설정 깊숙이 있어 혼자 쓰다 그만둠 (P2).
- 초대받는 사람에게 가입·비밀번호 부담을 줄까 걱정 → spec "인증은 이메일 링크"를 근거로 안내 가능.
- 숫자가 보이면 그 숫자를 믿을 수 있는가 → 홈의 숫자는 본인에게 배정된 할 일에서 센 값만, 누르면 그 할 일 목록이 걸러져 검증 가능해야 함.

### 제약
- 기술: React 18 + Vite SPA, REST API, 인증은 이메일 링크, 이메일은 외부 API(초대), Slack 연동 제외.
- 브랜드·시각: `DESIGN.md` 토큰(Primary #2F5D50는 주 행동·현재 위치에만, Accent #C8553D는 마감 경고에만, Pretendard Variable, rounded 8px, spacing 16px). 이번 단계에서는 색·폰트를 적용하지 않음(와이어프레임은 잉크 3단계 그레이스케일).
- 구조: `DESIGN.md` "좌측 내비 + 본문 1열, 밀도 중간" — 본문을 2단으로 쪼개지 않음.
- 콘텐츠: 한국어 UI. 근거 없는 고객 수치·후기·배지 금지. 팀 성과 KPI 금지(athena).
- 접근성: 랜드마크·헤딩 순서, 키보드, 색 외 신호(마감 지남은 글자+기호), 상태 알림.

### 관찰 가능한 성공 기준
- 프로젝트 0개 owner의 첫 뷰포트(1280×800, 390×844)에 주 행동 "첫 프로젝트 만들기"가 하나만 솔리드로 보이고, 한 번 눌러 마법사로 간다.
- 팀원 초대를 홈에서 화면 이동 없이 시작할 수 있다.
- 홈의 모든 숫자는 사용자 본인 데이터에서 센 값이며, 숫자를 누르면 해당 할 일만 남는다.
- member가 처음 들어왔을 때도 빈 화면이 아니라 다음에 갈 곳(프로젝트 보드)이 있다.
- 제품 지표(가입 24시간 내 첫 프로젝트 생성률 30% → 60%)는 spec의 목표이며 이 디자인 단계에서 측정하지 않음.

## 미해결 질문 (사용자 확인 필요)

1. "대시보드답게"가 팀 성과 KPI·차트를 뜻한다면, athena·인터뷰에서 MVP 제외로 정한 결정을 뒤집는 것인지. 이번 설계는 "내 할 일·프로젝트·팀 현황 + 첫 행동"으로 해석함.
2. `member`가 프로젝트를 만들거나 팀원을 초대할 수 있는지. spec은 owner의 주요 업무에만 적고 member 금지 행동에는 적지 않음 → 초안은 member에게 둘 다 `숨김`(가설).
3. 프로젝트를 만들기 전에 팀원을 초대할 수 있게 둘지. 초안은 허용(P2 대응)하되, 그 경우 초대받은 member가 프로젝트 없는 팀에 들어오는 상태를 따로 설계함.
4. member는 팀의 모든 프로젝트를 보는지, 참여한 프로젝트만 보는지.
