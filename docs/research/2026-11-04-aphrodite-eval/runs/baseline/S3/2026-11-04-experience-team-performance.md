## Page Goal

- 사용자가 이 화면에서 달성할 결과: 팀이 최근 기한 안에 일을 끝내고 있는지 판단하고, 지금 밀린 할 일을 열어 조치한다.
- 제품이 얻어야 하는 결과: owner가 주기적으로 돌아와 팀 운영을 이 도구 안에서 확인한다. 데이터가 없는 새 팀은 이 화면에서 MVP 활성화 단계(팀원 초대·할 일 배정)로 돌아간다.
- 관찰 가능한 성공 조건: 첫 진입 5초 안에 완료 수·기한 내 완료율·밀린 수와 변화 방향을 말함 / `기한 지난 할 일 보기` → 할 일 열기가 2번 조작 이내 / 기록 없음 상태에서 다음 단계 버튼 클릭

## Audience and Tasks

- 주요 사용자와 사용 상황: `owner`(팀 소유자), 5~20명 팀. 주간 회의 전 데스크톱에서 확인, 이동 중 휴대폰으로 밀린 일만 확인
- 최우선 과업: 지금 밀린 할 일로 이동(T2). 그 판단 근거로 완료 수·기한 내 완료율의 변화(T1), 프로젝트별 비교(T3)
- 시작 조건과 완료 조건: 좌측 내비 `팀 성과` 진입 → 서랍에서 할 일 선택 시 해당 프로젝트 보드에서 그 할 일이 열림
- 주요 불안·마찰·실패 가능성: 숫자의 정의·기준 시각을 모름 / 비교 기준이 없음 / 표본이 작은데 퍼센트가 큼 / 집계 실패 / 새 팀은 데이터 자체가 없음 / 개인 감시 도구로 읽힘

## Core Message

- 핵심 약속: 우리 팀이 일을 제때 끝내고 있는지, 지금 어디가 밀렸는지 한 화면에서 안다.
- 설명: 최근 4주(진행 중인 이번 주 제외)를 이전 4주와 비교한 완료 수·기한 내 완료율, 지금 기준 기한 지난 할 일.
- 증거: 분모(`마감일 있는 완료 43건 중 37건`), 비교 기준값(`이전 4주 38건`), 주별 막대(이전 4주·최근 4주가 같은 그래프에 있음), 집계 시각(`12분 전 갱신 · 11월 4일 09:12 기준`), `지표 정의 보기`
- 사용자가 다음에 이해해야 할 것: 밀린 6건이 무엇이고 누구 담당인지 → 서랍

## Section Order

1. 페이지 제목 + 한 줄 설명: "이 화면은 무엇을 위한 곳인가"
2. 기간 선택 + 기간 범위 + 집계 시각·`지표 정의 보기`: "언제, 무엇을 기준으로 센 숫자인가" — 숫자보다 먼저 와야 숫자를 믿음
3. KPI 3장(완료 → 기한 내 완료율 → 지금 기한 지난 할 일): "잘 끝내나 → 기한을 지키나 → 지금 손볼 곳은" 순서. 마지막 카드만 행동(`기한 지난 할 일 보기`)을 가짐
4. 주별 완료한 할 일(추세): "좋아지는 중인가" — KPI 변화값의 근거(이전 4주·최근 4주 막대)를 바로 아래에서 확인
5. 프로젝트별 표: "어느 프로젝트 때문인가" — 기한 지난 할 일 많은 순, 행에서 보드로 이동

## CTA Strategy

- Primary: `기한 지난 할 일 보기 →` — 기한 지난 할 일이 1건 이상일 때 KPI 3번째 카드 안에 1회. 목적지: 같은 화면 오른쪽 서랍(모바일은 전체 화면 시트). 0건이면 버튼 대신 `기한 지난 할 일 없음` 문장
- 기록 없음 상태의 Primary: 아직 끝나지 않은 첫 단계 1개만 solid — `팀원 초대하기`(설정의 팀원 초대 구역으로 직접 이동) 또는 `첫 프로젝트 만들기`(마법사). 나머지 단계는 텍스트
- Secondary: 표 행의 `보드 열기 →`(텍스트 링크, 행 전체 클릭 가능), `표로 보기`, `지표 정의 보기`, 집계 실패 시 `다시 시도`(outline)
- 반복 규칙: solid 버튼은 화면에 항상 1개 이하. 서랍 안에는 solid 버튼 없음(항목 자체가 링크)
- 완료·실패 피드백: 서랍 열림 시 제목에 포커스 + `기한 지난 할 일 6건` 낭독. 보드 이동 실패(할 일이 이미 삭제·완료됨) 시 서랍 안에 "이미 완료되었거나 삭제된 할 일입니다. 목록을 새로 고쳤습니다." 표시 후 목록 갱신

## Trust Strategy

- 사용자가 불안을 느끼는 지점: 숫자를 처음 볼 때, 회의에서 숫자를 인용할 때, 퍼센트가 갑자기 변할 때
- 그 직전에 제시할 근거: KPI 위 기간 범위(`10월 5일 – 11월 1일 · 진행 중인 이번 주 제외`)와 집계 시각, 카드 안 분모·이전 값, 차트의 이전/최근 구간 표시, `지표 정의 보기`
- 출처·날짜·검증 가능성: 모든 값은 팀 자신의 할 일 데이터. 집계 시각을 항상 표시. 실패 시 마지막 성공 시각을 굵게
- 근거가 없을 때 생략할 요소: 이전 기간 데이터가 없으면 증감 대신 `비교할 이전 기간 없음`. 완료된 주가 2주 미만이면 추세 대신 안내. 완료 10건 미만이면 `표본 적음`. 팀원 개인 순위·업계 평균·목표 대비 같은 외부 기준은 근거가 없으므로 넣지 않음

## Accessibility Contract

- 문서·랜드마크·헤딩 읽기 순서: `nav`(좌측 내비) → `main` → h1 `팀 성과` → 기간·집계 시각 → h2 KPI(시각적 제목 없음, `aria-label="요약 지표"`) → h2 `주별 완료한 할 일` → h2 `프로젝트별 · 최근 4주`
- 키보드·포커스·Escape 동작: 기간 선택은 라디오 그룹(화살표 이동). 서랍은 열릴 때 제목으로 포커스, Tab 순환을 서랍 안에 가두고 Escape·`닫기`로 닫힌 뒤 `기한 지난 할 일 보기` 버튼으로 포커스 복귀
- 레이블·오류 연결·상태 알림: 증감은 `+9건 · 이전 4주 38건`처럼 문장. 기간 변경·집계 실패·갱신 성공은 `aria-live="polite"`. 차트는 `표로 보기`로 같은 값의 표를 제공하고 SVG에 요약 `aria-label`. 표 행 링크 이름은 `{프로젝트명} 보드 열기`
- 대비·색 외 신호·터치 타깃: 기한 넘김은 해치 패턴, 마감일 없음은 외곽선, 이번 주는 점선 — 색 없이 구분(와이어프레임에서 확인). 모바일 버튼·목록 행 높이 44px 이상
- reduced-motion과 대체 경험: 서랍은 이동 없이 즉시 표시, skeleton 반짝임 정지

## Prompt Contract

GOAL — owner가 팀이 기한 안에 일을 끝내는지 판단하고 밀린 할 일을 열게 한다
AUDIENCE — 5~20명 팀의 owner, 주간 점검, 데스크톱 우선·모바일 확인
TASK — 기한 지난 할 일 보기 → 서랍에서 할 일 선택 → 보드
FLOW — 진입 → 기간·기준 확인 → KPI → 추세 근거 → 프로젝트 비교 → 서랍/보드. 실패: 집계 실패 배너 → 다시 시도
HEADER — 좌측 내비(팀 성과 활성) + h1 `팀 성과` + 한 줄 설명
MESSAGE — 우리 팀이 제때 끝내는지, 지금 어디가 밀렸는지
FACTS — 팀 자신의 할 일 데이터만. 외부 기준·순위 없음
CONTENT_INTEGRITY — 지표 정의는 hypothesis, 와이어프레임 숫자는 prototype(layout 샘플 표)
SECTION_ORDER — 제목 → 기간·집계 시각 → KPI 3 → 주별 추세 → 프로젝트별 표
CTA — solid 1개: `기한 지난 할 일 보기 →`(기록 없음이면 다음 활성화 단계 1개)
TRUST — 기간 범위·집계 시각·분모·이전 값·지표 정의를 숫자 가까이에
ASSETS — 없음
LAYOUT — layout 문서의 Layout Blueprint(좌측 내비 + 본문 1열, KPI 3열, 차트·표 전체 폭)
RESPONSIVE — 위 Mobile Transformations
STATES — 위 States 표(A 기록 없음·B 쌓이는 중·C 실패·D 권한·서랍)
PERFORMANCE — 장식 효과 0, 상태 모션만, 집계 요청 1회
ACCESSIBILITY — 위 Accessibility Contract
PRESERVE — 기존 좌측 내비 구조와 `DESIGN.md` 토큰, 다른 화면
EXCLUDE — 팀원 개인 순위, 시간 추적, 리포트 내보내기, 카운트업, 배경 전체 색 신호
SUCCESS — 5초 안에 세 숫자와 변화 방향을 말함 / 2번 조작으로 밀린 할 일 열기 / 새 팀이 빈 차트 대신 다음 단계 실행

## Success Checks

- 첫 5초 안에 핵심 약속과 주 행동을 설명할 수 있는가?
- 화면의 사실·수치·후기·브랜드 자산이 출처와 상태를 가지며, unverified 항목을 사실처럼 보이지 않는가?
- 주요 과업을 막는 상태·정보·행동 누락이 없는가?
- 모바일이 데스크톱 축소판이 아니라 우선순위에 맞게 재구성됐는가?
- 아름다움, 접근성, 성능 중 하나를 다른 하나의 희생으로 얻지 않았는가?
