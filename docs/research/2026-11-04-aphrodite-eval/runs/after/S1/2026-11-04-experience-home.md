## Page Goal

- 사용자가 이 화면에서 달성할 결과: 팀 리더가 지금 할 다음 한 단계(첫 프로젝트 만들기)를 바로 시작하고, 남은 두 단계(팀원 초대·첫 할 일 배정)를 안다.
- 제품이 얻어야 하는 결과: 가입 당일 첫 프로젝트 생성, 이어서 팀원 초대(spec 공유 전제 목표).
- 관찰 가능한 성공 조건: 가입 후 24시간 안 첫 프로젝트 생성 계정 비율 60% 이상(현재 30%). 화면 수준 — 색을 뺀 와이어프레임에서도 primary 1개가 5초 안에 식별되고, 홈에서 초대 창까지 설정 메뉴 없이 1번에 닿는다.

## Audience and Tasks

- 주요 사용자와 사용 상황: 5~20명 소규모 팀의 팀 리더가 이메일 링크로 가입·로그인한 직후(핵심 사람). 초대받은 팀원이 초대 메일 링크로 처음 들어온 직후.
- 최우선 과업: 첫 프로젝트 만들기 → 팀원 초대 → 첫 할 일 배정.
- 시작 조건과 완료 조건: 시작 = 프로젝트 0개 계정의 홈. 완료 = 시작하기 3단계 모두 완료(첫 할 일이 팀원에게 배정됨). 이번 화면의 1차 완료 = 프로젝트 1개 생성.
- 주요 불안·마찰·실패 가능성: 무엇부터 할지 모름(P1), 초대 경로를 못 찾음(P2), 초대 메일 전송 실패·미수락, 홈 데이터 로드 실패.

사람 카드(요약, 전문은 brief 3절):

| 사람 | 상황·마음 | 알고 싶은 것 → 답이 보이는 자리 | 성공한 순간 |
|---|---|---|---|
| 팀 리더 박지수(핵심) | 가입 직후, 막막함 + 팀이 쓸지 의심 | 지금 뭘 하지 → 다음 한 단계 카드 / 얼마나 남았지 → 시작하기 3단계 / 팀원은 어디서 부르지 → 2단계 행·먼저 초대하기 / 팀원이 들어왔나 → 팀원 구역 | 초대한 팀원이 수락하고 첫 할 일이 배정됨 |
| 팀원 이도윤 | 초대 메일로 첫 진입, 반쯤 의무감 | 내가 뭘 해야 하지 → 내 할 일(주인공) / 언제까지 → 마감 / 누가 불렀지 → 제목 줄 | 배정된 할 일을 완료로 옮김 |

여정표(요약, 전문은 brief 4절):

| 시기 | 팀 리더: 할 일 / 궁금 / 막힘 | 팀원: 할 일 / 궁금 / 막힘 |
|---|---|---|
| 사용 전 | 로그인 / 뭐부터? / 다음 행동 없는 빈 홈 → empty(첫 실행) | 초대 링크 클릭 / 무슨 팀? / 링크 만료 → error(초대 만료, 홈 밖 초대 수락 화면) |
| 사용 중 | 프로젝트·초대 / 메일이 갔나? / 전송 실패 → error(초대 실패), 미수락 → stale | 할 일 확인 / 내 할 일? / 배정 0건 → empty(팀원 첫 실행) |
| 사용 후 | 재방문 / 누가 뭘 하나? / 초대 만료 → stale | 할 일 완료 / 다음은? / 할 일 0건 → empty |

## Header and Navigation

- 브랜드·현재 위치·전역 이동·주 행동의 순서: 로고(플로우보드) → 팀 이름(한빛 마케팅팀, 팀 전환) → 전역 내비(홈 활성) → 사용자(박지수 · 팀 소유자). 주 행동은 헤더가 아니라 본문 첫 카드에 1개.
- 데스크톱 내비게이션: 좌측 사이드바 232px, 항목 4개(홈 · 프로젝트 · 팀원 · 설정), 활성 1개만 배경 강조. 설정은 팀 소유자만.
- 모바일 대체 구조: 상단 바(팀 이름 ▼ + 아바타) + 하단 탭 바(홈 · 프로젝트 · 팀원 · 설정, 팀원은 3개).

## Core Message

- 핵심 약속: 세 단계를 마치면 팀원과 같은 보드에서 할 일을 나눌 수 있다.
- 설명: 지금 할 단계 하나(첫 프로젝트 만들기)와 남은 단계 둘(팀원 초대, 첫 할 일 배정).
- 증거: 만들면 열리는 보드의 모양(할 일 · 진행 중 · 완료 열), 이미 팀에 있는 나(박지수 · 팀 소유자). 고객 수치·후기는 쓰지 않는다.
- 사용자가 다음에 이해해야 할 것: 프로젝트를 만든 뒤 팀원을 부르고 할 일을 배정하면, 비어 있는 구역(내 할 일 · 프로젝트 · 팀원)이 실제 내용으로 채워진다.

## Section Order

1. 페이지 타이틀 "한빛 마케팅팀 시작하기" + 한 줄 약속: 여기가 어디고 이 화면이 무엇을 하게 하는가
2. 다음 한 단계 카드(지금 할 단계 · 1/3): "지금 뭘 하지?" — 앞에서 약속한 세 단계 중 첫 번째를 바로 시작
3. 시작하기 3단계: "얼마나 남았지? 팀원은 어디서 부르지?" — 카드 다음에 와야 지금 할 일이 가려지지 않음
4. 데이터가 생기면 채워지는 구역(내 할 일 · 프로젝트 · 팀원): "이 화면은 앞으로 어떻게 쓰이나, 팀원이 들어왔나" — 단계를 마칠수록 실제 내용으로 바뀜

## CTA Strategy

- Primary: "프로젝트 만들기" → project-wizard. 첫 실행 상태에서 첫 뷰포트의 다음 한 단계 카드에 1회. 단계가 넘어가면 같은 자리의 문구와 목적지가 바뀐다 — 2단계 "팀원 초대하기" → invite-dialog, 3단계 "첫 할 일 배정하기" → board의 task-form. 시작하기 완료 뒤에는 "보드 열기"(잠정, Open Decisions).
- Secondary: "먼저 초대하기"(outline) → invite-dialog. 2단계가 남은 단계일 때만 2단계 행에 표시(P2 — 설정 메뉴 경유 제거).
- 반복 규칙: 화면에 primary는 1개. 빈 구역 칸에는 버튼을 두지 않는다. 같은 위계의 솔리드 버튼 2개 금지.
- 완료·실패 피드백: 단계 완료 → 홈 상단 확인 문구 1줄("'11월 신제품 런칭' 프로젝트를 만들었어요.") + 다음 단계가 지금 할 단계로. 초대 실패 → invite-dialog 안에서 실패한 주소 옆에 이유, 입력 유지. 홈 로드 실패 → "다시 시도".

## Trust Strategy

- 사용자가 불안을 느끼는 지점: 팀원이 정말 쓸까, 초대 메일이 갔나, 마법사가 길까.
- 그 직전에 제시할 근거: 단계 수(3)를 처음부터 보여 줌 / 만들면 무엇이 열리는지(보드 모양) / 초대 결과를 확인할 장소(팀원 구역: "초대한 팀원과 수락 여부가 여기에 보입니다").
- 출처·날짜·검증 가능성: 화면이 보여 주는 것은 이 계정의 실제 상태(팀 이름, 나, 초대 상태)뿐이다.
- 근거가 없을 때 생략할 요소: 고객 수, 후기, 로고 띠, "5분이면 끝" 같은 시간 약속, 보안 배지.

## Desktop Structure

- 기준 뷰포트: 1280×800
- 첫 뷰포트: 사이드바 + 페이지 타이틀 + 다음 한 단계 카드(2/3) · 시작하기 3단계(1/3) + 채워질 구역(내 할 일 2/3 · 프로젝트/팀원 1/3 세로). 스크롤 없이 모두 보인다.
- 그리드·pane·콘텐츠 위계: 본문 폭 936px, 2/3:1/3 비율을 두 줄에서 반복. 위계는 카드 헤딩(28px) > 페이지 타이틀(22px) > 구역 제목(15px). 강조는 다음 한 단계 카드 1개(굵은 테두리 + solid 버튼).
- 스크롤 흐름과 밀도 변화: 첫 실행에는 스크롤 없음. 데이터 상태에서는 내 할 일 구역이 길어지며 그 구역 안에서만 늘어난다.

## Performance Budget

- 첫 화면 필수 자산: 텍스트, 단색 도형, 내비 아이콘 4개, 폰트 1패밀리(DESIGN.md Pretendard Variable). 이미지·영상 0.
- 지연 가능한 자산: 채워질 구역의 데이터(단계 정보보다 뒤에 와도 됨), 데스크톱 보드 미리보기.
- 폰트 weight·이미지·영상·모션 예산: 400·700 두 굵기, 이미지 0, 영상 0, 모션은 단계 완료 확인 문구 등장 1개(150~300ms).
- 저성능 기기와 느린 네트워크 폴백: 단계 정보가 먼저 오면 카드부터 그린다. 모션 없이 즉시 표시.

## Accessibility Contract

- 문서·랜드마크·헤딩 읽기 순서: nav(사이드바·탭 바) → main. h1 페이지 타이틀 → h2 지금 할 단계 카드 제목 → h2 시작하기 3단계(순서 목록, 현재 단계에 `aria-current="step"`) → h2 내 할 일 · 프로젝트 · 팀원.
- 키보드·포커스·Escape 동작: Tab 순서 = 내비 → primary → 먼저 초대하기 → 구역. invite-dialog는 포커스를 가두고 Escape로 닫으며 연 버튼으로 포커스를 돌린다.
- 레이블·오류 연결·상태 알림: 단계 완료 확인 문구는 `role="status"`, 홈 로드 실패는 `role="alert"`, loading 중 main에 `aria-busy="true"`. 초대 주소 오류는 `aria-describedby`로 입력과 연결.
- 대비·색 외 신호·터치 타깃: 현재 단계는 채운 원 + "지금 할 단계" 글자, 완료는 ✓ + "완료" 글자. 색만으로 구분하지 않는다. 터치 타깃 44px 이상(모바일 "먼저 초대하기"는 보이는 높이 36px에 누르는 영역 44px).
- reduced-motion과 대체 경험: 확인 문구 등장 모션을 생략하고 즉시 표시.

## Prompt Contract

GOAL — 프로젝트 0개 계정의 홈을 "다음 한 단계"가 주인공인 첫 실행 화면으로 바꾼다. 팀 리더가 첫 프로젝트를 바로 만들고 남은 두 단계를 안다.
AUDIENCE — 핵심 사람: 가입 직후 막막한 팀 리더(박지수). 두 번째: 초대받아 처음 들어온 팀원(이도윤).
TASK — 프로젝트 만들기 → 팀원 초대 → 첫 할 일 배정. 이 화면의 1차 완료는 프로젝트 1개 생성.
FLOW — home → project-wizard → project-created → invite-dialog → invite-sent → board의 task-form → task-assigned → home(시작하기 완료). 초대 실패는 invite-dialog 안에서 회복.
HEADER — 좌측 사이드바: 로고 → 팀 이름 → 홈·프로젝트·팀원·설정(활성 1) → 사용자. 헤더에 CTA 없음.
MESSAGE — "한빛 마케팅팀 시작하기" / "세 단계를 마치면 팀원과 같은 보드에서 할 일을 나눌 수 있어요." / 카드 "첫 프로젝트를 만드세요".
FACTS — Scenario Facts 표만 인용. 표에 없는 날짜·숫자·상태를 지어내지 말 것.
CONTENT_INTEGRITY — 시간 약속("5분")·내부 지표·후기·고객 수 금지. Scenario Facts는 prototype.
SECTION_ORDER — 타이틀 → 다음 한 단계 카드 → 시작하기 3단계 → 데이터가 생기면 채워지는 구역(내 할 일 · 프로젝트 · 팀원).
CTA — primary 1개("프로젝트 만들기", 단계에 따라 문구 교체) + outline 1개("먼저 초대하기", 2단계가 남았을 때만). 빈 구역에 버튼 없음.
TRUST — 단계 수, 만들면 열리는 보드 모양, 초대 결과를 볼 자리. 근거 없는 배지·수치 생략.
ASSETS — 외부 이미지 없음. 폰트는 DESIGN.md.
LAYOUT — 데스크톱: 사이드바 232 + 본문 936, 2/3:1/3 두 줄 반복. 강조는 다음 한 단계 카드 1개. layout 파일의 블록 표와 SVG가 기준.
RESPONSIVE — Mobile Transformations 표대로: 사이드바→하단 탭, 보드 미리보기 remove, 3단계 reorder+compress, 구역 collapse.
STATES — loading(회색 자리) · empty(팀 리더/팀원) · error(로드 실패/초대 실패) · success(단계 완료/시작하기 완료) · permission(member) · stale(초대 대기).
PERFORMANCE — 이미지·영상 0, 폰트 1패밀리 2굵기, 모션 1개.
ACCESSIBILITY — Accessibility Contract 그대로. 현재 단계는 색 외 신호로도 구분.
PRESERVE — DESIGN.md 토큰(primary는 주 행동·현재 위치, accent는 경고만), 좌측 내비 + 본문 1열 원칙, 기존 React SPA 구조.
EXCLUDE — 팀 성과 KPI 카드·차트(scope 결정 대기), 시간 추적, 리포트 내보내기, Slack 알림 유도, 샘플 데이터 채우기.
SUCCESS — 색을 빼도 primary 1개가 5초 안에 보임 / 홈 → 초대 창 1번 / member 홈에 갈 곳이 있음 / Scenario Facts와 모든 문구 일치.

## Success Checks

- 첫 5초 안에 핵심 약속과 주 행동을 설명할 수 있는가? — 와이어프레임 관찰: 카드 헤딩 "첫 프로젝트를 만드세요"와 solid 버튼이 가장 먼저 읽힘(layout 5절).
- 화면의 사실·수치·후기·브랜드 자산이 출처와 상태를 가지며, unverified 항목을 사실처럼 보이지 않는가? — 화면에 수치 주장 없음. Scenario Facts만 사용.
- 주요 과업을 막는 상태·정보·행동 누락이 없는가? — States 표와 states SVG (a)~(e). 초대 실패는 invite-dialog 설계 때 확인.
- 모바일이 데스크톱 축소판이 아니라 우선순위에 맞게 재구성됐는가? — Mobile Transformations 9행.
- 아름다움, 접근성, 성능 중 하나를 다른 하나의 희생으로 얻지 않았는가? — 아름다움은 Phase 3 이후 실제 렌더로 판정(이번 범위 밖).
