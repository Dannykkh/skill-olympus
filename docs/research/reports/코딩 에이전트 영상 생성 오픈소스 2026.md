# 진입점은 지키고 세 경로를 고치는 video-maker 현대화

video-maker는 현대화해야 합니다. 다만 전면 개편이 아니라 선택적 흡수가 맞습니다. 흡수할 것은 세 가지입니다. 첫째, **한국어 TTS·자막 기본값을 교정**합니다. Kokoro에는 한국어 음성이 없고, Typecast는 단어와 문자 타임스탬프를 초 단위로 함께 준다는 사실이 확인됐습니다. 둘째, **내레이션 없는 모션 단편용 빠른 경로**를 둡니다. 셋째, **앱 홍보영상용 참조 흐름**을 들이고, 지금 계약에 없는 **Capture(실제 화면 확보) 단계**를 더합니다. 반대로 진입점은 그대로 두고, HyperFrames 번들 갱신은 사용자가 결정할 작업으로 남기며, Claude Motion은 기다립니다. 2026년 8~10월 GitHub 지형을 보면 렌더러는 **HyperFrames(65,513★)와 Remotion(64,642★) 양강**으로 굳었고, HyperFrames는 59일 동안 별을 +23,912개 얻어 Remotion(+7,773)의 약 3배를 기록하며 10월 중 별 수에서 Remotion을 앞질렀습니다. 그 위에 스킬과 파이프라인이 폭발했습니다. 가장 큰 큐레이션 목록에 실린 304개 중 **절반이 2026-08-01 이후 생성**됐습니다. 앱 홍보영상 도구는 모션 런치 필름(brag 16,385★, video-shotcraft 12,231★)과 실제 앱을 조작해 찍는 데모(aidemo, cursorcam 등, 대부분 100★ 미만) 두 갈래로 나뉩니다. 판단을 가르는 근거는 2026-10-11 블라인드 실측입니다. **스킬 16개와 스킬 없는 Claude Code가 모두 15초 프로모 검사 4개를 통과**했고, HyperFrames 경로가 23.5분으로 가장 느렸습니다. 스킬의 가치는 "렌더할 수 있느냐"가 아니라 룩, 사운드, 측정 가능한 품질 검사에 있습니다. 따라서 video-maker는 무거운 워크플로를 통째로 들이지 말고 **단계 구성과 검사 방법만** 가져와야 합니다.

> 측정 기준: 별 수, 생성일, 마지막 push(최근 커밋 대용), 라이선스는 2026-10-17 `gh api`로 측정했습니다. GitHub stargazers 타임스탬프 API가 이날 404를 반환해 과거 별 수는 Wayback Machine에 보관된 GitHub 페이지와 awesome-claude-video-skills 커밋 이력의 스냅숏(제3자 크롤 값)으로 대신했습니다. 날짜 구간이 불규칙하므로 증가량은 근사치입니다. 노트에 근거가 없는 판단에는 "(추론)"을 붙였습니다.

## 렌더러는 양강으로 굳었고 HyperFrames가 10월에 Remotion을 추월했습니다

코드로 영상을 렌더하는 프레임워크 가운데 **공식 에이전트 스킬 번들을 운영하는 곳은 HyperFrames와 Remotion 둘뿐**입니다. 두 엔진은 렌더 방식이 같습니다. headless Chrome에서 프레임마다 seek하고 FFmpeg로 인코딩합니다. 차이는 정본 형식입니다. HyperFrames는 빌드 없이 재생되는 HTML을 쓰고, GSAP·CSS·Lottie·Three.js 등을 어댑터로 붙입니다([HyperFrames README](https://github.com/heygen-com/hyperframes/blob/main/README.md)). Remotion은 번들러가 필요한 React 컴포넌트를 씁니다. 스킬 구조도 결이 다릅니다. HyperFrames의 공개 스킬 21개는 **라우터 1개, 입력 유형별 완결 워크플로 10개**(product-launch-video, pr-to-video, motion-graphics 등), **도메인 스킬 10개**로 이뤄지며, 라우터가 필요할 때 워크플로를 설치합니다([skills 디렉터리](https://github.com/heygen-com/hyperframes/tree/main/skills)). Remotion의 12개 스킬은 markup, render, captions, maps 같은 API 영역별 지식이고, "PR을 영상으로" 같은 완결 산출물 절차는 없습니다([remotion-dev/skills](https://github.com/remotion-dev/skills/blob/main/README.md)).

연동 표준도 바뀌었습니다. Remotion은 호스티드 MCP를 deprecated로 돌리고 `/remotion-docs` 스킬로 옮겼습니다. 사유로는 문서 최신성 부족, 토큰 비용, 에이전트가 MCP를 안정적으로 호출하지 않는다는 점을 들었고, MCP 종료를 **"no earlier than August 31, 2026"**으로 예고했습니다(10-17 현재 가동 여부는 미확인)([Remotion MCP 문서](https://github.com/remotion-dev/remotion/blob/main/packages/docs/docs/ai/mcp.mdx)). HyperFrames는 처음부터 Claude Code·Codex·Cursor 플러그인과 `gemini-extension.json`을 저장소 루트에 두고 스킬만 배포합니다([plugin.json](https://github.com/heygen-com/hyperframes/blob/main/plugin.json)). 2026년 하반기 공식 에이전트 연동은 MCP가 아니라 **SKILL.md 번들 + CLI 플러그인**으로 수렴했습니다. 두 엔진은 서로를 의식하며 같은 방향의 기능을 내놓고 있습니다. Remotion이 8월 25일 `@remotion/gsap`, 26일 Studio WebMCP를 냈고([v4.0.518](https://github.com/remotion-dev/remotion/releases/tag/v4.0.518)), HyperFrames가 이틀 뒤 Studio 편집 상태를 WebMCP로 노출했습니다([v0.8.17](https://github.com/heygen-com/hyperframes/releases/tag/v0.8.17)). Remotion의 최근 무게중심은 Studio 타임라인 개편과 Codex annotation 통합([v4.0.533](https://github.com/remotion-dev/remotion/releases/tag/v4.0.533))입니다. "코드로 만들고 사람이 Studio에서 다듬는" 하이브리드 편집기로 가는 중입니다.

활동량은 HyperFrames 쪽으로 기울었습니다. Wayback 실측으로 **HyperFrames는 08-19 41,601★에서 10-17 65,513★**으로 늘었고, Remotion은 08-20 56,869★에서 64,642★로 늘었습니다([HyperFrames 08-19](https://web.archive.org/web/20260819043507/https://github.com/heygen-com/hyperframes), [Remotion 08-20](https://web.archive.org/web/20260820083236/https://github.com/remotion-dev/remotion)). 최근 60일 릴리스는 169회 대 24회입니다. 다만 HyperFrames의 하루 다회 릴리스는 main 머지마다 배포하는 연속 배포이므로 성숙도 지표로 읽으면 안 됩니다([HyperFrames releases](https://github.com/heygen-com/hyperframes/releases)). 절대 규모는 여전히 Remotion이 큽니다. 최근 1주 npm 다운로드는 `remotion` 2,261,910회, `hyperframes` 811,570회입니다([remotion](https://api.npmjs.org/downloads/point/last-week/remotion), [hyperframes](https://api.npmjs.org/downloads/point/last-week/hyperframes)). 그러나 9월 대비 10월 페이스는 HyperFrames만 오르고 Remotion은 보합입니다([npm range hyperframes](https://api.npmjs.org/downloads/range/2026-04-01:2026-10-16/hyperframes)). 나머지는 사실상 멈췄습니다. Motion Canvas는 2025-02 이후 커밋이 1건이고, Revideo는 7월 15일 이후 커밋이 없습니다. 2026년 새 렌더러 중 의미 있는 것은 **academa-labs/manimgx** 하나입니다. 생성 12일 만에 1,652★를 얻었고, Manim CE API와 호환되는 Rust/wgpu 엔진이며 자체 벤치마크로 "90.6× faster than ManimCE"를 주장합니다([manimgx](https://github.com/academa-labs/manimgx)). 독립 검증은 없습니다. 중요한 외부 검증도 하나 있습니다. 가장 큰 에이전트 영상 파이프라인 **OpenMontage는 제안 단계에서 Remotion과 HyperFrames 중 하나를 `render_runtime`으로 고정**합니다([OpenMontage README](https://github.com/calesthio/OpenMontage/blob/main/README.md)). video-maker의 "프로젝트당 엔진 하나" 설계와 같은 결론입니다.

## 앱 홍보영상은 '모션 런치 필름'과 '실제 앱 조작 데모'로 갈라졌습니다

사용자가 관심을 보인 "앱 홍보영상"은 실제로는 두 가지 작업입니다. 하나는 **모션 런치 필름**입니다. UI를 HTML로 재구성하거나 스크린샷을 씬에 배치하고, 음악 비트에 맞춰 움직입니다. 다른 하나는 **실제 앱 조작 데모**입니다. 에이전트가 실제 앱을 클릭하며 녹화하고, 줌·커서·보이스오버를 입힙니다. 앞의 갈래가 별을 거의 다 가져갔습니다. **latent-spaces/brag(16,385★, MIT)**는 방금 만든 프로젝트를 음악·모션·공유 문구가 들어간 짧은 런치 영상으로 바꿉니다. Opus 5.5에서는 HyperFrames 없이 단일 파일로 동작하는 `/brag-slim`으로 자동 전환하고, 내레이션은 기본으로 꺼 둡니다([brag](https://github.com/latent-spaces/brag)). **video-shotcraft(12,231★, Apache-2.0)**는 실제 페이지를 캡처한 뒤 150샷 레시피에서 샷을 골라 Remotion으로 애니메이션하고 비트 컷과 사운드 디자인까지 합니다. 그러나 커뮤니티 쇼케이스 페이지는 "No submissions yet"입니다([video-shotcraft](https://github.com/Vincentwei1021/video-shotcraft), [showcase](https://vincentwei1021.github.io/video-shotcraft/showcase.html)). 같은 "152 shot recipe cards"를 내세운 복제 저장소가 최소 6개 있어 하나로 묶어 봐야 합니다. **onetake(2,556★)**는 컷 없는 원테이크 필름을 만들고, `probe.py` 오라클로 컷 경계의 연속성을 채점합니다(v1 0.00 반려 → 0.83 채택). 무료판은 비상업 전용입니다([onetake](https://github.com/feitangyuan/onetake), [onetakemotion.com](https://onetakemotion.com)). 흥미로운 반대 흐름도 있습니다. **product-launch-motion v2는 GSAP/HyperFrames를 버리고** 순수 HTML, closed-form spring, "music-first timing instead of voiceover"로 다시 만들었습니다([product-launch-motion](https://github.com/AbubakrChan/product-launch-motion)).

데모 갈래의 핵심 기술은 실시간 녹화가 아니라 **결정적 재생과 사후 가상 카메라**입니다. aidemo는 에이전트가 `storyboard.json` 하나를 쓰면 실제 Chrome으로 같은 조작을 재생해 녹화하고, 음성·자막·자동 줌을 붙이고 dead time을 자릅니다. 결정적이므로 GitHub Action으로 **CI에서 다시 렌더**할 수 있고 "about $0 a render"라고 합니다([aidemo](https://github.com/tandryukha/aidemo)). surajshetty3416/demo-video-skill은 Playwright로 한 단계씩 스크린샷을 찍고, 프레임별 초점과 줌을 가진 가상 카메라로 ScreenStudio풍 60fps를 합성합니다([demo-video-skill](https://github.com/surajshetty3416/demo-video-skill)). playwright-recast는 Playwright `trace.zip`을 받아 idle 가속, SRT, 보이스오버를 거쳐 1080p MP4로 만듭니다([playwright-recast](https://github.com/ThePatriczek/playwright-recast)). 이렇게 만들면 고칠 때 다시 녹화하지 않고 JSON만 고쳐 재렌더하면 됩니다. 반면 가장 인기 있는 녹화기인 openscreen(39,925★)과 Cap(23,379★)은 GUI 전용이라 에이전트가 끝까지 구동할 수 없습니다([openscreen](https://github.com/siddharthvaddem/openscreen)). 한국어로 쓸 수 있는 사례도 있습니다. chacha95/demo-video-creator는 제품 URL로 영어 40초·한국어 45초 런치 필름을 −14 LUFS로 마스터링해 저장소에 올려 두었고([demo-video-creator](https://github.com/chacha95/demo-video-creator)), Kminer2053/demo-video-skill은 "데모 영상 만들어줘" 한마디로 앱 조작 시연 mp4를 만들면서 AI 응답 대기 구간을 압축합니다([Kminer2053](https://github.com/Kminer2053/demo-video-skill)).

HyperFrames의 **product-launch-video**가 가장 엄격하게 통제되는 정식 경로입니다. 순서는 다음과 같습니다. `npx hyperframes capture`로 스크린샷·DOM·토큰을 확보하고, 실패하거나 `BLOCKED.md`가 생기면 합성 대체물을 만들지 않고 중단합니다. 프리셋을 브랜드 토큰에 리믹스해 `frame.md`를 만들고, `STORYBOARD.md`·`SCRIPT.md` 승인 게이트를 거칩니다. TTS·BGM·SFX를 만들고 약 400개 레지스트리 블록을 검색합니다. **프레임당 서브에이전트 1개**로 병렬 빌드한 뒤 전환을 주입하고, 음성 아래 BGM 스펙트럼을 깎고(`carve.mjs`), lint/check/snapshot으로 컷 전후 프레임을 비교하고, 사용자 승인을 받아 렌더합니다([product-launch-video SKILL.md](https://github.com/heygen-com/hyperframes/blob/main/skills/product-launch-video/SKILL.md)). 짧은 기능 클립에는 **motion-graphics**가 맞습니다. 대개 10초 미만(최대 약 30초), 내레이션 없음, 질문 최대 1회의 자율 실행이며, `webpage` 카테고리가 UI 스크롤·리빌·커서·콜아웃을 다룹니다([motion-graphics SKILL.md](https://github.com/heygen-com/hyperframes/blob/main/skills/motion-graphics/SKILL.md)). 릴리스 노트 영상은 pr-to-video가 맡습니다. slideshow는 SKILL.md가 "Do not `hyperframes render` a slideshow into a single MP4"라고 못박으므로 영상 도구가 아닙니다([slideshow SKILL.md](https://github.com/heygen-com/hyperframes/blob/main/skills/slideshow/SKILL.md)).

## 한국어 나레이션은 Kokoro로는 불가능하고 Typecast가 어절 타이밍까지 한 번에 줍니다

인기 도구들의 무료 기본 음성은 한국어에서 조용히 실패합니다. **Kokoro의 1차 출처 음성 목록에는 한국어가 없습니다.** 영어, 일본어, 중국어, 스페인어, 프랑스어, 힌디어, 이탈리아어, 포르투갈어뿐입니다([Kokoro-82M VOICES.md](https://huggingface.co/hexgrad/Kokoro-82M/raw/main/VOICES.md)). 일부 2026 비교 기사가 "Kokoro supports Korean"이라고 썼지만 1차 출처가 우선입니다. HyperFrames의 `npx hyperframes tts`는 Kokoro 전용이고 TTS 우선순위의 무키(no key) 폴백도 Kokoro입니다([media-use audio references](https://github.com/heygen-com/hyperframes/tree/main/skills/media-use/audio/references)). 그러니 HyperFrames 기본 경로로는 한국어 내레이션을 만들 수 없습니다. 내레이션을 켤 때 Kokoro를 쓰는 brag, 로컬 Kokoro 음성을 쓰는 explainroo도 마찬가지입니다. 전사 쪽 함정도 둘 있습니다. HyperFrames `transcribe`의 기본값 `small.en`은 비영어 음성을 영어로 번역해 버립니다(로컬 09-01 번들 문서 기준이며, upstream이 이후 넣은 Whisper 언어 자동 감지가 이 기본값을 바꿨는지는 미확인). upstream이 새로 넣은 Parakeet TDT v3는 유럽 25개 언어만 지원해 **한국어가 없습니다**([Parakeet 모델 카드](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)).

유료 경로 중에서는 **Typecast가 한국어 음성과 타임스탬프를 한 번에 줍니다.** `POST /v1/text-to-speech/with-timestamps`(권장 모델 `ssfm-v30`)는 `words`와 `characters` 배열을 초 단위 `start`·`end`로 함께 돌려주고, `granularity=word|char`로 한쪽만 받을 수도 있습니다([Typecast TTS with timestamps](https://typecast.ai/docs/api-reference/text-to-speech/text-to-speech-with-timestamps)). 공식 MCP 서버(`text_to_speech_with_timestamps` 도구), Claude 플러그인 스킬, `cast` CLI가 10월 14~15일에 함께 갱신됐습니다([typecast-skills](https://github.com/neosapience/typecast-skills), [typecast-api-mcp-server](https://github.com/neosapience/typecast-api-mcp-server)). 이 사실로 video-maker `voice-captions.md`의 `[확인 필요]` 두 건이 해소됩니다. 한국어는 띄어쓰기가 있으므로 `word` 단위가 어절 단위가 될 가능성이 높지만 실측하지는 않았습니다(추론). ElevenLabs는 한국어를 지원하지만 `with-timestamps`가 **문자 단위 정렬만** 반환합니다([ElevenLabs docs](https://elevenlabs.io/docs/api-reference/text-to-speech/convert-with-timestamps)). 공식 로컬 MCP는 8월 20일 archived 되고 OAuth 호스티드 MCP로 바뀌었습니다([elevenlabs-mcp](https://github.com/elevenlabs/elevenlabs-mcp)). HeyGen Starfish는 단어 타임스탬프를 주지만 문서에 한국어가 명시돼 있지 않습니다([HeyGen speech](https://developers.heygen.com/docs/voices/speech.md)). 따라서 한국어 기본값으로 둘 근거가 없습니다. 한국어 품질을 MOS나 CER로 직접 비교한 신뢰할 만한 2026 자료는 찾지 못했으므로, "Typecast가 한국어에서 가장 낫다"는 공급자 성격에 근거한 추론입니다.

무료·오프라인 폴백은 좁아졌습니다. 한국어를 지원하던 경량 온디바이스 TTS **Supertonic이 9월 9일 아카이브**됐기 때문입니다([supertonic](https://github.com/supertone-oss-archive/supertonic)). 남은 선택지는 edge-tts입니다. 한국어 음성 3종이 있고 `WordBoundary`와 SRT 출력을 지원하지만, 라이선스가 LGPLv3이고 Microsoft의 비공식 읽어주기 엔드포인트를 씁니다([edge-tts](https://github.com/rany2/edge-tts)). GPU가 있다면 Apache-2.0인 Qwen3-TTS(한국어 프리셋 "Sohee")와 Fun-CosyVoice3, MIT인 Chatterbox Multilingual V3가 있습니다([Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS), [CosyVoice](https://github.com/QwenAudio/CosyVoice), [chatterbox](https://github.com/resemble-ai/chatterbox)). TTS 내레이션은 대본을 이미 알고 있으므로 **자유 전사보다 강제 정렬이 낫습니다.** WhisperX는 한국어 정렬 모델 `kresnik/wav2vec2-large-xlsr-korean`을 기본 내장하고([alignment.py](https://github.com/m-bain/whisperX/blob/main/whisperx/alignment.py)), Qwen3-ForcedAligner-0.6B는 한국어를 포함한 11개 언어에서 5분 이하 음성을 정렬합니다([Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR)). 편집 쪽에서 무음 컷의 표준은 auto-editor(Unlicense, 31.7.2)입니다([auto-editor](https://github.com/WyattBlue/auto-editor)). 앱 홍보영상은 처음부터 합성하는 작업이므로 9:16은 YOLO 리프레이밍이 아니라 컴포지션 해상도를 1080×1920으로 직접 지정하는 편이 맞습니다(추론).

## 실제 위험은 AGPL, 한국 제외 조항, 무검증 설치입니다

라이선스 위험은 렌더 엔진보다 그 위의 도구에서 더 자주 생깁니다. 렌더 엔진 중에서는 Remotion만 비 OSI 자체 라이선스입니다. 개인, **직원 3명 이하 영리 조직**, 비영리, 평가 목적은 상업적 사용까지 무료입니다. 그 밖의 영리 조직은 Company License가 필요하고, Remotion 코드를 고쳐 파생물로 판매·재라이선스하는 것은 금지됩니다([Remotion LICENSE.md](https://github.com/remotion-dev/remotion/blob/main/LICENSE.md)). 2024년부터 열려 있는 Remotion 5.0 PR은 **계약자도 팀 규모에 넣도록** 바꿉니다([PR #3750](https://github.com/remotion-dev/remotion/pull/3750)). 그러면 "직원 3명 + 외주" 팀이 유료 대상으로 바뀔 수 있습니다(추론). `remotion-dev/skills`에는 LICENSE 파일이 없어 스킬 텍스트를 재배포할 조건이 불명확합니다. 반면 HyperFrames는 "no per-render fees or commercial-use thresholds"를 명시한 Apache-2.0입니다([HyperFrames README](https://github.com/heygen-com/hyperframes/blob/main/README.md)). 위층 도구에서는 **AGPL-3.0**이 두드러집니다. OpenMontage, guizang(별도 상용 라이선스 있음), OpenChatCut, pireel, Concat, mortiflix가 AGPL이고, Comfy `comfy-mcp`는 AGPL 또는 상용입니다. 서비스 백엔드에 넣으면 네트워크 사용자에게 소스를 공개할 의무를 따져야 합니다. onetake 무료판은 비상업 전용이고, 라이선스 파일이 없는 저장소(opencat 등)는 기본적으로 재배포할 수 없습니다. 음성에서는 F5-TTS 사전학습 가중치가 CC-BY-NC이고, Fish Speech는 10월 13일 개정된 커뮤니티 라이선스를 씁니다([F5-TTS](https://github.com/SWivid/F5-TTS), [Fish Speech LICENSE](https://github.com/fishaudio/fish-speech/blob/main/LICENSE)). 상업용 앱 홍보에는 Apache-2.0/MIT 계열(Qwen3-TTS, CosyVoice, Chatterbox)이 안전합니다. 생성 영상에서는 앞서 본 한국 제외 조항, Veo SynthID, 무료 티어의 상업 사용 금지(Kling·Runway, 2차 정리 자료 기준)를 확인해야 합니다.

보안 등급은 참고용 이상으로 믿으면 안 됩니다. awesome 목록의 등급은 304개 중 298개 SAFE입니다. 그러나 이는 README와 설치 문구에 대한 규칙 기반 1차 스캔이며 스스로 "not a manual audit"라고 밝힙니다([agentskillshub](https://agentskillshub.top/skill/howseen-ai/claude-motion-design/)). 실제로 `curl -fsSL … | bash` 설치를 안내하는 EverMind-AI/Raven과 공급자 키 8종을 요구하는 OpenMontage도 SAFE로 표시돼 있습니다([Raven](https://github.com/EverMind-AI/Raven), [OpenMontage](https://github.com/calesthio/OpenMontage)). HeyGen도 자기 커뮤니티 스킬 저장소에 "A skill can instruct an agent to run commands, read files, call network services, or spend money"라고 경고합니다([hyperframes-community-skills](https://github.com/heygen-com/hyperframes-community-skills)). `npx -y <패키지>@latest`로 실행 시점의 최신 npm을 받아 실행하는 도구(openfilm, FableCut, Orkas MCP)가 있습니다. digitalsamba 툴킷에는 생성 영상 워터마크 제거 도구 예시까지 들어 있습니다([claude-code-video-toolkit](https://github.com/digitalsamba/claude-code-video-toolkit)). video-maker의 기존 규칙은 이 위험을 대부분 이미 막고 있습니다. `@latest`, 원격 설치 스크립트, `npx skills add`를 금지하고 API 키는 환경 변수로만 읽습니다([SKILL.md Phase 2](../../../skills/video-maker/SKILL.md)). 따라서 유지하는 것이 맞습니다. 새로 더할 것은 생성 미디어의 워터마크·SynthID 고지와 워터마크 제거 도구 사용 금지 정도입니다(추론).

## video-maker는 진입점을 지키고 Capture·모션·한국어 세 곳을 고쳐야 합니다

현재 video-maker는 다섯 CLI 공통 진입점으로서 엔진 하나를 고르고 Script→Voice→Composition→Captions→Render 계약과 렌더 QA를 소유합니다([SKILL.md](../../../skills/video-maker/SKILL.md), [설계 기록 036](../../../memory/architecture/036-video-maker-pipeline-stages-tts-provider.md)). 이 뼈대는 외부 증거와 충돌하지 않습니다. OpenMontage도 엔진을 프로젝트 단위로 고정하고, 블라인드 실측도 렌더 능력보다 검사와 룩이 차이를 만든다고 보여 줍니다. 고칠 곳은 계약의 빈칸입니다. 아래 표는 일곱 가지 선택지에 대한 권고와, 그 권고가 노트 근거인지 추론인지를 정리한 것입니다.

**진입점은 그대로 둡니다.** HyperFrames 라우터는 스스로 "mandatory entry point"를 자칭하고, 사용자가 다른 프레임워크를 고르지 않으면 HyperFrames를 기본 출력으로 삼으며, 생성 워크플로를 진입 직전에 온디맨드로 설치합니다([HyperFrames README](https://github.com/heygen-com/hyperframes/blob/main/README.md)). 이 동작은 엔진 중립, 버전 고정, 다섯 CLI 동등성이라는 video-maker의 세 전제와 모두 충돌합니다. 네 CLI에서 이미 검증된 경계 결정([교훈 025](../../../memory/learned/025-third-party-skill-bundle-boundary.md))을 뒤집을 새 증거는 노트에 없습니다. HyperFrames가 Anthropic 공식 마켓에 올라 플러그인으로 설치되는 사례가 늘면 트리거 충돌이 더 잦아질 것입니다. 그럴수록 진입점 고정의 가치는 커집니다(추론).

**모션 우선 경로는 Voice·Captions를 건너뛰는 정식 brief 유형으로 만듭니다.** 지금 계약은 필요 없는 단계를 `SKIPPED`로 남기게만 할 뿐, 내레이션 없는 10초 안팎 단편에 맞는 흐름이 없습니다. upstream motion-graphics는 카테고리를 kinetic-type, stat, charts, logo-reveal, lower-thirds, maps, webpage로 나누고, director 서브에이전트가 `shot-plan.json`을 쓰면 builder가 만들며, 질문은 최대 1회입니다([motion-graphics SKILL.md](https://github.com/heygen-com/hyperframes/blob/main/skills/motion-graphics/SKILL.md)). video-maker에는 다음 형태가 맞습니다(추론). Phase 3에서 "motion-short" 유형이면 Voice·Captions를 `SKIPPED`로 확정하고, 스토리보드 승인 게이트를 한 번의 미리보기 승인으로 가볍게 하고, 타이밍의 정본을 음악 비트로 둡니다. 이 경로는 엔진 중립이어야 하므로 upstream 스킬을 의존성으로 두지 않습니다. 카테고리 분류와 "무음에서도 메시지 전달"이라는 기존 QA 원칙만 연결합니다. 현재 규칙인 "BGM·SFX는 명시적으로 필요할 때만"은 권리 보호 측면에서 유지합니다. 다만 프로모 유형에서는 Phase 3 Audio 행에서 BGM·SFX 여부를 반드시 한 번 묻도록 바꿀 만합니다. 실측에서 16개 중 9개가 사운드를 넣었고 상위 도구들이 music-first 타이밍을 쓰기 때문입니다(추론).

**앱 홍보영상 경로는 두 갈래를 모두 담는 참조 문서 하나와 Capture 단계로 해결합니다.** 현재 파이프라인에는 실제 화면을 확보하는 단계가 없습니다. 그런데 런치 필름도 데모도 캡처에서 품질이 결정됩니다. 런치 필름 갈래에는 product-launch-video의 단계 구성을 엔진 중립으로 옮깁니다. 순서는 캡처 → 브랜드 토큰 → 스토리보드 승인 → 오디오 → 장면별 빌드 → contact sheet 검수입니다. 특히 "캡처가 실패하면 합성 대체물을 만들지 않고 중단"한다는 규칙은 video-maker의 기존 원칙인 "실제 제품 수치·후기·로고를 추측하지 않습니다"와 정확히 맞습니다. 데모 갈래에는 aidemo·cursorcam·surajshetty가 공유하는 **"JSON 스토리보드 → 결정적 재생 → 사후 가상 카메라·idle 압축"** 패턴을 받아들입니다. 이들 저장소는 16~57★의 신생이므로 의존성으로 두지 않고 패턴만 씁니다(추론). 엔진별 캡처 도구는 다음과 같습니다. HyperFrames는 이미 읽고 있는 `hyperframes-cli` 모듈의 `capture` 명령을 쓰면 됩니다. Remotion은 프로젝트의 Playwright로 단계 스크린샷이나 trace를 확보합니다. 이 저장소에는 Playwright 흐름을 만드는 `minos` 스킬이 있으므로 그 산출물을 데모 촬영 레시피로 재사용하는 방향을 검토할 만합니다(추론). 두 가지 선택지가 남습니다. 하나는 upstream product-launch-video를 HyperFrames 선택 시 정확 경로로 읽는 선택 모듈로 승격하는 안입니다. 다른 하나는 패턴만 자체 문서로 옮기는 안입니다. 이 보고서는 후자를 권합니다. 이유는 세 가지입니다. 그 워크플로는 `BRIEF.md`, HeyGen 기본 음성(Marcia)과 음악 라이브러리, 라우터 경유를 전제합니다. 실측에서는 HyperFrames 라우터 경로가 23.5분으로 가장 느렸습니다(라우터가 어느 워크플로를 골랐는지는 공개되지 않음). upstream이 60일에 169번 바뀝니다(추론). 승격을 택한다면 교훈 025의 "워크플로 스킬은 쓰지 않는다"를 SUPERSEDED로 기록하고, 라우팅 테스트([source-only-module-routing.test.js](../../../scripts/tests/source-only-module-routing.test.js)의 video-maker 테스트)의 문구 잠금도 함께 갱신해야 합니다. 어느 쪽이든 새 활성 스킬을 만들지 않고 video-maker 안의 reference로 해결하므로 인벤토리 카운트 가드는 바뀌지 않습니다(추론).

**번들 갱신은 video-maker가 하지 않고 사용자가 결정합니다.** video-maker는 설계상 이미 설치된 서드파티 번들을 제거·갱신·재설치하지 않습니다. 그래서 갱신 여부는 저장소 관리자의 선택입니다. 갱신하지 않으면 로컬 `media-use`의 TTS 표와 전사 기본값이 9월 1일 상태로 고정됩니다. 그 상태에는 Gemini TTS도, Whisper 언어 자동 감지도 없습니다. 갱신한다면 README가 권하는 `npx hyperframes skills update`(코어 세트만 설치)를 씁니다. 이때 버전을 고정하는 방법은 노트에서 확인하지 못했으므로 `[확인 필요]`이며, 최소한 실행한 CLI 버전과 날짜를 기록해야 합니다(추론). `skills add`는 skills.sh 레지스트리를 거치므로 main보다 몇 시간 늦을 수 있습니다([HyperFrames README](https://github.com/heygen-com/hyperframes/blob/main/README.md)). 갱신 직후에는 `hyperframes-engine.md` 모듈 표의 정확 경로가 아직 유효한지 다시 확인해야 합니다. 노트가 확인한 바로는 2026-10-17 upstream에 `media-use/audio/references/{tts,tts-to-captions,transcribe}.md`와 `captions/` 경로가 존재합니다([media-use audio references](https://github.com/heygen-com/hyperframes/tree/main/skills/media-use/audio/references)). 문서 쪽에도 즉시 고칠 사실 오류가 하나 있습니다. `hyperframes-engine.md`는 `general-video`를 포함한 워크플로 스킬이 "설치되어 있지 않"다고 쓰지만, 이 PC에는 2026-09-03자 `general-video`가 설치돼 있습니다([hyperframes-engine.md](../../../skills/video-maker/references/hyperframes-engine.md)). 라우터가 온디맨드로 설치한 흔적으로 보입니다(추론). 문구를 "설치돼 있어도 진입점·워크플로로 쓰지 않는다"로 바꿔야 합니다.

**한국어 TTS·자막 기본값은 노트 근거로 바로 교정할 수 있습니다.** `voice-captions.md` 3절 공급자 표는 2026-09-04 기준입니다([voice-captions.md](../../../skills/video-maker/references/voice-captions.md)). 고칠 내용은 다섯 가지입니다. ① Typecast 타임스탬프 `[확인 필요]`를 "단어+문자, 초 단위, `granularity=word|char`, 권장 `ssfm-v30`"으로 바꿉니다. ② Kokoro 한국어 `[확인 필요]`를 "한국어 음성 없음, 한국어 나레이션에 사용 금지"로 바꿉니다. ③ ElevenLabs 행에 "공식 로컬 MCP archived, 호스티드 OAuth MCP로 이전"을 더합니다. ④ HeyGen 행에 "한국어 음성 미확인"을 명시합니다. ⑤ Edge TTS 행에 LGPLv3를 적습니다. 선택 규칙은 지금 순서(한국어면 Typecast 제안, 비용을 못 쓰면 Edge TTS)를 유지합니다. 다만 오프라인 폴백으로 Qwen3-TTS·CosyVoice3(Apache-2.0)를, 상업 영상 후보 제외 대상으로 F5-TTS 가중치와 Fish Speech를 추가할 만합니다. 5절 자막 정렬 분기에는 "음성이 TTS이고 공급자 타임스탬프가 없으면 자유 전사보다 대본 기반 강제 정렬(WhisperX `ko`, Qwen3-ForcedAligner 5분 단위)을 우선"하는 행을 넣습니다. 전사 금지 목록에는 기존 `.en` 모델에 더해 Parakeet와 OpenAI `gpt-*-transcribe`를 넣습니다. OpenAI에서 단어 타임스탬프는 `whisper-1`만 지원합니다([OpenAI STT](https://developers.openai.com/api/docs/guides/speech-to-text)).

**생성형 B-roll은 기본 꺼진 선택 단계로만 연동합니다.** 생성 클립이 이득인 곳은 실사 인물, 제품이 실제 환경에 놓인 장면, 분위기 B-roll, 히어로 샷입니다. UI 화면, 키네틱 타이포, 수치·차트, 로고는 결정적 코드 렌더가 맞습니다(추론). 규칙은 다섯 가지입니다(추론). 생성 전에 공급자, 모델, 길이, 예상 비용을 제시하고 승인을 받습니다(OpenMontage의 비용 게이트와 기존 "요금 발생 호출은 확인 후" 규칙의 결합). 결과는 즉시 로컬 파일로 고정해 해시와 함께 `video-qa.md` 5절 provenance 표에 적습니다. 생성 영상 안에 텍스트를 그리게 하지 않고 텍스트·로고·CTA는 코드로 덧입힙니다. 한국에서 로컬 오픈웨이트를 쓸 때는 HunyuanVideo-1.5와 MiniMax H3를 배제합니다. Veo 출력에는 SynthID 고지를 남깁니다. 이 사용자 환경에는 Kling 공식 MCP가 이미 연결돼 있어 가장 마찰이 적은 경로입니다. 그러나 MCP 커넥터는 CLI마다 다르므로 다섯 CLI 동등성을 위해 이 단계는 커넥터가 없으면 `NOT RUN`으로 떨어지는 선택 단계여야 합니다(추론).

**Claude Motion은 아무것도 만들지 않고 기다립니다.** 공식 문서에 Claude Code·API·스킬 경로가 없고 이 계정의 Artifact 타입에도 없으므로, 지금 연동할 대상이 없습니다. 재검토 조건(reopen-when)만 기록합니다. Anthropic이 Motion을 Claude Code·API·`anthropics/skills`·Artifact 타입 중 하나로 노출하면 그때 엔진 라우터의 세 번째 선택지로 검토합니다.

흡수·변환·무시 판정은 저장소의 기존 조사 형식([motion-web 조사](../2026-10-06-motion-web-assessment.md))을 따라 정리합니다.

## 결론

이번 조사로 희소한 자원이 무엇인지에 대한 이해가 바뀌었습니다. 2026년 하반기 코딩 에이전트는 스킬 없이도 그럴듯한 15초 프로모를 렌더합니다. 그래서 차별화는 "무엇을 만들 수 있나"에서 **"만든 것을 무엇으로 검증하나"**로 옮겨 갔습니다. 상위 도구들이 미감을 연속성 점수, 라우드니스, 정지 프레임 같은 숫자로 강제하는 것도 그 때문입니다. video-maker가 처음부터 렌더 QA를 계약으로 소유한 것은 우연히 맞는 방향이었고, 현대화의 중심도 워크플로 추가보다 측정 가능한 검사를 늘리는 데 있어야 합니다. 같은 맥락에서 한국어는 숨은 강점입니다. 별을 가장 많이 받은 경로들(HyperFrames 무키 기본값, brag의 음성 옵션, explainroo)이 한국어에서 소리 없이 실패하는 Kokoro에 기대고 있으므로, 한국어 TTS·정렬 규칙을 명시한 진입점은 생태계에서 드뭅니다.

남은 긴장은 upstream 속도입니다. HyperFrames는 60일에 169번 배포되고 핵심 워크플로 문서가 매주 바뀝니다. 그래서 번들 모듈을 정확 경로로 읽는 설계는 의존을 늘릴수록 유지비가 커집니다. 실천적 함의는 분명합니다. video-maker는 계약(단계, 검사, 한국어 규칙, 권리 기록)을 자체 문서로 소유하고, 번들은 엔진 사용법(core 계약, cli 명령, media-use 오디오)에만 기대야 합니다. 그리고 번들을 갱신할 때마다 경로 테스트를 다시 돌리는 절차를 사람이 결정하는 이벤트로 남겨야 합니다. Claude Motion이 같은 "코드로 만든 애니메이션 + MP4" 방향을 택했다는 점은 이 설계가 맞다는 신호입니다. 그러나 대응 경로가 열리기 전까지는 기록만 하고 기다리는 것이 가장 싼 선택입니다.
