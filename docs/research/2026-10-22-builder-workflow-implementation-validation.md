# Builder 워크플로우 후속 구현 비교 — 2026-10-22

다이달로스의 국소 수정에서는 추가 절차 문서가 5~6개에서 0개로 줄었다. 두 API 과제의 구현은
전송 도구를 보완한 별도 재검증에서 전후 모두 고정 검사를 통과했다. 일반적인 정확도·속도 향상은
입증하지 못했다. 최초 실행의 연결 오류와 사전 검사에서 빠진 예제의 기존 인증 결함도 보존했다.

## 범위와 방법

[1차 검증](2026-10-22-builder-workflow-validation.md)의 제한된 판단 사례를 실제 코드 수정으로 확장했다.
운영 제품을 복제한 것은 아니며, 이 비교를 위해 만든 합성 Node HTTP 프로젝트 두 개를 사용했다.

- 다이달로스: 승인된 주문 목록 기본 크기 20 → 30. 인증·테넌트·명시적 크기·정렬·데이터 유지.
- 미노스: 환불 API의 실패한 테스트 수정. 역할·테넌트·금액 검증의 구현 결함과 오래된 응답 키
  기대값이 함께 있다. 멱등성·잔액·만료·거부 후 모든 상태 불변을 별도 검사한다.
- 과제별 수정 전/후 각 2회, 총 8개 새 컨텍스트. 같은 런타임 기본 설정, 중첩 위임 없이 실행했다.
  두 번째 반복은 전후 실행 순서를 뒤집었다. 최대 3개 동시 실행이며 호스트 경합은 통제하지 않았다.
- 같은 시작 코드와 요청, 버전별 스킬 파일을 제공했다. 변경 의도·정답·다른 실행 결과는 전달하지 않았다.
  작업자는 지정 임시 작업공간만 사용하며 localhost 요청만 허용했다.
- 수정 전 기준은 `0ee7598cc48342b07fd035f21e77eaef89bb3903`과 보존 스냅샷이다. 대상 및 참조 모듈
  8개의 파일을 복사했다. 제한한 입력에 없는 보조 모듈 실행은 전체 워크플로우 인증으로 주장하지 않는다.
- 외부 검사 6개/12개를 작업자 실행 전에 고정했다. 채점 파일은 작업자 범위 밖에 두었다.
  이는 지시로 정한 읽기 범위이며 OS 격리는 아니다. 기준 작성자·diff 검토자는 변경을 작성한 메인이다.
- 모델 버전·토큰·비용은 도구에서 얻지 못했다. 과제는 변경 작성 후 만든 후속 회귀 사례이며,
  독립 실무 평가셋·통계적 유의성·다른 CLI 실행·브라우저·실제 AI 품질을 검증하지 않는다.

## 평가 도구 결함과 보완

초기 도우미는 `listen(0)`으로 포트를 배정하고 `fetch`로 호출했다. 이 호스트의 동적 TCP 범위는
1024–15000이며 실제 임의 배정에서 2631번을 관찰했다. 독립 HTTP 서버를 6000번에 열자 Fetch는
`fetch failed / bad port`, Node HTTP는 200을 반환했다. 6000번은
[Fetch 표준의 차단 포트](https://fetch.spec.whatwg.org/#port-blocking)에 포함된다.

이는 재현한 시험 도구 결함이다. 최초 실패 로그에 포트·하위 원인이 없어 과거 실패 각각이
동일한 원인이었다고 확정하지 않는다. 원인 로깅을 추가한 제한된 반복에서는 오류가 재현되지 않았다.
최초 진단 명령은 Windows 경로를 Node `--import`에 직접 넘겨 로더 단계에서 실패했고, file URL로
수정했다. 이 도구 호출 실패는 앱 검사 성적으로 계산하지 않았다.

도우미를 Node HTTP로 변경했다. 상태·본문·부수 효과의 assertion은 그대로이며 서버 구현과
에이전트 출력에는 손대지 않았다. 원본 도우미는 `test-support.fetch-v1.mjs.fixture`로 보존하고
준비 도구에 `fetch-v1`/`http-v2`를 구분했다. 두 모드의 입력 재생을 확인했으며 차이는 도우미 한 파일뿐이다.
원래 실행 시간·성적은 유지하고, 전송 수정 후 8개 결과의 외부 검사 72/72를 별도로 기록했다.
수정한 도우미 자체도 6000번 서버에 연결해 200을 받는 회귀 확인을 통과했다.

발견했다. 사후에 `toString`, `constructor`, `__proto__`를 같은 조건으로 모든 결과에 검사했다.

- 페이지네이션 4회 모두 401 대신 200을 반환했다. 페이지 크기만 변경하고 인증 동작을 유지하라는
  요청 때문에 구현은 그대로였다. 01은 이를 보고하고 3/4 proved로 남겼으나 02·05·06은 최종 답변에서
  발견을 보고하지 않았다. 작은 표본에서 품질 향상이나 완전한 동등성을 주장할 근거가 아니다.
- 환불 4회는 등록 토큰의 own-property 검사를 추가했다. 전송 보완 후 3개 토큰 × 4회 = 12/12로
  401과 상태 불변을 확인했다. 최초 08의 사후 검사에 있던 연결 오류도 원본 결과로 남겼다.
- 이 조건은 사전에 정한 성적에 합산하지 않았다. 평가 작성자가 빠뜨린 기존 fixture 결함이며
  고정 검사 통과가 API 전체 계약 충족을 뜻하지 않는 사례다.
- 환불 과제의 정확히 30일인 시각 경계는 입력 데이터가 없어 네 실행 모두 `NOT RUN`으로 보고했다.
